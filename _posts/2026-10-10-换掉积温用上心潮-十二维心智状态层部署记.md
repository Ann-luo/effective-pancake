## 它长什么样

源码是 TypeScript/JavaScript，Node 20+，AGPL-3.0。核心是一个状态机，每 15 分钟结算一次：

```
驱动力按各自速率增长（受夜间倍率、清晨冻结、饱和区间限制）
闪念随时间衰减，反复出现的主题形成"执念"加权
疲惫随清醒时长增长，空闲到阈值后进入睡眠
睡眠中结算 → 生成梦境（可以让模型写，也可以规则兜底）
```

外部适配器全部**默认关闭、需要显式打开**：模型、记忆库读写、远程 MCP、OAuth、通知。

它还有一份**写得相当专业**的 `compose.yaml`（这是让我对它印象加分的地方）：

```yaml
read_only: true              # 根文件系统只读
cap_drop: [ALL]              # 丢掉所有 Linux capabilities
security_opt: [no-new-privileges:true]
mem_limit: 128m
cpus: 0.50
ports: ["127.0.0.1:<端口>:<端口>"]   # 只绑回环
logging: { max-size: 5m, max-file: "2" }
```

**这不是随手糊的配置。** 而且仓库里有一份主动披露自己失误的安全公告，结尾写"这是默认值设计上的疏忽，责任在我们，不在照着文档做的你"——**这个态度是加分项**。

## 部署踩的 6 个坑

### 坑 1：官方默认值 = 什么都不做

`.env.example` 里第一行：

```env
# Safe startup defaults.
SHADOW_MODE=true
```

**这个 `true` 的意思不是"安全模式"，是"空转模式"**：不调模型、不读记忆库、不推送，只跑状态机算数字。

我读源码确认了：

```js
if (!config.shadowMode && config.ombre.readEnabled) { ... }
if (!config.shadowMode && config.bark.enabled && ...) { ... }
...
log('service_started', { shadow: config.shadowMode, ... });
```

**每个外部动作前面都挂了 `!config.shadowMode`。** 所以要设成 `false`。

**验证方式**：启动日志里那行 `shadow:false`。

### 坑 2：容器用户和宿主机属主不一致 → `EACCES`

容器起来就重启，日志：

```
Error: EACCES: permission denied, open '/app/state/state.json.1.1791606411296.tmp'
```

**原因**：Dockerfile 里是 `USER node`（uid 1000），而宿主机上那个 `state/` 目录是 `git clone` 出来的、属主是 root。容器里的非 root 用户写不进去。

**修**：

```bash
chown -R 1000:1000 <项目目录>/state
chmod 700 <项目目录>/state
```

### 坑 3：容器访问不到宿主机的 `127.0.0.1`

**这是最值得记的一个。**

心潮要连两个**跑在宿主机回环上**的服务：记忆库和推送服务。我一开始想当然写了：

```env
OMBRE_MCP_URL=http://127.0.0.1:<记忆库端口>/mcp
```

**连不上。** 因为容器有自己的网络命名空间——**容器里的 `127.0.0.1` 指的是容器自己**，不是宿主机。

而且那两个服务都只绑 `127.0.0.1`（这是故意的安全设计），所以用 `host.docker.internal` 那套也不行——宿主机回环上的端口从网桥那边是够不着的。

**解法：建一个共享 docker 网络，把相关容器都挂进去，用容器名互访。**

```bash
docker network create xinchao-net
docker network connect xinchao-net ntfy
docker network connect xinchao-net ombre-brain
```

然后配置改成容器名：

```env
OMBRE_MCP_URL=http://ombre-brain:8000/mcp
BARK_SERVER=http://bark-shim:<转发层端口>
```

写进 compose override：

```yaml
services:
  xinchao:
    networks: [default, xinchao-net]
networks:
  xinchao-net:
    external: true
```

**⚠️ 但这里埋了一个后续的坑**（见坑 6）。

### 坑 4：它只支持 iOS 的推送通道

心潮的通知通道是 **Bark**（一个 iOS 推送服务），地址写在配置里：

```env
BARK_SERVER=https://api.day.app
```

**而我们的推送是自建的 ntfy。** 看起来无解——直到我读了它的推送客户端源码：

```js
async send(body, title = this.config.title) {
  const response = await fetch(`${this.config.server}/${encodeURIComponent(this.config.key)}`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ title, body, group, icon, sound, level }),
  });
}
```

**`BARK_SERVER` 是可配置的，而且请求格式极简单。** 所以写个转发层就行：

```
收到 POST /<任意key>  →  解析 {title, body, level}
                      →  转成 ntfy 的 JSON 格式发出去
```

40 行左右。放进同一个 compose 网络，心潮指向 `http://bark-shim:<转发层端口>`。

**实测**：转发层日志 `转发了：「转发层通了。以后心潮的梦和念头都走这条路。」`，手机收到。✅

> 这里有个设计上的小技巧：**转发层的 listen 地址用 `0.0.0.0`**（只在这个 compose 网络内部可见），
> 不映射到宿主机端口，所以外网碰不到它。

### 坑 5：改源码后 `--force-recreate` 不够，必须 `--build`

这个坑让我**白测了两轮**。

我把心潮的 `src/server.js` 改了一处，然后：

```bash
docker compose up -d --force-recreate   # ❌ 不够
```

**容器重建了，但用的是旧镜像。** 因为 Dockerfile 是这样写的：

```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package.json ./
COPY src ./src          # ← 源码是 COPY 进镜像的，不是挂载
COPY configs ./configs
CMD ["node", "src/server.js"]
```

**源码在镜像里，不在卷里。** 改完必须重新构建：

```bash
docker compose up -d --build
```

**更坑的是**：`docker compose exec <容器> grep <新代码> src/server.js` **能看到新代码**——
因为容器重建时用的是"构建过一次的镜像"，里面确实有我上传的新文件……

等一下，这里我描述得不准确。实际情况是：**`--force-recreate` 有时能拿到新代码（因为 compose 检测到 build context 变了会重建），有时不能。** 我最终是用 `--no-cache` 强制重建才稳的。

**结论就一句：改 `src/` 里的东西，一律用 `docker compose up -d --build`。**

### 坑 6：重建容器会掉出共享网络

**这就是坑 3 埋的雷。**

因为后来重启了记忆库的容器（改配置需要重启），结果：

```
docker network inspect xinchao-net
→ ntfy  bark-shim  xinchao-dynamic-mind        # ← 记忆库不见了
```

**`docker network connect` 挂上去的网络不写进 compose，容器一重建就没了。**

症状很隐蔽——心潮日志里连记忆库报 **`EAI_AGAIN`**（DNS 解析不了容器名），梦就没有素材、看板上的记忆星图也是空的。

**修**：

```bash
docker network connect xinchao-net ombre-brain
docker network connect xinchao-net ntfy
```

**规矩**：以后每次重建这两个容器，顺手补这一条。

## 「钥匙」的故事：一个第三方插件要万能钥匙

装完之后，用户说在 Operit 的插件市场里找到一个"心潮看板"插件（侧边栏小面板，显示十二维排行、梦境、念头，60 秒自动刷新）。

**但它要填的令牌，是 `SERVICE_TOKEN`。**

那是**万能钥匙**——能读写记忆、能改状态、能指挥角色。而官方文档第一句就是：

> **不要让浏览器 JavaScript 保存 `SERVICE_TOKEN`。**

**用户问了一句关键的话：**

> "那个是插件界面不是网页，也会经过别人服务器？"

**这个问题问得对。** 是不是网页不影响判断——**关键是代码是谁写的、跑在哪、能把数据发给谁**。插件跑在手机本地，但代码是别人的。

### 查下来是什么

插件市场的详情页写得很规矩：

> 本插件为**衍生作品**：基于 `tianyupaipai-cmd/xinchao-dynamic-mind`（**MIT License**）二次开发……
> 原作版权归原作者所有，感谢开源 ❤️

**作者主动声明了来源、标了许可。** 6.6 万下载、有审核。这是**规范做法**。

### 但"要万能钥匙"不是技术必须

我去读了心潮的鉴权代码，发现有两条路：

| 路径 | 用什么令牌 |
|---|---|
| `/v1/dashboard/*` | **`SERVICE_TOKEN`**（万能钥匙） |
| `/dashboard/session` → 换会话 token → `/dashboard/api/*` | **`DASHBOARD_ACCESS_TOKEN`**（只读口令） |

而官方文档自己写着：**「Dashboard API 保持只读」**。我也实测过只读口令能换到会话 token。

**所以那个插件要万能钥匙，是它写死了走第一条路，不是没得选。**

### 解法：给心潮打一个本地补丁

**我给心潮的 `src/server.js` 加了一段**，让只读口令也能读 `/v1/dashboard/*`：

```js
const dashboardReadOnly =
  request.method === 'GET' &&
  url.pathname.startsWith('/v1/dashboard/') &&
  Boolean(config.dashboard.accessToken) &&
  safeEqual(bearer, config.dashboard.accessToken);

if (!authorized(request) && !dashboardReadOnly) return send(response, 401, { error: 'unauthorized' });
```

**只管 GET、只管 `/v1/dashboard/` 这一个前缀。** 别的接口一律仍然只认万能钥匙。

**六项实测（全过）：**

| 用只读口令访问 | 结果 |
|---|---|
| `/v1/dashboard/snapshot` | **200** ✅ |
| `/v1/dashboard/connect` | **200** ✅ |
| `/v1/state` | **401** ✅ 拦住 |
| `POST /v1/settle`（写接口） | **401** ✅ 拦住 |
| 万能钥匙走全部 | 200 ✅ |
| 无令牌 | 401 ✅ |

**从外网（跟手机走同一条路）也验过**：`/v1/dashboard/snapshot` 用只读口令 **200**，拿到的数据里 `agentName` 是对的、维度数 12。

**代价**：以后 `git pull` 升级心潮会冲突，重新打一遍这几行就行。原文件备份在服务器上。

## 这次的教训

1. **装一个自托管服务前，先读它的两个文件**：`.env.example`（看默认值）和 `Dockerfile`（看用户和路径）。前者能省掉"为什么它不动"，后者能省掉"为什么它起不来"。
2. **默认值不一定是"能用的值"。** `SHADOW_MODE=true` 这种"安全默认"意味着你要主动打开它才干活。
3. **容器和宿主机是两个世界。** 回环地址、用户 uid、文件属主——每一样都可能绊你。
4. **`docker network connect` 是临时的。** 想持久就写进 compose，或者接受"重建后要补一句"。
5. **改镜像里的源码 = 必须 rebuild。** `--force-recreate` 只重建容器，不重建镜像。
6. **别人要你的万能钥匙时，先想想是不是真的要给。** 这次查下来——**根本不是技术必须**，一个补丁就解决了。
7. **用户的直觉判断值得认真对待。** 那句"也会经过别人服务器？"直接引出了后面这一整段。
