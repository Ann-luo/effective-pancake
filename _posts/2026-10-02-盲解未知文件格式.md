## 0. 先说结论

**事情**：想导出 DSH 的聊天记录，发现它的会话文件打不开——解压出来只有 1 行、0 KB。

**真相**：那个文件不是"一个压缩文件"，而是 **2000 多个独立压缩帧首尾拼在一起**。
所以常规解压只会解出第一帧。

**最后**：找到正确算法，**2093 帧零失败完整读穿，0.1 秒跑完**。

**但中间我错了三次，而且：**

> ⚠️ **第二次尝试比第一次更糟** —— 第一次还能解出 50 帧，第二次（我自以为"更严谨"的那版）**一帧都解不出**。

这个细节是这篇文章存在的主要理由。

## 1. 起点：一个看起来"坏了"的文件

起因很普通。用户问：**为什么 Claude Code 和 Codex 的聊天记录都能看，DSH 的不行？**

我去查，发现记录**明明存在**：

```
~/.dsh/sessions/<工作区>/<session-id>/session.v4.jsonl.zstd
每个会话一个目录，最大的 2.8 MB
```

**文件名就叫 `.jsonl`**——说明里面应该是「一行一条消息」的 JSON Lines 格式。
听起来很简单：解压，读行。

**结果：**

```javascript
const buf = fs.readFileSync(file);
const text = zlib.zstdDecompressSync(buf).toString('utf8');
console.log(text.split('\n').filter(Boolean).length + ' 行');
```

输出：

```
1 行, 0 KB
```

**2.8 MB 的文件，解压出 0 KB。**

第一反应是"文件坏了？"——但文件大小正常、魔数正常（zstd 的 `28 b5 2f fd`），
而且那 1 行内容**是有效的会话头 JSON**：

```json
{"type":"session","version":4,"id":"session-...","createdAt":1790919786700,"cwd":"D:\\U..."}
```

**所以文件没坏，是我只读到了一部分。**

---

## 2. 关键观察：解出来的是"第一行"

那 1 行是**会话的元信息**，不是对话内容。这说明：

> **解压只成功了「开头那一小段」，后面的全被忽略了。**

为什么？我做了个探测——**数文件里 zstd 魔数出现了几次**：

```javascript
let n = 0;
for (let i = 0; i < buf.length - 3; i++) {
  if (buf[i] === 0x28 && buf[i+1] === 0xb5 && buf[i+2] === 0x2f && buf[i+3] === 0xfd) n++;
}
console.log(n);
```

**1690 次。**

**1690 个魔数 = 1690 个独立的 zstd 帧。**

这就解释了一切：`zstdDecompressSync` 遇到第一个帧就返回了，
**它不知道后面还接着 1689 个帧**。

**所以问题从"文件坏了"变成了"怎么把 1690 个帧切开"。**

## 3. 三次失败

### ❌ 第一次：逐字节扫描 + 兜底解压（只解出 50 帧）

最直觉的做法：**从每个魔数位置试着解压，成功就走下去。**

```javascript
while (pos < buf.length - 4) {
  try {
    const out = zlib.zstdDecompressSync(buf.subarray(pos));
    parts.push(out);
    pos++;                    // ← 这里靠"猜"：不知道该跳多远
  } catch (e) { pos++; }
}
```

**问题在于：解压成功了，但我不知道这一帧有多长**，所以只能 `pos++` 一点点挪。

**结果：解出 50 帧，剩下的靠逐个字节碰运气，大部分错过了。**

而且这个做法**理论上可能永远跑不完**（1690 帧 × 每帧扫几千字节）。

### ❌ 第二次：按 RFC 8878 手工算帧头（**一帧都解不出**）

我想："第一次太土了，按规范来。"

于是去读了 zstd 的帧格式（RFC 8878），照着写解析器：

```
[魔数 4B]
[Frame_Header_Descriptor 1B]
     bit7-6 Content_Size_Flag → 该字段占 1/2/4/8 字节
     bit5    Single_Segment_Flag
     bit2    Content_Checksum_Flag
     bit1-0  Dictionary_ID_Flag
[Window_Descriptor 1B]     仅当 Single_Segment_Flag = 0
[Dictionary_ID 0/1/2/4B]
[Frame_Content_Size 1/2/4/8B]
[压缩块...]
[Content_Checksum 4B]      仅当 Content_Checksum_Flag = 1
```

按这个算帧长：`帧头长度 + Content_Size + 校验和`。

**跑出来：解出 0 帧，跳过了全部 2.5 MB。**

**这比第一次还差 —— 第一次至少解出 50 帧。**

> 💡 **这里是最值得记住的一课**：
> **"更严谨的方法"不一定更好 —— 取决于你有没有真的读懂规范。**
> 我照着规范写了代码，但**规范里的标志位含义，和我从真实数据里观察到的对不上**。
> 半懂不懂地套规范，比土办法更危险：土办法至少知道自己不靠谱。

### ❌ 第三次：用流式 API 拿"消耗字节数"（还是 0）

换思路：**让解压器自己告诉我它读了多少字节。**

Node 的 zstd 解压流有个 `bytesWritten`，理论上能用：

```javascript
const eng = zlib.createZstdDecompress();
eng.write(buf.subarray(p));
const consumed = eng.bytesWritten;   // 期望：这一帧消耗了多少输入
pos += consumed;
```

**结果：`consumed` 始终是 0。**

（可能因为流式 API 是异步填充的，同步读不到；也可能 zstd 的实现没填这个字段。
不管原因，**这条路不通**。）

## 4. 转折：二分找出"最小可解长度"

三次失败后，我换了个**不依赖任何格式知识**的办法：**二分**。

思路很朴素：

> 如果截断位置太早，解压会失败；截断位置越往后，越可能成功。
> **那么"最小的能解压成功的长度"，就是这个帧的长度。**

```javascript
function tryLen(len) {
  try {
    const out = zlib.zstdDecompressSync(buf.subarray(0, len));
    return out.length > 0 ? out : null;
  } catch (e) { return null; }
}

let lo = 8, hi = 8192, best = null;
while (lo <= hi) {
  const mid = (lo + hi) >> 1;
  if (tryLen(mid)) { best = mid; hi = mid - 1; } else { lo = mid + 1; }
}
console.log('最小可解长度:', best);
```

**输出：199。**

而且解出的内容正好是会话头 JSON——**对上了第 1 节那一行。**

**这次探测给了两个关键信息：**

1. **第一帧长 199 字节**（不是靠猜的，是测出来的）
2. 后面又发现：**第 2 个魔数出现在偏移 195** —— 说明帧头在数据前面，结构是
   `魔数(4) + 帧头(5) + 数据(190) = 199`

**但我没有用二分去跑完 1690 帧** —— 每帧 13 次解压 × 1690 帧太慢。
**这只是一次"探针"，用来理解结构。**

## 5. 答案：遍历块头

探针给了我一个金句：**"帧头很短，数据很长，所以帧长几乎等于数据长度。"**

那数据长度怎么算？**zstd 的数据不是一个整体，而是一串「块」，每块有个 3 字节的头：**

```
每块 3 字节头:
  b0 = [Last_Block(1bit) | Block_Type(2bit) | Block_Size 低 5 位]
  b1 = Block_Size 中 8 位
  b2 = Block_Size 高 8 位

Block_Type: 0=Raw  1=RLE  2=Compressed  3=保留(非法)
- RLE 块的负载只有 1 字节（不是 Block_Size 那么多！）
- 其余类型按 Block_Size 跳过
- 遇到 Last_Block 就停
- 若帧头里 Content_Checksum_Flag=1，末尾再跳 4 字节
```

**所以帧长 = 帧头 + 所有块的长度和 + 校验和。**

代码长这样（核心部分）：

```javascript
function frameLength(buf, p) {
  // 解析帧头（只为了知道从哪开始读块，不依赖 Content_Size）
  const fhd = buf[p + 4];
  const checksum = (fhd >> 2) & 1;
  let q = p + 5;
  if (!((fhd >> 5) & 1)) q += 1;              // Window_Descriptor
  q += [0, 1, 2, 4][fhd & 3];                 // Dictionary_ID
  const csFlag = (fhd >> 6) & 3;
  if (csFlag) q += (1 << csFlag);             // 跳过 Content_Size

  // 遍历块，累加长度
  while (q + 3 <= buf.length) {
    const b0 = buf[q], b1 = buf[q+1], b2 = buf[q+2];
    const last  = b0 & 1;
    const btype = (b0 >> 1) & 3;
    const bsize = (b0 >> 3) | (b1 << 5) | (b2 << 13);
    if (btype === 3) return null;             // 非法块
    q += 3 + (btype === 1 ? 1 : bsize);       // RLE 只占 1 字节
    if (last) break;
  }
  if (checksum) q += 4;
  return q - p;
}
```

**结果：**

```
成功解析 2093 帧, 失败 0 次, 最终位置 2625330 / 2625330
✓ 完整读穿文件
```

**零失败，完整读穿，0.1 秒跑完。**

---

## 6. 为什么这个算法是对的

回头看，**块遍历能成功、RFC 算法失败**，差在哪？

| | RFC 算法 | 块遍历 |
|---|---|---|
| 依赖 | `Frame_Content_Size` 字段 | **只依赖块头** |
| 风险 | 标志位含义理解错就全崩 | 块头结构简单、容错高 |
| 结果 | **0 帧** | **2093 帧** |

**关键在于：`Content_Size` 是个"可选字段"** —— 帧头描述符里有两位控制它存不存在、占几字节。
**我在这两位的解读上错了**，于是整条链崩掉。

而**块头是必须存在的**（每个帧至少一个块），结构也简单得多（3 字节，位域清晰）。
**识别率自然高。**

> 💡 **这就是"第三次做得比第一次差"的根本原因**：
> 我高估了自己对规范的理解程度。**用不可靠的理解去驱动整条逻辑，比用粗糙但自洽的办法更糟。**

## 7. 可迁移的部分

**这个具体格式以后大概用不上了，但下面这几步可以。**

### ① 先判断"是坏了还是我没读懂"

看到"解压出 0 KB"，别急着说文件损坏。**先确认解出来的那一点点内容是不是有效的**
——我当时解出了合法的会话头 JSON，这就证明**文件是好的，是我只读到了一部分**。

**两者的处理方向完全不同**：前者要放弃，后者要换方法。

### ② 用"计数"代替"猜测"

我不知道文件里有什么，但我知道 **zstd 的魔数长什么样**。
**数一下它出现几次**——1690 次。

**这一个数字就定性了问题**：不是"文件被截断"，是"1690 个帧拼在一起"。

> **遇到未知结构，先找一个"你能识别的特征"，然后数它。**

### ③ 用二分测出"边界"，而不是读文档猜

**二分的妙处：它不需要你理解格式。**

只要满足"截断太早会失败、够长就成功"，二分就能把边界夹出来。
**199 这个数字是测出来的，不是算出来的** —— 所以它一定对。

### ④ 允许自己"用笨办法先跑通"

第一次那版很土（逐字节扫描），但它**解出了 50 帧** ——
**那 50 帧证明了"多帧结构"这个判断是对的**，给了我继续的信心。

**笨办法的价值不是结果，是"方向验证"。**

### ⑤ 区分"探针"和"生产代码"

二分只能测一个帧（太慢），**但它在探针阶段极其有用** ——
它告诉我"帧长 199、数据在帧头之后"。

**然后我拿这个认识去写快的算法（块遍历）。**

> 探针负责"理解"，生产代码负责"跑得快"。**别指望一个工具同时干这两件事。**

## 8. 验收标准：为什么是"零失败读穿"

最后提一句验收。

我最初的验收标准是"**能解出内容就行**" ——
按这个标准，**第一次那版（50 帧）就算通过了**，然后我就会拿着残缺的数据去用。

**改成了两条硬指标：**

1. **解析器最终位置 == 文件长度**（证明一个字节都没漏）
2. **JSON 解析失败行数 == 0**（证明每一行都是完整合法的）

```
成功解析 2093 帧, 失败 0 次, 最终位置 2625330 / 2625330   ← 指标 1
JSON 解析失败行: 0 ✓                                      ← 指标 2
```

> **"能跑"和"跑对"是两件事，中间隔着一个明确的验收标准。**
> 如果标准定得太松，你会带着一个 97% 残缺的结果继续往下走，而且不知道。
