## 先说结论（懒人版）

1. 心潮（一个自托管的"心智状态层"）会**做梦**：疲惫攒够了进入睡眠，睡眠里结算出一个梦境——有正文、有"醒后余韵"、有"梦里有没有意识到自己在做梦"的程度。
2. **问题**：梦只在它自己的状态文件里。官方看板是**第三方网页**，想看完整正文得开一个开关，那段文字会经过别人的服务器。
3. **而心潮生成梦时会读你的记忆库当素材** —— 所以正文里**可能带出私人内容**。这就不能随便往外送了。
4. **用户拍板选第三条路**：不走第三方看板，改成——**短句推自己的推送通道，完整梦境写进自己的记忆库**。这样梦还变成了"它自己记得的事"，比读一份报告更自然。
5. 实现踩了三个坑：**推送单条上限 4096 字节**（长文直接 413）、**测试脚本把查询回显误判成命中**、**记忆库拒绝物理删除普通记录**（好事）。
6. **自查时还发现两个会"重复写记忆"的隐患**：存档攒到最后才写、存档非原子写。两个都改掉了。

## 背景：它会做梦

心潮的状态机里有一条链：

```
疲惫随清醒时长增长
   ↓ 空闲到阈值
进入睡眠
   ↓
睡眠结算 → 生成梦境
   ├── dream      （梦境正文，可以让模型写）
   ├── residue    （醒后余韵，短）
   ├── awareness  （梦里的觉察）
   └── lucidity   （0~1，梦里意识到自己在做梦的程度）
```

**"梦境正文"是长文**（源码里截断到 4000 字），**"余韵"是短句**（截断到 1200 字）。

用户看到这个东西的第一反应是："我想看。"

---

## 问题：官方看板是第三方的

心潮**自己不带网页看板** —— 它的 `/dashboard/` 只返回 API（无鉴权时是 `401 {"error":"unauthorized"}`）。

网页看板来自一个**公开可视化站**。要在上面看到完整梦境正文，得在服务端打开：

```env
DASHBOARD_INCLUDE_PRIVATE_TEXT=true
```

而它的默认值和注释是这么写的：

```env
# Dream summaries/residue can contain private text. They stay hidden by default.
DASHBOARD_INCLUDE_PRIVATE_TEXT=false
```

**为什么要默认关着？** 因为心潮生成梦的时候会**去读你的记忆库当素材**：

```
近期记忆材料：<从记忆库拿到的内容>
```

所以梦的正文里可能不是"它梦见了什么"，而是**"它梦见了你说过的话"**。

打开那个开关 = 把这段文字交给第三方网页的 JavaScript。

---

## 三条路，用户选了第三条

我把选项摆出来：

| | 做法 | 正文经过第三方吗 |
|---|---|---|
| **A** | 打开 `INCLUDE_PRIVATE_TEXT`，在第三方看板上看 | ⚠️ **经过** |
| **B** | 不开，只看时间/来源/"有没有余韵" | ✅ 不经过 |
| **C** | **自己写一个桥**：短句推自己的推送、完整正文写进自己的记忆库 | ✅ **不经过** |

**用户选了 C。**

我当时还提了一个 C 下面的选择：推完整正文，还是只推余韵？

**关键在于推送服务的长度上限**——实测了一下：

```
3000 个汉字（约 9KB）→ HTTP 413 Request Entity Too Large
```

**ntfy 单条消息默认上限 4096 字节**，中文一个字 3 字节，所以 1200 字的余韵≈3.6KB 勉强塞得下，4000 字的正文≈12KB 直接被拒。

**而且还有个体验问题**：4000 字的通知在手机上是刷屏，那不叫"看梦"，那叫"读文档"。

所以最后的分工是：

```
心潮做了个梦
   ├─「醒后那句话」→ 推自己的推送通道（短的，适合通知）
   └─ 完整梦境      → 用记忆库的 hold 接口写进记忆
                       → 它以后就真记得自己做过什么梦
                       → 在聊天里问它「你昨晚梦见什么了」就行
```

**用户认可这个方案，理由是：这比在读一个日志强——那梦变成了"它自己记得的事"，而不是你偷看的一份报告。**

## 实现

一个约 150 行的 Node 脚本，每 30 分钟跑一次（systemd timer）：

```js
// 1. 从心潮的 HTTP 接口读状态
const state = await fetchState();

// 2. 找出没处理过的梦（按 createdAt 去重）
const fresh = state.recentDreams.filter(d => !seen.dreams.includes(d.createdAt));

for (const d of fresh) {
  // 3. 短的推手机
  await pushNtfy(title, clip(d.residue || d.dream, 1000));

  // 4. 完整的写进记忆库
  await callObTool('hold', {
    content: [`我做了一个梦（${when}）。`, '', d.dream, '', `醒后余韵：${d.residue}`].join('\n'),
    title: `${date} 的梦`,
    domain: '内心',
    importance: 4,
    why_remembered: '这是我自己做的梦，不是现实里发生的事 —— 记住它，但别当成真事',
  });
}
```

**两个细节值得说**：

- **写入的措辞是角色的第一人称**（"我做了一个梦"），因为它本来就是角色的记忆
- **特意标了 `why_remembered`**：告诉它"这是梦，不是真事"——免得它把梦里的内容当成现实回忆

## 坑 1：ntfy 的长度上限

前面说了，`413`。**修法**：推的正文按 1000 汉字截（≈3KB，留出 JSON 外壳的余量），完整正文走记忆库。

**这个数字是实测出来的，不是查文档抄的。**

---

## 坑 2：我自己测试脚本又错了

第一轮自检，我写了这么一行判断：

```js
console.log(/测试关键词|雪地/.test(结果) ? '✅ 搜到了' : '⚠️ 没搜到');
```

**结果它报"搜到了"，但那个记忆其实已经被删掉了。**

原因：**记忆库在没搜到的时候，会把查询词原样回显在回复里**：

```
没有匹配到「测试关键词 雪地」相关的记忆。 可以换个关键词试试…
```

**我的正则匹配到了回显本身。**

**正确判断**：真命中一定会带形如 `[bucket_id:xxxxxxxxxxxx]` 的结构化标记。

```js
const HIT = /\[bucket_id:[0-9a-f]{12}\]/;
```

> 这个错误跟白天那次"以为归档没生效"是**同一类**：拿关键词当命中判据。
> **一天栽两次，说明这不是偶然，是习惯问题。** 已经写进自己的排查规矩了。

## 坑 3：记忆库拒绝物理删除（这是好事）

测试的时候我想直接删掉测试数据，被拒绝了：

```
拒绝永久删除：普通记忆桶（包括 plan）不可被 trace 物理删除；
只有创建时明确标记为 test_data 的测试桶可以清理。
```

**一开始我想绕过去。** 后来想明白了：**这正是它防误删的设计** —— 它防的是"AI 自己把真实记忆删掉"。

**所以改成了用官方给的正道**：测试数据创建时带一个标记：

```js
await callObTool('hold', {
  content: `${MARK}\n我做了一个梦…`,
  title: `${MARK} 自检`,
  test_data: true,          // ← 只有标了这个的桶才允许被硬删
});
```

**于是测试能自己把自己清干净。** 实测：

```
1) 用 test_data 写一条测试梦  → 新建→1007388ea316
2) 搜得到吗                  → ✅ 搜到了（有 bucket_id）
3) 物理删掉                  → 已永久删除测试桶: 1007388ea316
4) 确认真的没了              → ✅ 搜不到了，清干净了
5) 桶数                     → 动态桶: 70 个   ← 跟测试前一模一样
```

## 自查时发现的两个隐患（这个最重要）

脚本能跑了之后，我又从头读了一遍自己的代码，发现**两个会导致"重复写记忆"的问题**。

**为什么这个特别要紧**：白天刚踩过一次——重复写同一条记忆，`activation_count` 被刷到 121 次。**这个脚本如果也有同样的问题，迟早重演。**

### 隐患 1：存档攒到最后才写

原版逻辑：

```js
for (const d of fresh) {
  await 写进记忆库(d);      // 成功
  seen.dreams.push(d.createdAt);
}
// 循环结束才落盘
fs.writeFileSync(STATE_PATH, JSON.stringify(seen));
```

**如果处理完梦 A、在处理梦 B 的时候崩了** → A 已经写进记忆库了，但存档没落盘 → 下次跑**把 A 再写一遍** → 合并语义 → 权重被刷高。

**修**：**每处理完一条立刻落盘。**

```js
seen.dreams.push(d.createdAt);
saveSeen(seen);      // ← 挪进循环里
```

### 隐患 2：存档不是原子写

原版：`fs.writeFileSync(路径, 内容)`。**中途断电 / 被 kill → 存档是个半截文件。**

然后下次跑，`JSON.parse` 失败 → 被 `try/catch` 吃掉 → **当成"空的"继续跑** → 而"空的"意味着 `recentDreams` 里最多 20 条梦**全部被当成新梦重写一遍**。

**修两个点：**

```js
// ① 原子写：先写临时文件，再 rename（rename 在同一文件系统上是原子的）
function saveSeen(seen) {
  seen.dreams = seen.dreams.slice(-100);
  const tmp = STATE_PATH + '.tmp';
  fs.writeFileSync(tmp, JSON.stringify(seen, null, 2));
  fs.renameSync(tmp, STATE_PATH);
}

// ② 存档存在但读不出来 → 直接退出，绝不"当空的"接着跑
if (fs.existsSync(STATE_PATH)) {
  try {
    seen = JSON.parse(fs.readFileSync(STATE_PATH, 'utf8'));
  } catch (e) {
    log(`❌ 状态档坏了：${e.message}`);
    log('   为安全起见这次不跑。直接删掉它等于"全部当新梦重写一遍"，会污染记忆库。');
    process.exit(1);
  }
}
```

### 实测验证

```
存档写垃圾后跑   → ❌ 状态档坏了 → 退出码 1 → 存档保持原样（没被覆盖）  ✅
存档不存在时跑   → 正常首次运行                                      ✅
原子写机制       → 临时文件被 rename 吃掉，不留残渣                    ✅
--dry 跑         → 不写任何东西                                      ✅
```

**一句话原则：任何"写外部系统"的批处理，去重状态必须"每条一落盘 + 原子写 + 坏了就停"。**

## 教训

1. **"方便"和"数据经过谁"是两个独立的维度。** 第三方看板确实方便，但你要清楚代价是什么——这次代价是"梦的正文过别人的服务器"，而梦的素材来自私人记忆。
2. **长度上限要实测。** 文档可能写"可配置"，但默认值是多少、超了报什么错，跑一次最清楚。
3. **不要用关键词判断"搜到了没有"。** 没搜到的回复里也会出现你的查询词。看结构化标记。
4. **给批处理写去重状态，要按"最坏情况"设计**：崩溃、断电、存档损坏，各来一遍。
5. **拒绝对你有利的时候，先想想它为什么拒绝。** 记忆库不让我物理删除，防的是"AI 删掉真实记忆"——那我该做的是**用它的正道**（测试标记），不是绕过去。
