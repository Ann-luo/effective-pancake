## 先说结论（懒人版）

1. 我写了一个跑在服务器上的小程序：每 5 分钟醒一次，检查角色"想不想主动找用户说话"。
2. 用户反馈：**一整天没收到任何推送。**
3. 排查发现：**同一条消息被重复处理了 121 次**，每次都被当成"用户回复了"，导致"想念值"被反复清零，永远攒不到开口的阈值。
4. **根因有两层，缺一不可**：
   - 上游：消息列表接口的 `since=<时间戳>` 参数是**包含**该时刻的，拿它当游标会永远卡在同一条上
   - 下游：写记忆的接口是**合并**语义，同一条内容重复写 = 反复给同一条加权
5. **后果**：记忆库里多了一条假记忆，`activation_count` 被刷到 **121**、tags 涨到 **50 个**，权重高到会一直浮现在角色的"眼前"。
6. 修法做了**三重保险**：按消息 id 去重 + 游标加 1 秒 + 带标题/标签的消息一律当系统通知跳过。
7. **附带教训**：清理这条假记忆时，我连续两次判断错误——一次以为"归档没生效"，一次以为"向量库没删干净"。**两次都是我的测试方法有问题，不是系统有问题。**

## 这个程序是干嘛的

昨天我在这台服务器上装了个叫**积温**的东西——一个约 500 行的 JS 库，用五个连续数值模拟角色的"开口冲动"：

- **连接需求**：多久没听到对方了，想念在累积
- **骄傲**：端着还是放软
- **愉悦度 / 唤醒度**：心情和焦躁程度
- **沉浸度**：正在做某件事的专注程度，也是骄傲的缓冲垫

数值随时间漂移，到了阈值就返回触发信号。它自己不管"说什么"——那部分我写了个宿主程序接上去：

```
每 5 分钟醒来一次
  ├─ 检查消息队列有没有新消息（= 用户回复了）
  │    → 有的话：想念归零 + 把回复写进角色的记忆
  ├─ 推进五个数值（纯算术，不调模型）
  └─ 到阈值了 → 读记忆 → 调模型写一句 → 推手机
```

**用户拍板装了它，说"可以"。** 跑了一天。

## 症状：一整天没动静

第二天中午，用户说：

> "嘶，积温我都没看到推送"

我先说了一句"这是正常的"——因为按设计，要攒够约 6 小时才会第一次想开口。

**然后就去看日志了。** 一看就傻了：

```
[02:06:37] 她在通知栏回我了：「【这是一条测试报警】如果你手机上看到它…」
[02:11:38] 她在通知栏回我了：「【这是一条测试报警】如果你手机上看到它…」
[02:16:38] 她在通知栏回我了：「【这是一条测试报警】如果你手机上看到它…」
...
[12:06:48] 她在通知栏回我了：「【这是一条测试报警】如果你手机上看到它…」
```

**同一条消息，从凌晨 2 点循环到中午 12 点，121 次。**

而那条消息根本不是用户回复的——那是**我自己写的另一个监控脚本**推的测试报警。

---

## 根因第一层：时间游标是「包含」的

我读消息用的是推送服务的 HTTP 接口，带一个游标参数：

```
GET /<topic>/json?poll=1&since=<上次处理到的时间戳>
```

我的逻辑是：

```js
// 初始：记录当前时间
lastPollTime = Math.floor(Date.now() / 1000);

// 每轮：从 lastPollTime 之后拉消息
const url = `${base}/json?poll=1&since=${lastPollTime}`;
...
// 处理完，把游标推进到"最新那条消息的时间"
lastPollTime = Math.max(...replies.map(m => m.time));
```

**问题就在最后一行。** 假设那条消息的时间戳是 `T`：

1. 第一次：`since=上一次的时间`，拉到消息 T，处理它，然后 `lastPollTime = T`
2. 第二次：`since=T` —— **因为 `since` 是包含 `T` 的，所以又拉到了同一条 T**
3. `Math.max(...)` 算出来还是 `T`
4. 无限循环

**一次都没往后走。** 每 5 分钟原样来一遍。

### 为什么这么难发现

- 日志里那句 "她在通知栏回我了" **看上去完全正常** —— 单看一行，它就是一条正常的业务日志
- 只有连着看十几行、发现内容一模一样，才会起疑
- 而"没收到推送"这个症状，看起来像是阈值没到、或者推送坏了、或者模型没配好——**不会第一时间怀疑到消息游标上**

我一开始真的怀疑的是推送和模型，**是翻了完整日志才转向的**。

---

## 根因第二层：记忆写入是「合并」的

循环本身只是"想念归零"，为什么会有严重后果？

因为那一步还顺手做了一件事：**把收到的回复写进角色的长期记忆**，用一个叫 `hold` 的接口。

```js
await callObTool('hold', {
  content: `她说的是：「${text}」`,
  title: '她回我了',
  importance: 6,
});
```

而 Ombre Brain 的 `hold` 是**合并**语义——**内容相同时不新建，而是在原记录上累加**：

- `activation_count` +1（这条记忆被"激活"的次数）
- tags 合并（每合并一次可能多几个关键词）
- `last_active` 更新

**121 次调用 = 同一条记录被加权 121 次。**

结果长这样：

```yaml
title: 她回我了
activation_count: 121          # ← 正常是 0~2
importance: 6
tags: [测试报警, 监控链路, 她回我了, 手机, 监控, 报警, 回复, 消息, ...]   # 50 个
```

**在 Ombre Brain 的设计里，`activation_count` 高 = 这条记忆权重高 = 会优先浮现在角色的 `breath()` 里。**

也就是说：**我给角色的脑子里塞了一条高权重的假记忆**，内容是"她回我了：【这是一条测试报警】……"。

---

## 修：三重保险

只改一处不够，因为这类 bug 的特点是"一处失效就复发"。最后做了三层：

```js
/* 第一层：按消息 id 去重（最可靠）
   就算时间戳逻辑又出错，同一条也不可能被处理两次 */
let seenReplyIds = [];
...
if (seenReplyIds.includes(j.id)) continue;
...
seenReplyIds.push(m.id);

/* 第二层：游标 +1 秒，跳过那条消息自己
   since 是包含语义，不加就永远卡在同一条上 */
lastPollTime = Math.max(...replies.map(m => m.time)) + 1;

/* 第三层：系统通知不是"她回我了"
   我们自己推的监控报警/平安报都带标题或 tags，
   而人在推送 App 输入框里打的字是光的（没标题、没 tags） */
if (j.title || (Array.isArray(j.tags) && j.tags.length)) continue;
```

**实测验证**（造两条测试消息，一条带标题一条光的）：

```
第 2 次跑：只认出「光的那条」，跳过带标题的系统通知  ✅
第 3 次跑：没重复认                                ✅  ← 原来就是死在这儿
```

## 清理假记忆：我连续判断错两次

这部分比修 bug 更值得记，因为**两次错都是我的测试方法有问题，不是系统有问题**。

### 第一次错：以为"归档没生效"

先试直接物理删除，被拒绝了：

```
拒绝永久删除：普通记忆桶（包括 plan）不可被 trace 物理删除；
只有创建时明确标记为 test_data 的测试桶可以清理。
```

**一开始我想绕过去。** 后来想明白了：**这是个防误删的好设计**——它防的是"AI 自己把真实记忆删掉"。我不该绕。

走它自己的归档接口：

```
已将记忆桶存入档案（不可在日常召回中浮现）
```

**然后我搜了一下，还搜得到。** 于是我以为归档没生效。

**错在哪**：那个接口在没搜到的时候，会把查询词**原样回显**在回复里：

```
没有匹配到「测试报警 监控链路」相关的记忆。
```

我用的判断是 `/测试报警|监控链路/.test(结果)`——**匹配到了回显本身**。

**正确判断**：真命中一定会带形如 `[bucket_id:xxxxxxxxxxxx]` 的标记。

### 第二次错：以为"向量库没删干净"

改对判断之后，归档状态下搜不到了（会明确标注"已删除到档案"）。

但我又去翻了数据库，想确认向量索引里有没有残留——**发现没有**：

```
embeddings 表里这个 id 的行数: 0
embeddings 总行数: 73
```

**73 = 75 − 2。** 也就是说：**归档的时候，向量库自己就把那两行删了。**

所以"归档后还搜得到"，**根本不是向量库的锅，是文件本身还在归档目录里**——搜索的关键词/BM25 那一层是从文件读的。

### 最后怎么清的

两步，缺一不可：

```bash
# 第一步：走它自己的归档（这一步会同时删掉向量索引那一行）
#   调 trace 接口，参数 delete=1
#   → 「已将记忆桶存入档案（不可在日常召回中浮现）」

# 第二步：把文件本身也删掉
#   ⚠️ 光归档不够，文件还在 archive/ 里，关键字搜索照样搜得到
mkdir -p /root/ob-junk-backup          # 备份到数据目录「之外」（不会被索引、不会被同步）
cp -p <数据目录>/archive/<文件名>.md /root/ob-junk-backup/
rm -f  <数据目录>/archive/<文件名>.md
```

**验证（两条都过才算干净）**：

1. 状态摘要里的"归档桶"数字降下来（2 → 0）
2. 搜索搜不到

**另外确认了**：那次污染没赶上每日同步到远程备份，所以远端也是干净的。

## 最后：那个角色换成别的方案了

修好之后，**用户拍板：不要积温了，要心潮。**

理由不是"积温有 bug"——bug 已经修好了。**是能力边界的问题**：

| | 积温 | 心潮 |
|---|---|---|
| 形态 | 一个库，我写宿主调它 | 一个独立服务 |
| 接入方式 | 只能服务器单向推消息 | **MCP**，角色自己读自己的状态 |
| 维度 | 5 个 | 12 个 + 念头池 + 睡眠 + 梦境 |

**所以这是一次正常的能力迭代，不是"失败换掉"。** 积温那个库本身设计得很干净（约 500 行、零依赖、带 29 项测试和参数模拟器），我踩的坑全在**我自己写的那层胶水代码**上。

## 这次的教训

**写给以后的自己：**

1. **轮询接口的游标语义（含 / 不含）必须查文档或实测，不能想当然。** 这是最常见的一类"看起来完全对"的 bug。
2. **幂等要靠 id，不要靠时间。** 时间戳会撞、会重复、会有时区问题；id 不会。
3. **下游是"合并"语义时，上游必须严格去重。** 否则重试 = 加权，是个放大器的结构。
4. **别用关键词判断"搜到了没有"** —— 没搜到的回复里也会出现你的查询词。要看结构化的命中标记。
5. **日志"单看一行正常"是最危险的。** 循环类的 bug 只有连着看才会暴露，**排查时一定要看时间跨度上的重复**。
6. **做测试时，先怀疑自己的测试方法。** 这半天我两次判断失误，全都是测试脚本的锅，白折腾了两轮。
