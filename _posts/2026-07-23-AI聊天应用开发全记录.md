## 前言

一个单文件 HTML 仿微信 AI 聊天应用，双击打开即用。**没有服务器，没有数据库，没有框架。**

功能清单：多智能体 + 多房间聊天（流式 SSE）、朋友圈（AI 自动发帖互动）、AI 日记、待办清单、共享歌单（自动识别平台）、红包 + 礼物商店 + 钱包系统、锁屏密码、深色模式、消息搜索翻页、收藏 + 引用、快捷指令、年度报告、话题标签、全模块导入导出、IndexedDB 存储、HBuilder 打包 APK。

这篇文章记录了从 4600 行到 9500 行的完整开发过程，包括架构设计、踩坑记录、自检修复。不写代码，只说思路。

## 一、怎么开始的

最初的想法特别简单：做一个能跟我聊天的 AI 角色，界面要像微信那样亲切。

核心需求就三个：

1. 能跟 AI 角色自然聊天
2. 能记住聊过的重要事情
3. 界面好看，像真的微信

技术选型几乎没纠结：

- **单文件 HTML** — 不用装任何东西，打开就能跑
- **原生 JavaScript** — 不引入框架，一个文件搞定
- **DeepSeek API** — 国产大模型，便宜好用
- **localStorage** — 浏览器自带的小型数据库

为什么选 DeepSeek？因为它性价比高，API 兼容 OpenAI 格式，迁移成本低。而且提供了四个不同能力的模型，可以根据场景切换：

- `deepseek-v4-flash`：速度快，日常聊天首选
- `deepseek-v4-pro`：推理能力强，复杂任务用
- 还有两个旧版模型作为备选

## 二、文件结构：只有一个 HTML

整个项目就是一个 HTML 文件，大约 4600 行代码，170KB。

虽然没有分文件，但代码内部用了清晰的分区注释，相当于把 CSS 和 JS 都"折叠"在同一个文件里：

```
布雷斯.html
├── SECTION 1: CSS 样式（约 1400 行）
└── SECTION 2: JavaScript 逻辑（约 3200 行）
      ├── 模块 A: 数据层（存储、加载、全局变量）
      ├── 模块 B: 聊天核心（消息渲染、AI 调用）
      ├── 模块 C: 朋友圈（发布、互动、自动管理）
      ├── 模块 D: 功能组件（头像、红包、搜索、语音、快捷回复...）
      ├── 模块 E: 个人主页（签到、成就、心情日历）
      └── 模块 F: 设置 & 初始化（所有开关、数据导入导出）
```

**这样做的好处：**

- 一个文件，发给别人就能用，不需要解释怎么部署
- 代码内部分区清晰，查找修改方便
- 省去了模块加载、打包构建的复杂度

**代价是：**

- 文件比较大，阅读需要耐心
- 没有代码提示和类型检查
- 多人协作会比较痛苦（但这个项目也不需要）

## 三、页面架构：仿微信三页导航

整个应用是一个手机框（430px 宽，圆角），里面有：

```
┌─────────────────┐
│   Status Bar    │  电池、WiFi、时间
├─────────────────┤
│                 │
│   Page Area     │  三个页面切换
│                 │
├─────────────────┤
│  💬  📷  👤   │  底部导航栏
└─────────────────┘
```

**三个页面：**

| 页面 | 功能 |
|------|------|
| 💬 聊天 | 消息列表、输入框、表情面板 |
| 📷 朋友圈 | 帖子流、点赞、评论、发帖 |
| 👤 个人主页 | 资料、签到、钱包、成就、日历 |

页面切换有左右滑动动画，跟原生 App 体验接近。

> 💡 **架构要点：** 所有页面都在 DOM 里，切换就是控制 CSS 的 `display` 和 `animation` —— 不需要路由库，不需要 SPA 框架。

## 四、数据持久化：用浏览器"自带数据库"

数据全部存在浏览器的 `localStorage` 里。它像个超简单的 key-value 数据库：

```js
localStorage.setItem('key', value)  // 存
localStorage.getItem('key')         // 取
```

我把它拆成了十几个独立的 key，每个 key 管一种数据：

| 存储 Key | 存什么 |
|----------|--------|
| `bles_chat_data` | 聊天消息、心情、好感、API Key |
| `bles_memory` | AI 记忆库 |
| `bles_moments` | 朋友圈帖子 |
| `bles_moments_config` | 朋友圈自动发布设置 |
| `bles_balance` | 虚拟钱包余额 |
| `bles_user_profile` | 用户资料（昵称、头像、签名） |
| `bles_checkin` | 签到记录 |
| `bles_achievements` | 成就解锁记录 |
| `bles_scheduled_msgs` | 定时消息列表 |
| `bles_mood_log` | 心情日历数据 |
| `bles_quick_replies` | 快捷回复配置 |
| `bles_msg_reactions` | 消息表情反应 |

**为什么拆开而不是全存一个 key？**

- **读写更快：** 只更新变化的部分
- **降低丢失风险：** 一个 key 损坏不影响其他数据
- **方便调试：** 浏览器 DevTools 可以直接查看每个 key

**localStorage 的限制：**

- 每个域名总共约 5-10MB（文字聊天记录几乎碰不到上限）
- 只能存字符串（图片需要转 base64）
- 不同浏览器不共享（换浏览器数据就没了）

## 五、核心模块逐个说

### 5.1 AI 聊天

这是最核心的功能。流程很简单：

```
用户输入 → 构建 Prompt → 调用 DeepSeek API → 显示回复
```

但 **"构建 Prompt"** 这一步是精髓。

每次调用 AI 前，会拼出一个完整的 System Prompt，包含：

- AI 角色的基础人设（性格、背景、语气要求）
- 从记忆库提取的用户信息（名字、爱好、习惯等）
- 当前心情值和好感等级
- 最近的朋友圈动态
- 用户自定义的额外设定

**这个 Prompt 设计有几个经验：**

1. **人设描述要具体**，不能只说"你是一个温柔的人"——要写具体的行为。比如："你叫她宝贝或小姑娘，回复简短自然，两句话以内，像真实的微信聊天"

2. **负面约束比正面约束更有效**——"绝对不要用小姐姐小可爱这类称呼"比"用亲密的称呼"更不容易出错

3. **给 AI 上下文要适量**——太多会稀释重点，太少会信息不足。最近的 ~20 条消息加记忆摘要，效果最好

还有一个性能优化：Prompt 字符串很长（3000+ 字），每次 API 调用都重新拼接很浪费。所以加了**缓存机制**——只有当记忆库内容真正变化时才重建 Prompt，否则复用缓存。

### 5.2 记忆系统

这是让 AI 更"懂你"的关键。

**实现方式：**

1. 每聊 8 轮，自动触发记忆提取
2. 把最近 20 条对话发给 AI，让它"找找有什么值得记住的"
3. AI 返回 JSON 数组：`[{"key": "不爱吃的", "value": "葱"}]`
4. 存到记忆库，下次聊天自动写入 Prompt

**记忆库支持：**

- ✅ 自动提取（AI 找）
- ✅ 手动删除（用户管理）
- ✅ 自动清理（超过 7 天没更新的记忆，可开关）
- ✅ 向后兼容的升级迁移（旧格式自动转新格式）

**这里面有一个坑：记忆缓存的版本判断。**

一开始我用"记忆条数"作为缓存版本号——条数没变就不重建 Prompt。但这有个 bug：如果记忆的**值**变了但条数没变（比如把"8月开学"改成"9月开学"），缓存不会刷新。

**修复方式：** 改用 `JSON.stringify(memoryStore)` 的完整内容做哈希——任何改动都会触发 Prompt 重建。虽然比数条数慢一点，但记忆库很小（几十条），完全可接受。

### 5.3 朋友圈系统

朋友圈有三个子功能：

**📝 自动发布：AI 定时发朋友圈**

- 取最近聊天上下文，调 AI 生成一句话朋友圈
- 可设置开关和间隔（5-480 分钟）
- 新帖标记红点未读

**💬 自动互动：AI 给用户的帖子点赞/评论**

- 30 秒冷启动期（发帖后等一会再互动，比较自然）
- 每次只做一个动作（点赞或评论一条）
- 优先评论还没互动过的帖子
- 如果用户评论了 AI 的帖子，AI 会回复

**🖼️ 图片支持：**

- 发朋友圈可以附带图片
- 上传时自动压缩（最长边 400px，JPEG 质量 0.5）
- 存 base64 到 localStorage
- 点击图片全屏预览

> 💡 **设计思路——"像真人"：** 不立即互动（有延迟）、不批量互动（每次一条）、不重复互动（已经点赞/评论过的跳过）。

### 5.4 红包系统

一个纯娱乐功能，**虚拟币**，初始 1000 元。

**发红包：**

- 输入金额 + 祝福语 → 红包气泡出现在聊天中
- 红包样式仿微信（红色渐变 + 金色文字）

**拆红包：**

- 点击 → 抖动动画 → 裂开显示金额
- 余额实时增减

**AI 也参与：**

- 心情好的时候会主动给用户发小红包（5-20 元）
- 用户发的红包，30-90 秒内自动领取

**防重复：**

- 拆红包加了锁，动画播放期间点击无效
- 这个 bug 是后来才发现的——连点会重复加钱 💸

### 5.6 心情日历

GitHub 贡献图风格的月历热力图，按**当天实际平均心情值**来着色。

之前的版本用"当日消息条数"来映射颜色——但这并不准确。聊得多不等于心情好，有时候深夜倾诉恰好说明状态低落。

现在的做法：每次发消息时记录当前心情快照 `{totalMood, samples}`，渲染日历时算出 `avgMood = totalMood / samples`，映射到 5 个等级：

| 平均心情 | 颜色 |
|----------|------|
| 0-15 | 红色（低落） |
| 15-35 | 橙色（偏低） |
| 35-55 | 黄绿（中性） |
| 55-75 | 绿色（不错） |
| 75-100 | 墨绿（很好） |

这样看一眼日历，就能知道一段时期内的整体心情走向，而不是"哪天话多"。

数据存储也从简单计数改成了对象：`{ "2026-07-23": { totalMood: 1100, samples: 20 }, ... }`

每 5 条消息才写一次 localStorage（减少 I/O），且有深色模式配色。

## 六、优化历程：自检修 Bug

这个项目前后做了**三轮自检**，修了十几个 bug。挑几个有意思的：

### 🐛 Bug 1：红包消息格式问题

朋友圈自动发布时，上下文里包含了红包消息，但红包消息没有 `text` 字段（它是 `type: 'red_packet'`），导致上下文拼接了 `"undefined"`。

**修：** 加 fallback → `m.text || (m.type === 'red_packet' ? '[红包]' : '')`

### 🐛 Bug 2：Plus 菜单和表情面板互斥

两个面板同时打开会叠在一起。

**修：** 打开一个时关闭另一个。

### 🐛 Bug 3：贴纸标签含引号导致 onclick 截断

贴纸标签里有单引号时，HTML `onclick` 属性中的 JS 字符串会被提前终止。

**修：** 发送前 `replace(/'/g, "\\'")`

### 🐛 Bug 4：图片加载没错误处理

用户选了损坏文件或非图片文件 → 静默失败，无任何反馈。

**修：** 加 `img.onerror` → toast 提示

### 🐛 Bug 5：主动消息的 tag 标记错误

晚间已发过问候后，逻辑 fallthrough 到了 idle 分支，但 tag 变量错误地被标记为 `'night'`。

**修：** 引入显式 `msgTag` 变量追踪每条消息的实际类型

### 🐛 Bug 6：记忆缓存不刷新

改了记忆值但条数没变 → Prompt 还是旧的。

**修：** 版本号改用完整内容的哈希（`JSON.stringify`）

### 🐛 Bug 7：红包连点重复领钱

动画 600ms 期间可以点多次。

**修：** 加 `isOpeningRedPacket` 锁

### 🐛 Bug 8：导入聊天记录后主动消息不触发

`importChat` 不会重置 morning/night 检查计数器。

**修：** 导入后清零缓存

### 🐛 Bug 9：存储超限静默失败

localStorage 写满时无提示。

**修：** 捕获 `QuotaExceededError` 并弹 toast（每分钟最多一次，避免刷屏）

## 七、架构经验总结

### 1. 单文件开发是可行的

4600 行、170KB 的单文件，用分区注释管理，完全够用。不需要 Webpack/Vite/Node 那一套。**对于个人小项目来说，简单就是最大的优势。**

### 2. Prompt 工程是 AI 应用的灵魂

代码逻辑其实很简单——拼字符串、调 API、显示结果。真正决定体验的是 Prompt 怎么写：人设的具体程度、负面约束的使用、上下文的组织方式。

### 3. localStorage 够用但有坑

- 总量有上限（5-10MB），但文字聊天几乎不会碰到
- 存图片要压缩，否则很快就满
- 要防御 `QuotaExceededError`
- 不同浏览器、不同设备不互通（想云同步需要后端）

### 4. 定时器要小心错峰

7 个定时任务如果都在整分钟触发，会出现峰值并发。错开 15 秒间隔后，CPU 压力均匀分布。

### 5. 防御性编程从小处做起

很多 bug 是"边缘情况"：

- 红包消息没有 `text` 字段
- 用户选了损坏的图片
- localStorage 满了
- 连点按钮

这些情况正常使用很少碰到，但碰到了就会出问题。**养成写 fallback、加 error handler、加锁的习惯。**

### 6. 向后兼容很重要

记忆库格式从旧的 `{name, hobby, food}` 字典升级到新的 `[{id, key, value}]` 数组时，做了自动迁移逻辑，老用户的数据不会丢。这个设计习惯在任何一个需要长期维护的项目里都很重要。

## 九、总结

这个项目用到的技术都很"普通"：HTML + CSS + 原生 JS + 第三方 AI API。**没有任何高深的东西。**

但把这些普通的东西拼成一个完整、好看、好用的产品，中间需要大量的细节打磨：UI 动画、错误处理、性能优化、数据迁移、用户体验的微小改进。

**如果你也想做一个类似的 AI 聊天应用：**

1. 别一上来就想后端、数据库、部署——先写一个能用的原型，哪怕所有数据只存在浏览器里。
2. 花时间打磨 Prompt——这比代码优化重要得多。
3. 自己用它、反复用它，自己用的时候会发现无数 bug。
4. 把日常发现的小问题记下来，攒一批统一修，做完一轮做一轮自检。

最重要的是：**做自己想用的东西。** 如果你自己都不想用它，那肯定还有很多没打磨好的地方。

## 十、第四轮优化：性能与准确性的系统打磨

前三轮自检都是在修 bug——东西做出来了但不一定对。这一轮不一样：功能已经有了，但体验不够好，逻辑不够准。

用户提了大约 20 条优化建议，我逐条评估了代码实际状态，最终实施了 7 项改动，回退了 1 项误判。

### 采纳的 7 项优化

**1. 心情日历：从"计数"到"心情值"**

前面 5.6 已经说了。之前按消息数量着色，聊得多不一定心情好。现在改成按当天实际平均心情值着色，红橙黄绿五档，看一眼就知道最近状态怎么样。

数据格式从 `{ "date": count }` 改成 `{ "date": { totalMood, samples } }`，向后兼容——旧数据没有 samples 字段时显示"无数据"。

**2. 统一心跳：一个定时器管所有**

之前代码里至少飘着 4 个 `setInterval`：一个管朋友圈自动发布、一个管互动评论、一个管状态刷新、一个管时钟更新。每个独立跑，互相不知道对方在干嘛。

现在合并成一个 15 秒的"心跳"：每个子系统记录上次运行的时间戳，心跳触发时各自判断"我该不该干活"：

| 子系统 | 频率 |
|--------|------|
| 定时消息、角色状态 | 每 60 秒 |
| 朋友圈自动发布、互动、主动消息 | 每 60 秒 |
| 红包自动收发 | 每 60 秒 |
| 自动清理（旧朋友圈、旧记忆） | 每 5 分钟 |
| 状态栏时钟 | 每 30 秒 |

一个 `clearInterval` 就能停止所有定时任务，也方便将来做暂停/恢复功能。

**3. 朋友圈互动提速 + 多轮回复**

原来节流是 3 分钟跑一次、发帖后等 30 秒才互动。用户发条朋友圈，等到布雷斯点赞评论可能要好几分钟——太慢了，不像真人。

改动：
- 节流降到 30 秒
- 冷启动等待降到 15 秒
- 回复链不再只针对布雷斯自己的帖子，扩展到所有帖子
- 加了上限：每个帖子最多 6 轮你来我往，防止无限对话

现在用户发朋友圈大概 45 秒内就能收到互动，而且可以跟布雷斯连续互怼好几轮。

**4. 消息列表懒加载**

消息超过 250 条时，每次 `renderMessages` 都在重建上千个 DOM 节点，滚动开始卡。加了一个简单的懒加载：超过阈值时只渲染最近 200 条，顶部显示"📜 查看更早的消息"按钮。点击后展开全部。

这个优化把 1000 条消息时的单次渲染量降低了 80%，成本几乎为零——就是多了一个 `slice` 和几行条件判断。

**5. 记忆提取改用消息快照**

原来记忆提取时，直接读全局 `messages` 数组。但 `sendMsg` 是异步的——用户消息发出去、等 AI 回复、收到回复后才触发提取。这中间可能有新的定时消息插入，导致提取的上下文错乱。

修复很简单：在异步调用前拍一个快照 `msgSnapshot = [...messages]`，记忆提取用快照而不是实时数组。一行代码解决潜在的顺序错乱。

**6. 记忆冲突不再静默覆盖**

以前的逻辑：如果 AI 提取到同一条 key（比如"不爱吃的"），新值直接覆盖旧值，用户根本不知道变了。

现在加了冲突标记：如果同 key 值发生了变化，不静默覆盖，而是写入 `_conflictNote` 字段记录"曾记录为 X → 更新为 Y"。虽然目前没有 UI 展示这个标记，但数据层面不再丢信息，将来可以加"记忆变更历史"功能。

**7. 长按滚动不再误触发删除**

长按消息 400ms 触发删除弹窗。但如果用户在滑屏浏览历史消息，手指在消息气泡上按了一下然后滑动，也会触发倒计时。原来的 `touchmove` 只会取消倒计时，但如果弹窗已经弹出来了就不会关。

改成 `touchmove` 触发 `endPress`——既取消倒计时，又关闭已经弹出的删除遮罩。滑屏浏览不会再误触删除了。

### 一次误判：红包概率

代码里有一行：`if (Math.random() > 0.15) return;` ——我第一眼看觉得这是 85% 概率触发，应该是 15% 才对。改成了 `> 0.85`。

后来重新捋了一遍逻辑：`> 0.15` 在 85% 的情况下为 true，触发 `return`（即跳过不发红包），只有 15% 的情况下不 return（即发红包）。所以原代码是对的，我改反了。

**教训：先写注释确认逻辑，再动手改。** 改完之后加了一行清楚的注释，防止下次再误读。

### 改完还不行——再自检一轮

实施完 7 项优化后，又从头到尾审查了一遍代码。发现了 3 个新问题：

**Bug A：冲突记忆记录的是覆盖后的值**

`saveMemory` 里先执行了 `existing.value = val`，然后才拼接 `_conflictNote = '曾记录为：' + existing.value`——这时候 existing.value 已经是新值了，记录变成了"新值 → 新值"，完全没用。

修：在覆盖前先用 `oldValue` 捕获旧值。

**Bug B：懒加载永远不触发**

`renderShowAll` 初始值设成了 `true`，意味着 `!renderShowAll` 永远是 `false`，懒加载代码路径永远不走。无论有多少条消息，都会全量渲染。

修：初始值改成 `false`，启动时自动进入懒加载模式。

**Bug C：死代码残留**

`startStatusUpdater()` 函数已在心跳重构中移除，但全局变量 `statusUpdateTimer` 还留着。删掉，保持代码整洁。

---

这一轮优化的核心经验是：**写完代码后，放一放，换个角度再读一遍。** 第一遍写的时候注意力在"怎么做"，第二遍读的时候才能注意到"之前做了什么假设，现在还是对的吗"。自检不是在找别人的 bug——你找不出自己刚写过的那段代码的问题。但放几个小时再回来看，能发现相当多的惊喜。

## 十一、多智能体切换：不止布雷斯一个人

八的"改进方向"里有一条：多角色切换。没想到这么快就动手做了。

### 不是重构，是包装

面临一个选择：重构整个代码让架构原生支持多角色——还是用最小的代价"包装"现有的单例逻辑？

选了后者。

原因是这个项目已经 4600 行了，功能稳定，重构成本太高。更重要的是：**多智能体的需求本质上就是"同样的功能，不同的数据"，不需要改逻辑，只需要改数据路由。**

实现的思路就一个核心函数：

```js
function agentKey(baseKey) {
  return 'agent_' + activeAgentId + '_' + baseKey;
}
```

所有 localStorage 的读写都通过这个函数包一层。当 `activeAgentId` 是 `'bres'` 时，`agentKey('bles_chat_data')` 返回 `'agent_bres_bles_chat_data'`；切换到 `'cat'` 时，同一个调用返回 `'agent_cat_bles_chat_data'`。

换智能体 = 换一组 localStorage key。代码不用改，数据天然隔离。

### 什么共享，什么独立

需要想清楚一个设计问题：哪些设置是全局的，哪些是按角色分家的？

| 全局共享 | 按智能体独立 |
|----------|--------------|
| API Key | 聊天记录 |
| 模型选择 | 记忆库 |
| 深色模式 | 心情值 + 好感等级 |
| 聊天背景 | 朋友圈帖子 |
| 用户资料 | 成就解锁 |
| | 快捷回复 |
| | 定时消息 |
| | 签到记录 |
| | 心情日历 |
| | 红包余额 |

逻辑很简单：**跟"和谁聊天"有关的东西按角色隔离，跟"用什么环境聊天"有关的东西全局共享。** API Key 不可能换一个角色就要重新输一遍，但你跟布雷斯的记忆不应该混到新角色身上。

### 切换的时候发生了什么

`switchAgent()` 做的事情：

1. `saveData()` —— 把当前内存里的所有状态写回 localStorage
2. 换 `activeAgentId`
3. `loadData()` —— 从新 key 路径读数据填回内存
4. 重置所有运行时状态：正在收的红包、搜索状态、主动消息计数、Prompt 缓存
5. 重绘整个 UI：消息列表、聊天头部、朋友圈、心情面板、快捷回复、成就摘要、日历
6. 记录当前智能体 ID 到 localStorage（刷新页面后还在这个角色）

全程约 30 行代码。代价是重置 Prompt 缓存——因为人设模板变了，旧的缓存不能复用。但这个代价只在切换时付一次，完全可接受。

### 微信联系人列表风格

原始设计只做了设置面板里的一行选择器。用户说"没看到切换智能体的界面"，要求做成微信好友列表的样子。

于是把聊天头部的名字和头像改成了可点击区域——点进去弹出一个半屏面板，每个智能体一行：头像 emoji + 名字 + 选中标记（当前活跃的打个勾）。样式直接抄微信通讯录的排版。

新建/编辑智能体也是一个半屏表单：名字、头像 emoji、人设模板（大 textarea）。人设模板预填了布雷斯的完整背景故事作为参考，告诉用户"改这里就能定制角色的性格"。

两个入口：
- 聊天页顶部点名字/头像 → 智能体列表
- 设置面板里"🤖 当前智能体"区域 → 同样跳列表

### 数据迁移：老用户的包袱

这是个历史遗留问题。之前所有的 key 都是 `bles_xxx` 前缀，现在变成了 `agent_bres_xxx`。老用户打开新版本，如果没有迁移逻辑，他们会看到一片空白——好像数据全丢了。

迁移逻辑写在初始化流程里：

1. 检查 `bles_agents_list` 是否存在（新格式的标志）
2. 如果不存在但 `bles_chat_data` 存在（有旧数据），自动执行迁移
3. 创建默认布雷斯智能体 → 把 `bles_*` 全部拷贝到 `agent_bres_*` → 保留旧 key 不删

保留旧 key 是故意的不删——万一迁移出 bug，用户的数据还在。这个决策占了一点存储空间，但换来了可以放心迁移的底气。

### 重置 / 导入导出的澄清

用户问了两个好问题：重置清的是谁？导入导出是合并的吗？

- **重置（clearAll）：只清当前智能体。** 弹窗里写了清楚的名字："确定要清空「布雷斯」的聊天记录吗？💡 其他智能体的数据不受影响。"——名字是动态的，切换到的角色就叫什么。
- **导入导出：按智能体分别操作。** 导出的文件名带智能体名字，导入的数据也只进当前活跃的智能体。不会出现"把布雷斯的聊天记录导入到新角色"这种混乱。

### 实际工程量

改了大约 300 行：数据层 ~80 行，系统提示词模板化 ~60 行，UI ~100 行，功能适配 ~40 行，初始化 + 迁移 ~20 行。触及约 25 个函数。

算上 sed 编辑导致的语法错误修复（模板字符串被 sed 改坏、agent 管理函数漏加、HTML 片段没插进去）——实际的调试时间大概是写代码的两倍。主要是教训：**在 5000 行的单文件上做批量替换，还是老老实实手改，不要信 sed。**

## 十二、让 AI 回复更像真人：一个 Prompt 工程的实战

多智能体做完了，但用户说了一句话让我开始重新审视整个 Prompt 设计：

> "布雷斯回复太人机了，怎么活人感重。"

第一次改，我把系统提示词大改了一版——加了大量对话风格描述、语气指南、场景举例。结果用户反馈：

> "还是很人机……咋回事？原本的提示词你别大改，你优化。"

这就很有意思了。改得多不一定对，有时候反而把原来的好东西覆盖掉了。

### 诊断：不是人设的问题，是"怎么跟模型说"的问题

重新通读了 `buildSystemPrompt()` 整个流程，找到了四个根因：

**根因 1：记忆注入像数据报表。** 原来的写法是：

```
关于她的信息：
- 喜欢吃的：火锅
- 爱好：画画
- 认识天数：365天
```

这种 key-value 清单让模型进入一种"数据检索"模式——它把这些当信息点处理，而不是"关于这个人我知道什么"。回复自然会像在调数据库。

**根因 2：心情和好感是数字。** 原来的写法是：

```
心情值：55/100，好感等级：3/10
```

活人不这么理解自己的情绪。没人会在心里想"我现在心情值是 65 分"。数字让模型产生一种游戏化的机械感——好像在处理 RPG 角色面板。

**根因 3：记忆被注入两遍。** `buildSystemPrompt()` 里注入了一次全量记忆 + 心情 + 好感，然后 `callDeepSeek()` 里又读了一遍 `getStoredMemory()` 追加了一条独立的 system 消息。模型收到了两份记忆信息，加重了"重复"和"冗余"的感觉。

**根因 4：回复空间太小。** `temperature: 0.85, max_tokens: 300`，加上人设里原有的"两句话以内"规则——模型被严重压缩。它想自然表达但空间不够，被迫产出短促、模板化的句子。

### 修复：四刀同时下

**第一刀：记忆改成自然语言。**

```
你知道关于她的事：她叫xxx；她爱吃火锅；她喜欢画画；你们认识365天了。
在聊天中随手用到，别像背书一样逐条念。
```

从"信息清单"变成"你脑子里知道的事"，加了一句关键指令"别像背书一样逐条念"——这告诉模型这不是数据，是常识。

**第二刀：心情和好感改成描述。**

```js
// 原来是数字
var moodDesc = moodValue >= 80 ? '你今天心情很好，话可能会多一点' :
               moodValue >= 60 ? '你今天心情不错' :
               moodValue >= 40 ? '你今天心情一般' : '你今天心情不太好';

var affDesc = affectionLevel >= 8 ? '你们感情很深，彼此非常信任' :
              affectionLevel >= 5 ? '你们正在熟悉起来，关系越来越近' :
              '你们还在互相了解的阶段';
```

把"55/100"变成"你今天心情不错"——模型收到的不是数据，而是感受。

**第三刀：删掉重复注入。** `callDeepSeek()` 里的 `getStoredMemory()` 代码直接删了。记忆只在 `buildSystemPrompt()` 里注入一次，干净不重复。

**第四刀：松开缰绳。** `temperature: 0.85 → 0.92`，`max_tokens: 300 → 400`。去掉了人设里固定长度的约束，让模型有空间说想说的话——而不是说完必须停下来的感觉。

### 人设本身没改

这是关键。布雷斯的原始背景故事——1200 字的完整人设：童年经历、性格形成、感情观、错过与重逢、魔法世界的设定——一字没动。

只在末尾加了一段实操指南：

```
【对话风格——像真人发微信，不要像在写小说】
- 口语化短句、语气词自然带（嘛、呀、呢、吧）
- 心情不好时话少、困了就说困、被逗到会笑——情绪有起伏才像活人
- 反问、接话茬、追问细节——不是在回答问题，是在聊天
- 偶尔带点魔法日常（练习魔法的小抱怨、吐槽魔法世界的琐事）
```

这不是人设，这是**"教他怎么说话"**。人设告诉你"你是谁"，说话方式告诉你"怎么当这个人"。两个东西分开之后，人设不用动，只调说话方式就行了。

### 经验

这轮折腾学到的：

1. **AI 回复的"人机感"，根因往往不在人设内容，而在注入方式。** 同样的信息，用自然语言描述 vs. 用结构化数据呈现，效果天差地别。模型对格式高度敏感——你给它数据它当数据处理，你给它感受它当感受表达。

2. **temperature 和 max_tokens 是"对话质感"的隐藏开关。** 0.85 到 0.92 看起来只是小数点后两位，但对模型的自由度影响很大。300 tokens 到 400 tokens 多出来的 100 tokens 刚好是"多说一句人话"的空间。

3. **用户的直觉往往是对的。"还是很人机"**——不是胡扯，是身体感受。模型在温度不够高、空间不够大、输入太机械的时候，确实会产出"看起来正确但感觉不对"的东西。你是人，你的感觉是最终判断标准。

## 十三、SSE 流式输出：打字机效果

"改进方向"里提过流式输出，这次真的做了。

### 从一发一收到逐字吐

之前的模式是：用户发送 → 等 AI 生成完整回复 → 一次性显示。体验上就是突然冒出一大段文字，不像聊天，像收邮件。

DeepSeek API 兼容 OpenAI 的 SSE（Server-Sent Events）格式。把请求里的 `stream: false` 改成 `stream: true`，返回的不再是一个 JSON，而是一条一条的 `data: {"choices":[{"delta":{"content":"你"}}]}` ——每个 delta 只包含一两个字。

前端要做的就是：**读流 → 拼字 → 实时更新 DOM。**

### Fetch + ReadableStream

核心代码很简洁：

```
fetch(url, { body: { stream: true } })
→ resp.body.getReader()
→ while 读 chunk → TextDecoder 解码 → 按 \n 分行
→ 过滤 "data: " 前缀 → JSON.parse → delta.content
→ onChunk(token) → 追加到气泡 textContent
→ 直到 "data: [DONE]" → 返回完整文本
```

两个坑：

**坑 1：UTF-8 多字节字符。** emoji 和中文生僻字可能跨 chunk 边界被截断。用 `TextDecoder` 的 `{ stream: true }` 模式，它会自动把不完整的多字节序列留在 buffer 里，等下一个 chunk 到了再拼起来。

**坑 2：`[DONE]` 的 break 作用域。** 收到 `[DONE]` 时如果只 `break`，只跳出内层 for 循环，不会跳出外层 while。虽然实践中 `[DONE]` 之后服务端就关了流、下个 `reader.read()` 返回 done，但写了显式的 `streamDone` flag 控制 while 条件——不依赖隐式行为。

### 增量渲染

流式期间不能每次 token 都调 `renderMessages()`——它会 `innerHTML = ''` 全量重建，闪烁+性能爆炸。

改法：发送前创建一个空壳 AI 气泡（`text: ''`），`renderMessages()` 只调一次把它渲染到 DOM。之后每个 token 通过 `updateBubbleText(msgId, text)` 直接修改对应 DOM 节点的 `textContent`。

流结束时再写一次 `updateBubbleText` 把最终文本落进去 + `saveData()`。全程不重建 DOM，不闪。

### 停止按钮

发送期间 sendBtn 变成红色 ⏹。点击 → `AbortController.abort()` → fetch 抛 `AbortError` → catch 里返回已收到的半条消息 → 保留落盘。

### 滚动追底

每收到 token 检查 `scrollHeight - scrollTop - clientHeight`。如果用户在看最近 400px 内的消息，自动追底；如果手动翻上去看历史了，不拽回来。

### 一个意料之外的问题：流完闪一下

第一版实现里，流结束后我调了 `renderMessages()` 做最终刷新——结果每次都闪一下。原因就是上面说的 `innerHTML = ''` 清空重建。后来全改成了 `updateBubbleText()` 直接更新，不闪了。

## 十四、多气泡连发：AI 一次性说好几句话

真人在微信上经常连发——"看到你消息了" + "哈哈哈哈" + "你今天咋样"——三条短消息连续蹦出来。AI 每次只回一条，不像。

### ||| 分隔符

最简单的实现：系统提示词里约定一个分隔符 `|||`。AI 如果觉得话自然断成两截了，就在中间插入 `|||`。前端收到完整回复后按分隔符切分，逐条渲染。

Prompt 怎么写：

```
【多段回复】如果话自然分成了两段（比如先吐槽一句再认真回一句），
用「|||」隔开。不要勉强——大部分时候不拆就行。也不要超过三段，太碎招人烦。
```

注意措辞：不鼓励滥用。"不要勉强"、"不要超过三段"——因为如果不加约束，AI 可能把所有逗号都替换成 `|||`。

### 前端切分 + 错开延迟

```js
var parts = fullText.split('|||').map(trim).filter(Boolean).slice(0, 3);
// 第一段覆盖 placeholder
aiMsg.text = parts[0];
updateBubbleText(aiMsgId, aiMsg.text);
// 后续段：400-900ms 随机间隔
for (var i = 1; i < parts.length; i++) {
  setTimeout(function() {
    messages.push(newMsg);
    renderMessages();
  }, delay * i);
}
```

`renderMessages()` 重新渲染全部消息——这是必要的，因为要创建新的 DOM 节点。但这里不闪，因为消息列表里已经有内容了，它不是从空白开始重建。

### 实际效果

AI 大概 20-30% 的回复会拆成 2-3 条。常见模式：
- "哈哈哈 ||| 你也太可爱了吧" → 先笑，再说理由
- "我刚刚在想 ||| 要不你明天来找我？" → 停顿感，像真的在斟酌语言

不会每条都拆——Prompt 里强调了"不要勉强"。

## 十五、沉默/生气不回：AI 的拒绝权利

之前的 AI 永远会回复。无条件。不管心情多差、不管用户说什么。

这不真实。真人有时候就是不想回。

### 两层兜底

**第一层：前端拦截（心情 < 20）。** 发消息后、调 API 之前，根据心情值掷骰子：

| 心情 | 沉默概率 |
|------|----------|
| 0-7 | 70% |
| 8-14 | 45% |
| 15-19 | 20% |
| ≥20 | 0%（正常回复） |

中了就不调 API，显示 1-2 秒的"正在输入…"然后消失——像对方打了字又删了——接着弹一条灰色系统提示。

**第二层：AI 自主沉默（心情 20-40）。** Prompt 里加规则：

```
【沉默的权利】如果你心情很差/很累/不想说话/被气到了，
可以只回「[SILENT]」表示不想聊。回了 [SILENT] 就不要再接任何其他文字。
今天你这个状态：偶尔可以 / 基本没必要。
```

心情越低越鼓励沉默，心情还行就说"基本没必要"——不误导模型。

### 17 条生动的沉默消息

不是干巴巴的"对方不想回复"，而是按心情和亲密度分了 4 个池：

- **心寒（心情 < 5）：** "对方沉默了……空气很安静"、"……"、"对方垂着眼，没有回应"
- **生气但亲密：** "对方背过身去了，哼"、"对方在生闷气…过一会就好了"、"对方翻了个白眼，没说话"
- **冷淡（低亲密度）：** "对方已读不回"、"对方看了屏幕一眼，放下了手机"、"对方假装没看到"
- **轻度：** "对方心不在焉地划着手机"、"对方叹了口气，没接话"

灰色居中文字，淡入动画，4-7 秒后自动消失。不存到聊天记录里——沉默不是消息。

### 停止按钮的盲区

自检发现一个 bug：沉默 tease 期间（那 1-2 秒的"正在输入"），用户点停止按钮无效，因为 `cancelSend()` 只处理了 `AbortController`，没处理沉默的 `setTimeout`。修法是给沉默定时器单独存一个 `silenceTimer`，`cancelSend()` 也清理它。

### 体验

沉默概率调得偏保守——心情 15 以上不会沉默，15 以下也只有 20-70% 概率。目的是偶尔给用户惊喜，不是让用户觉得 AI 坏了。"对方不想理你"配合"对方背过身去了，哼"这些文案，比一个 error toast 有生命力得多。

## 十六、AI 日记系统：布雷斯也会写日记

聊天、朋友圈都有了——布雷斯有没有自己的"内心世界"？能不能让 AI 根据聊天内容和朋友圈动态，自己写日记？

### 设计思路

日记是一个**独立于聊天记录的数据模块**。清空聊天记录不应该删日记——日记是 AI 的私人空间，不是聊天的一部分。

核心设计：
- **存储独立**：每个智能体有自己的日记 key（`bles_diary`），和聊天数据分开存
- **自动生成**：每 20-30 轮对话触发一次，降低频率避免骚扰
- **手动写日记**：日记页右上角有按钮，随时手动触发
- **开关控制**：设置面板有"自动写日记"开关，用户随时关掉
- **自动清理**：可配置保留天数（7-90 天），超过自动删
- **聊天引用**：最近 3 篇日记注入 System Prompt，聊天时 AI 自然提到

### 日记的存储结构

```javascript
diaryEntries = [
  {
    id: 'diary_...',
    timestamp: 1721830000000,
    content: '今天她和我聊了很多关于学校的事...',
    mood: '😊'
  }
];
```

字段不多：时间戳、内容、心情 emoji。不需要标题——日记就是按日期排列的。

### 触发机制：低频自然

频率是关键。太高每几条就写一篇，太多没意义；太低用户觉得这个功能形同虚设。

最终方案：每次 AI 回复后递增计数器，每 20-30 轮检查一次（带随机抖动），且需要至少有 10 条聊天记录。计数器持久化到 localStorage，切智能体时重置。

```javascript
function maybeWriteDiary() {
  diaryCounter++;
  var threshold = 20 + Math.floor(Math.random() * 11); // 20-30 随机
  if (diaryCounter < threshold) return;
  diaryCounter = 0;
  if (messages.length < 10) return;
  doWriteDiary();
}
```

### AI 写日记的 Prompt

这是最容易出错的地方——最初版本出来日记是**用户视角**的。

第一版 Prompt："你现在在写日记。根据聊天内容写一段日记。"角色设定是通用的"日记助手"。结果 AI 写出来的东西："今天布雷斯又在加班......他给我带了热可可。"

问题是 AI 不知道自己是布雷斯。它在写日记，但它以为自己在帮用户写日记。

修法：明确身份。

```
System: 你是布雷斯，正在写你自己的个人日记。用第一人称，自然口语化。
只输出日记内容，不要任何前缀或说明。

User: 你是布雷斯。现在你以自己的口吻写一篇日记。这是你个人的日记，
记录你今天和她的互动和你的内心感受。

要求：
- 用第一人称（"我"），你就是布雷斯
- 像真人写日记一样，口语化、自然、有情感
- 不要写成流水账，挑重点和内心感受写
- 心情用一个 emoji 标注在开头
- 提到她时用"她"或她的名字

最近的聊天内容：
她：今天好累...
布雷斯：怎么了宝贝，打工太辛苦了？
她：站了八个小时腿都要断了
布雷斯：回家泡个脚，别逞强。我煮了魔药茶，加了舒缓剂...
```

输出就对了："😔 今天她打工累坏了，站了八个小时。我跟她说泡脚、喝魔药茶，她说我好啰嗦。但我知道她嘴上嫌弃心里是暖的。这种被需要的感觉真好。"

### 日记 UI

日记页是新的 tab，和朋友圈平级。顶部一个"写日记"按钮，下面是日记卡片列表——最新在前。

每张卡片：日期 + 心情 emoji + 内容。超过 120 字的日记默认折叠，点"展开全文"查看。右上角有删除按钮。

空状态："还没有日记，AI 会在聊天中自动写日记"——如果日记功能被关闭，文案会变成"日记功能已关闭，在设置中开启后 AI 会自动写日记"。

### 设置集成

在设置面板新增了一个"📔 AI 日记"区域，三个控制项：
- "自动写日记"开关（默认开）
- "自动清理"开关 + 保留天数输入框（默认 30 天）
- 保存设置时一起生效

### 清空聊天的影响

`clearAll()` 的确认弹窗更新了一行："📔 日记不受影响，需单独管理"。用户清空聊天记录时，日记原封不动——它存在另一个 localStorage key 里。

### 工程量

约 350 行新增：CSS ~60 行，HTML ~30 行，JS 逻辑 ~260 行（存储 + UI + 生成 + 设置）。比多气泡+沉默那波大，但逻辑简单——主要是 CRUD。

## 十七、朋友圈多轮回复：一次 API 调试

朋友圈自动互动之前只做了一层：用户发朋友圈 → AI 点赞 + 评论。但评论之后呢？用户回复了 AI 的评论，AI 应该追评才对——这才像真实的社交互动。

### 设计好的逻辑

代码里早就有 Priority 2：

```
Priority 1：用户发的帖子，AI 还没评论过 → 评论
Priority 2：任何帖子，用户评论了最后一条，AI 还没回复 → 追评
```

每次心跳 tick（最初 60s，后来改到 30s）只做一个动作：点赞、评论、或追评。

限制：每条帖子最多 6 轮 AI 回复（`MAX_REPLY_CHAIN = 6`），防止无限盖楼。

### 问题：Priority 2 触发了，但回复不出现

日志显示：

```
autoInteractMoments: reply_user_comment on post "啦啦啦..."
autoInteractMoments: empty reply from API for reply_user_comment
```

Priority 2 正确触发了，API 也调了、没报错，但返回来的 content 是空的。

### 排查过程

**第一轮排查——网络错误。** 最初 `autoInteractMoments` 的错误处理是 `.catch(() => {})`——静默吞错。改成打印 toast + console.error 后，网络波动时有错误提示，但网络恢复后依然 `empty reply`。

**第二轮排查——render guard。** `.then()` 里有一行：`if (!document.querySelector('.m-comment-input[style*="flex"]')) { renderMoments(); }`。意思是"如果用户正在输入评论，就别刷新页面"。但这个 guard 导致回复入数据了但屏幕不刷——用户看到"没触发"。实际上 `renderMoments()` 内部已经处理了评论输入框的保留和恢复，这个 guard 完全多余。移除。

**第三轮排查——Prompt 格式。** 加了 raw content 日志后发现：API 返回的 content 不是 null，是一个纯空白字符串。HTTP 200，没有报错，就是内容为空。

问题出在 Prompt 结构。旧代码把所有内容塞进 system message，user message 只有一个光秃秃的 `"请回复"`：

```javascript
// 旧格式
messages: [
  { role: 'system', content: '你叫布雷斯。你在朋友圈发了："啦啦啦"。她评论说："哈哈哈"。请以布雷斯的身份回复她的评论，语气温柔自然，8-25字。只说内容，不要加引号或前缀。' },
  { role: 'user', content: '请回复' },
]
```

DeepSeek 不喜欢这种格式。System message 过载，user message 没信息量，模型直接返回了空白。

### 修复

把 Prompt 拆成真正的 system/user 分工：

```javascript
// 新格式
sysMsg = '你是布雷斯。用温柔自然的语气回复朋友圈评论，8-25字。只回复内容本身，不要加引号或前缀。';
usrMsg = '你发了："啦啦啦"\n她评论："哈哈哈"\n\n请以布雷斯的身份回复她：';

messages: [
  { role: 'system', content: sysMsg },
  { role: 'user', content: usrMsg },
]
```

System 只做角色和格式约束，user 携带具体内容。同时把 `max_tokens` 从 80 提到 200、`temperature` 对齐聊天接口的 0.92。

改动之后立竿见影——第一次 tick 就正常回复了。

### 节奏优化

最初的心跳节奏太慢——60s tick + 30s throttle + 15s 评论延迟，最坏情况 105 秒才有一轮回复。优化后：30s tick + 15s throttle + 10s 延迟，最多 55 秒一轮。对于异步的朋友圈互动来说够快了。

### 教训

1. **永远不要静默吞错。** `.catch(() => {})` 是最危险的代码——功能坏了你永远不知道
2. **Prompt 格式对模型行为影响巨大。** 同样的内容，system/user 拆分方式不同，结果从正常变成空白
3. **render guard 要和渲染函数内部逻辑对齐。** 渲染函数已经处理了输入框状态，外部再加 guard 就是画蛇添足

## 十八、细节打磨：括号、多气泡、心情日历

三个小问题，放在一起说。

### 括号问题

用户反馈"AI 发送太多括号有点出戏，毕竟是微信聊天"。

确实——DeepSeek 默认喜欢用括号做旁白：
> 今天去魔法部加班了（梅林啊累死了），你吃饭了吗（别又给我说没吃）

活人发微信从来不打括号。旁白是小说写法，不是聊天写法。

修法：在人设对话风格里加一行：

```
- 别用括号做旁白或补充说明（比如"（笑）""（扶额）""（bushi"这种），
  活人发微信不打括号。情绪和补充直接融进句子本身
```

一句话解决问题。AI 从"（笑）你好可爱"变成"你好可爱啊哈哈"。

### 多气泡 Prompt 反复调

多气泡功能做了之后发现几乎不触发。回去看 Prompt：

```
【多段回复】如果话自然分成了两段，用「|||」隔开。
不要勉强——大部分时候不拆就行。也不要超过三段，太碎招人烦。
```

三句话里两句在劝退。DeepSeek 听话——"好，不拆"。

第一版修复改成鼓励措辞，触发率有提升但还是偏低。第二版直接给场景：

```
【多段回复——重要！】遇到以下情况直接拆：
① 先吐槽/感叹一句再接正文
② 话题自然转折
③ 话有点长分两段更自然
用「|||」隔开。大约每 4-5 条回复里拆一次就好。
```

"直接拆"比"可以拆"强，具体场景比模糊描述强。触发率明显提升。

另外修了一个流式显示的 bug：流式输出时 `|||` 会原样出现在气泡里，用户看到 "好啦好啦|||你今天怎么起这么早"。修法是在 `onChunk` 回调里检测 `|||` 并截断显示：

```javascript
var displayText = aiMsg.text;
var sepIdx = displayText.indexOf('|||');
if (sepIdx !== -1) displayText = displayText.substring(0, sepIdx);
updateBubbleText(aiMsgId, displayText);
```

后续气泡也不再调 `renderMessages()` 全量重绘——写了 `appendMessageRow()` 函数增量追加 DOM 节点，彻底消除闪屏。

### 心情日历：无数据 ≠ 心情差

心情日历用 0-4 级颜色标注每天的平均心情。但有个设计问题：没有数据的日期显示为 lvl-0（红色），和心情极差（<15 分）是同一种颜色。

一个月 30 天，通常只有几天有聊天记录。结果日历上 25+ 天都是红色——用户看了以为日历坏了。

修法：区分"无数据"和"心情差"。没有聊天记录的日期用灰色（`.no-data` class），只有真正有数据且心情低的日期才用红色。一眼能看出哪些天聊过天、哪天心情好哪天不好。

## 十九、Temperature + Top P：把 AI 性格的旋钮交给用户

之前所有 API 调用都硬编码了 temperature——聊天 0.92，日记 0.8，朋友圈 0.85，主动消息 0.9。每次调参都要改代码，太傻了。

而且用户应该有这个权利：想要稳一点还是浪一点，应该自己决定。

### 两个参数是干嘛的

- **Temperature（0~2）**：控制输出的随机性。越低越保守、越可预测；越高越有创意、也越容易胡说八道。DeepSeek 的默认值是 1.0
- **Top P（0~1）**：核采样。值越小，候选词越集中在高概率的几个；值越大，候选词范围越广。1.0 等于不做限制

简单理解：Temperature 管"多敢说"，Top P 管"词库有多大"。两个配合能调出很不同的风格。

### 实现

设置页加两个 range 滑块，`accent-color: var(--wechat-green)` 跟微信绿统一：

```html
<input type="range" min="0" max="2" step="0.05" value="0.92"
       oninput="document.getElementById('tempValDisplay').textContent=this.value">
```

滑块拖到哪实时显示，保存时跟 modelName 一起塞进 `bles_global_settings`，全局跨智能体共享。

### 哪些 API 调跟，哪些不跟

不是所有 API 调用都应该用用户设置的参数。记忆提取需要低温度（0.3）保证准确性——让 AI 自己决定"要不要记住"这件事本来就不靠谱，必须冷血一点。聊天摘要是工具性质，固定 0.7。

最终方案：

| API 调用 | Temperature |
|----------|:--:|
| 主聊天 (`callDeepSeek`) | 用户设置 |
| AI 日记 | 用户设置 |
| 朋友圈发帖 | 用户设置 |
| 朋友圈评论 | 用户设置 |
| 主动消息 | 用户设置 |
| 记忆提取 | 固定 0.3 |
| 聊天摘要 | 固定 0.7 |

前五个是"角色表达"，后两个是"工具调用"。分清楚这个边界，改动就很干净——所有 7 处 `fetch` 调用点，5 处换变量引用，2 处保留硬编码。

### 一个小坑

变量名 `temperature` 和 API 参数名正好一样，JS 对象里写 `temperature: temperature` 很自然。但要确保全局作用域没有同名局部变量覆盖——`callDeepSeek` 函数体里没有叫 `temperature` 的局部变量，引用自动落到全局。如果哪天有人重构不小心在函数里声明了一个同名局部变量，所有调用点的温度就变成 `undefined` 了。这是一个团队维护注意点。

## 二十、锁屏密码：一个本地应用的隐私实验

纯前端应用做锁屏密码有意义吗？说实话——安全上没意义。localStorage 里的密码谁打开 DevTools 都能读。但这个功能的意义本来就不是防黑客，是防"朋友借手机翻聊天记录"。

### 两种模式

- **数字密码（PIN）**：4-6 位数字，3×4 圆形键盘 + 圆点指示器。抄 iPhone 锁屏的交互
- **问题-答案**：自定义一个问题，答案不区分大小写。比如"我最喜欢的颜色？→ 紫色"

两种模式可以在设置中切换。

### 锁屏界面

全屏浮层（z-index: 200，压在所有 overlay 之上），分两层：
- 底层：壁纸（或默认深蓝色渐变）+ 半透明暗色遮罩
- 上层：时间、日期、解锁入口

初始状态显示一个脉冲动画的 🔓 图标 + "点击解锁"。点任意位置 → 弹出密码输入区（PIN 键盘或问答输入框）。

```css
.ls-tap-hint {
  animation: lsPulse 2s ease-in-out infinite;
}
@keyframes lsPulse {
  0%, 100% { opacity: 0.7; transform: scale(1); }
  50% { opacity: 1; transform: scale(1.04); }
}
```

第一版做的是"上滑解锁"，加了一整套 `touchstart`/`touchmove`/`touchend` 监听。实测发现 desktop 上不工作——没有触摸事件。改成点击，一了百了。

### 自动锁定

三层触发：
1. **无操作计时**：可配置 1/5/15/30 分钟。用户每次点击、打字、滑动都重置倒计时
2. **切后台**：`visibilitychange` 事件——切标签页或最小化窗口 → 立即锁（"从不自动锁定"模式下跳过）
3. **手动**：设置里有个"🔒 立即锁定"按钮

```javascript
document.addEventListener('visibilitychange', function() {
  if (document.hidden && lockConfig.enabled && !lockActive
      && (lockConfig.autoLockMinutes || 5) > 0) {
    lockNow();
  }
});
```

### 密码存储：哈希但不加密

密码不存明文。用一个简单哈希（djb2 变体 + salt）存进 localStorage：

```javascript
function hashPassword(pwd) {
  var hash = 0, salt = 'bles_lock_2024', str = salt + pwd;
  for (var i = 0; i < str.length; i++) {
    hash = ((hash << 5) - hash) + str.charCodeAt(i);
    hash |= 0;
  }
  return 'h_' + Math.abs(hash).toString(36);
}
```

这不是加密——localStorage 里的哈希值任何人打开 DevTools 都能看到，但至少不是一眼就能读出来的明文。配合 PIN 长度信息（用于渲染圆点），前端锁屏的安全天花板就这么高。

### 忘记密码怎么办

这个问题想了很久。最初方案是"重置 = 清空所有数据"，用户反馈这太残暴了——忘记密码就要删聊天记录和日记？

改成了温和版本：输错 5 次后显示"🔓 重置锁屏密码"按钮，点击确认后只清除锁屏配置（关闭锁屏、清空密码），聊天数据、日记、记忆全部保留。

```javascript
function forgotLockPassword() {
  if (!confirm('确定要重置锁屏密码吗？')) return;
  lockConfig.enabled = false; lockConfig.pin = '';
  lockConfig.question = ''; lockConfig.answer = '';
  // ... 解锁、关浮层、saveData()
}
```

### 壁纸

上传图片 → canvas 压缩到 400px 宽 → JPEG quality 0.6 → base64 → localStorage。

为什么不直接存原图？localStorage 每个 key 上限 5MB，一张 iPhone 照片轻松 3MB+。压缩后通常 20-50KB，安全得很。

锁屏壁纸写在单独的 `bles_lock_wallpaper` key 里，和配置分开存——避免 `JSON.stringify` 时把几十 KB 的 base64 裹进配置 JSON，读写都慢。

### 自检发现的两个 bug

写完后自检，发现两个要命的问题：

**死锁**：`toggleLockEnable()` 里开关刚打开就立刻校验密码，但密码输入框才刚显示，用户根本来不及填 → 永远无法首次开启锁屏。修法是把校验从开关事件移到保存事件——开关只负责显示/隐藏 UI，保存时才检查"密码填了没有"。

**z-index 冲突**：锁屏用的 `z-index: 100` 和设置面板同级，某些情况下设置面板可能浮在锁屏上面。改成 200，并让 `lockNow()` 主动关闭所有打开的 overlay（设置面板、Agent 编辑器等）。

## 二十一、三个小优化：日记频率、沉默破防、记忆导出

### 日记频率可控

原来日记频率是固定的 20-30 轮一篇。用户说"能不能调"。加了频率控制，三个档位：

| 频率 | 触发间隔 | 适合场景 |
|------|------|------|
| 低 | 30-40 轮 | 不想被打扰，偶尔看看 AI 的心里话 |
| 中 | 20-30 轮 | 默认，自然节奏 |
| 高 | 10-15 轮 | 密集聊天，想看 AI 频繁记录心情 |

设置里一个 select，存进 `diaryConfig.frequency`。`maybeWriteDiary()` 里把原来的固定阈值换成动态计算：

```javascript
var freq = diaryConfig.frequency || 'medium';
var min, max;
if (freq === 'high') { min = 10; max = 16; }
else if (freq === 'low') { min = 30; max = 41; }
else { min = 20; max = 31; }
var threshold = min + Math.floor(Math.random() * (max - min));
```

### 沉默"破防"：AI 也会心软

沉默系统有个问题：AI 心情不好 → 不回 → 用户连发两条 → AI 还是沉默（因为心情没变）。用户觉得"这 AI 是不是坏了"。

加了一个"破防"机制：

```
用户发消息 → AI 沉默（心情低 + 概率）
     ↓ 用户在 2 分钟内再发一条
     → 跳过沉默检查 → AI 心软，回复了
```

实现就三行：

```javascript
var breakthrough = false;
if (_lastMsgSilenced && (Date.now() - _lastSilenceTime) < 120000) {
  breakthrough = true;
}
// 破防时 silenceThreshold 直接设为 0，100% 回复
var silenceThreshold = breakthrough ? 0 : (moodValue < 8 ? 0.7 : ...);
```

然后在发给 AI 的消息后面悄悄加一段系统提示：

```
[刚才她发消息你没回，现在她又发了一条。你有点过意不去，心软了，
决定还是回复她。用带一点点傲娇或愧疚的语气回应，但不要直接说
"刚才不想理你"之类的话，要自然。]
```

AI 看到这个会自然流露出那种"好吧好吧回你一下"的语气，不会机械地说"抱歉刚才没回你"。戏剧感就出来了。

### 记忆 + 配置的独立导入导出

之前的导入导出只管聊天记录。但用户在不同设备/浏览器之间迁移时，记忆库、日记、成就这些数据没法带走。

加了"📤 导出记忆+配置"和"📥 导入记忆+配置"两个按钮，放在设置页记忆库区域。

导出的 JSON 包含：
- 记忆库（memoryStore）
- 日记 + 日记配置
- 朋友圈配置、主动消息配置
- 快捷回复、签到数据
- 心情日志、成就、消息反应

导入时智能合并——记忆和日记按 id 去重，配置用 Object.assign 叠加，快捷回复做 Set 去重。不会覆盖已有数据。

和聊天导出分开的原因很简单：聊天是聊天，数据是数据。换设备时你可能想带着 AI 的记忆和日记，但不一定想带着所有聊天记录。两个独立的 JSON 文件，各取所需。

## 二十二、拍一拍：一个被 onclick 吃掉的交互

"拍一拍"是微信的经典交互——双击对方头像，头像抖一下，弹一行小字"你拍了拍XXX"。我做了一个翻版：双击布雷斯头像 → 头像抖动 → toast 提示根据心情变化（高心情："布雷斯回头对你温柔一笑 💕"，低心情："布雷斯从沉思中回过神…"）。

功能写好了，双击头像却触发不了——弹出来的是智能体切换列表。

### 排查

头像的 HTML：

```html
<div class="avatar" id="bresAvatar"
     onclick="showAgentList()">
```

JS 里又绑了一个：

```javascript
bresEl.ondblclick = doNudge;
```

同一个元素上 `onclick` 和 `ondblclick` 同时存在。双击时发生了什么？

1. 第一下 click → `onclick` 立刻触发 → `showAgentList()` 弹出智能体列表
2. 第二下 click → `ondblclick` 触发 → `doNudge()` 执行

但此时智能体列表已经占满了屏幕，toast 被遮在背后，头像的抖动动画也看不到了。用户只看到智能体列表弹出来，以为拍一拍根本没做。

本质上：**onclick 抢在 ondblclick 之前执行了**，破坏了双击的体验。

### 修法：单击延迟判定

经典方案——用定时器区分单击和双击。单击后不立刻执行，等 350ms，如果这期间来了第二下 click，说明是双击，取消等待直接拍一拍。

```javascript
var _nudgeClickTimer = null;
function handleAvatarClick() {
  if (_nudgeClickTimer) {
    // 350ms 内来了第二下 → 双击 → 拍一拍
    clearTimeout(_nudgeClickTimer);
    _nudgeClickTimer = null;
    doNudge();
    return;
  }
  // 第一下 → 等着，350ms 后还没第二下就是单击
  _nudgeClickTimer = setTimeout(function() {
    _nudgeClickTimer = null;
    showAgentList();
  }, 350);
}
```

HTML 改成 `onclick="handleAvatarClick()"`，删掉 `ondblclick`。350ms 的延迟对单击来说几乎无感，但双击检测足够了。

### 一个小细节

头像的 title 提示原来是"双击拍一拍"，改成了"单击切换智能体 · 双击拍一拍 布雷斯"——光标悬停时就能看到两个操作，不需要猜。

### 反思

这个问题暴露了一个更普遍的坑：**HTML 属性里写 `onclick` 和 JS 里绑 `ondblclick` 是两套独立的事件注册**，不会互相覆盖。同一个元素上同时存在时，click 永远先到。如果 click handler 有副作用（弹浮层、导航跳转），dblclick 基本等于不存在。

以后遇到"双击触发不了"的问题，先检查有没有 onclick 在抢。

## 二十三、IndexedDB 迁移：告别 localStorage 天花板

写到 6800 行的时候，一个根本性问题浮现了：localStorage 只有 5MB。

单智能体、一个房间、几百条消息——5MB 绰绰有余。但你想想后续要做的功能：一个智能体开几个房间、每个房间有独立记忆 + 日记 + 签到 + 成就……数据量是乘法级增长的。打开 DevTools 一看，localStorage 已经吃了 1.2MB。再不加节制，迟早爆仓。

### localStorage vs IndexedDB

localStorage 是同步 API，一行 `getItem` 搞定。简单，但太简单了——只能存字符串，只能按 key 查，没有索引，没有事务。

IndexedDB 是浏览器自带的"真正的数据库"：

| | localStorage | IndexedDB |
|------|:--:|:--:|
| 容量 | 5-10MB | 几百 MB ~ 几 GB |
| 数据类型 | 只存字符串 | 任意 JS 对象 |
| 查询 | `getItem(key)` | 按索引查、按范围查、排序 |
| API 风格 | 同步 | 异步（Promise） |

对聊天应用来说，IndexedDB 最大的吸引力就一个：**不用再担心"存储空间不足"的 toast 了。**

### 封装层：把异步藏起来

IndexedDB 原生 API 很啰嗦——打开数据库、建 store、开事务、读写——每一步都是回调。我写了一个薄封装：

```javascript
function idbOpen() {
  return new Promise(function(resolve, reject) {
    var req = indexedDB.open('bles_db_v1', 1);
    req.onupgradeneeded = function(e) {
      var db = e.target.result;
      if (!db.objectStoreNames.contains('data')) {
        db.createObjectStore('data', { keyPath: 'key' });
      }
    };
    req.onsuccess = function(e) { resolve(e.target.result); };
    req.onerror = function(e) { reject(e.target.error); };
  });
}

function idbGet(key) {
  return idbOpen().then(function(db) {
    return new Promise(function(resolve) {
      var tx = db.transaction('data', 'readonly');
      var req = tx.objectStore('data').get(key);
      req.onsuccess = function() { resolve(req.result ? req.result.value : undefined); };
    });
  });
}
```

`idbGet` / `idbPut` / `idbDelete`——三个函数覆盖所有操作。`loadData()` 从同步改成 `async`，init 流程用 `await` 等数据就绪。

### 迁移：搬家不丢东西

这是最不能出错的部分。用户打开新版 HTML → 自动检测 localStorage 里有旧数据 → 逐 key 搬运到 IndexedDB → 标记"已迁移" → 正常启动。旧 localStorage 数据**不删**，当保险。

旧 key 名（`bles_global_settings`、`agent_bres_bles_moments`……）和新 key 名（`global_settings`、`agent_bres_moments`……）不同。迁移函数里建了一个映射表，把 25+ 个旧 key 一一搬到新位置，同时把原来分散的记忆、日记、签到、成就等合并到一个 `room_{agentId}_default` 对象里。

### 翻车：第一次迁移只搬了聊天记录

写完后自己测——旧数据打开，聊天记录在，但朋友圈全空、日记全空、设置回到默认。排查发现迁移函数把旧 key 原样复制到 IDB，但 `loadData` 用的是新 key 名去找——全找不着。只有聊天记录因为 `loadData` 里有一个 fallback 分支捡了回来。

修法：重写 `idbMigrateFromLocalStorage()`，每个旧 key → 新 key 显式映射，per-agent 的数据读到内存里重组成 room 格式再写。加了一个自动修复逻辑——检测到 `_migrated` 标记存在但关键 key 缺失 → 删标记 → 重新迁移。用户什么都不用做，刷新页面就自动修好。

### 异步带来的改动面

`loadData()` 从同步变异步，调用它的地方都要改：
- `switchAgent()` → `.then()` 回调
- `switchRoom()` → `.then()` 回调
- 初始化的 `loadData()` → 包在 `(async function() { await loadData(); ... })()` 里

这是整个项目最大的一次"地基改造"。改完之后 `saveData()` 也不用再担心 QuotaExceededError 了——IndexedDB 的容量在聊天应用这个量级上几乎是无限的。

## 二十四、平行宇宙：同一个 AI，不同的房间

有了 IndexedDB 打底，房间（平行宇宙）就水到渠成了。

### 需求

同一个布雷斯，在"日常"房间里跟你嘻嘻哈哈，在"心事"房间里跟你认真聊人生。两个房间的记忆、情绪、好感度完全独立——"日常"房间里的布雷斯不记得"心事"房间里的对话。

### 数据模型

```
room_bres_default/   → { messages, mood, affection, memory, diary, ... }
room_bres_心事/      → { messages, mood, affection, memory, diary, ... }
room_bres_游戏/      → { messages, mood, affection, memory, diary, ... }
```

每个房间是一个独立的 JSON 对象存在 IndexedDB 里。`roomKey()` 函数根据当前智能体 ID 和房间 ID 拼接 key。

**房间内独立的数据：** 聊天记录、心情值、好感度、记忆库、日记、签到、成就、心情日志、快捷回复、定时消息、消息反应

**跨房间共享的：** 人设模板、头像、API Key、模型参数、朋友圈（同一个人的朋友圈没必要每个房间发一遍）

### 房间 UI

聊天页头部加了一个 📂 按钮，点击弹出房间列表：

```
● 日常          ✏️ 🗑️
○ 心事          ✏️ 🗑️
○ 游戏          ✏️ 🗑️
─────────────────────
[新房间名________] [+ 创建]
```

默认房间"日常"不可删除，保证始终至少有一个房间。切房间的体验跟切频道一样：保存当前房间 → 加载新房间 → 全量刷新消息列表、记忆、心情条、日记。

### 切房间的实现

```javascript
function switchRoom(roomId) {
  if (roomId === activeRoomId) return;
  saveRoomData(); // 保存当前房间状态
  activeRoomId = roomId;
  // 重置所有 volatile 状态
  messages = []; moodValue = 55; affectionLevel = 1;
  memoryStore = []; diaryEntries = []; diaryCounter = 0;
  // ... 全部变量清空
  loadData().then(function() {
    updateChatHeader();
    renderMessages();
    renderMoments();
    renderMoodCalendar();
    // ...
    showToast('已切换到「' + getRoomName() + '」📂');
  });
}
```

`saveRoomData()` 把当前房间的所有状态打包写入 IDB，然后 `loadData()` 从新房间的 key 读数据。切换是完全的——不会串味。

### 导入导出也跟着房间走

聊天的导入导出、记忆+配置的导入导出都加了 `roomId` 和 `roomName` 字段。导出文件名会标房间名：`布雷斯-心事-聊天备份-2026-07-24.json`。导入时把数据灌进当前房间，不会影响其他房间。

## 二十五、时间线：按月回放聊天记录

有了 IndexedDB 的容量保证，不用再删旧消息了。聊天记录可以一直存着——那就值得做一个回看功能。

### 需求

一个日历视图，有聊天记录的日期标绿点。点日期 → 显示那天所有消息。再加一个回放模式，消息按时间顺序逐条弹出，像看电影一样重温那天的对话。

### 日历 UI

用 CSS Grid 画 7 列日历。当月日期显示在格子里，有聊天记录的加绿点（`::after`伪元素），今天加粗，选中的变绿底白字。

```javascript
function renderTimelineCalendar() {
  var chatDates = new Set();
  for (var i = 0; i < messages.length; i++) {
    var d = new Date(messages[i].time);
    chatDates.add(d.getFullYear() + '-' + ...);
  }
  // 画 7 列 × 5-6 行的日历 grid
  for (var d = 1; d <= daysInMonth; d++) {
    var hasChat = chatDates.has(dateStr) ? ' has-chat' : '';
    html += '<div class="tc-day' + hasChat + '" onclick="showTimelineDate(...)">' + d + '</div>';
  }
}
```

点日期 → 过滤出当天的消息，渲染在日历下方。消息行复用聊天气泡样式——左边灰色 AI 气泡，右边绿色用户气泡。

### 回放模式

点"▶️ 回放" → 消息区清空 → 逐条弹出。用 `setTimeout` 链式调度：

```javascript
function timelineReplayTick() {
  if (_timelineReplayIdx >= _timelineMsgs.length) {
    stopTimelineReplay(); return;
  }
  // 追加一条消息到 DOM
  var m = _timelineMsgs[_timelineReplayIdx];
  container.appendChild(renderMsgRow(m));
  _timelineReplayIdx++;
  // 调度下一条：基础间隔 1200ms ÷ 速度倍数
  var delay = Math.max(200, Math.floor(1200 / _timelineReplaySpeed));
  _timelineReplayTimer = setTimeout(timelineReplayTick, delay);
}
```

速度可调：1×（正常节奏）、3×（快速回顾）、10×（飞速翻）。本质上就是把消息的时间间隔压缩到 200ms-1200ms 之间。

### 一个细节

切房间或切智能体时，如果当前在时间线页面，日历会自动刷新为新房间的数据。这个在 `switchRoom` 和 `switchAgent` 的 post-load 回调里各加了一行 `renderTimelineCalendar()`。

时间线是一个"感性的功能"——它不是工具，更像一个回忆盒子。三个月后点开日历，看到某一天你跟 AI 聊了 47 条消息，点进去从头看到尾，像翻旧相册。

## 二十六、最难的 bug：六个连锁故障的排查记

IndexedDB + 平行宇宙 + 时间线这三个大功能做完后，出现了一堆诡异的 bug：房间切换失败、日历永远显示一月、回放按钮失灵、手机端完全不能用。而且桌面端和手机端表现还不一样。

这是整个项目最难的一次调试——不是修一个 bug，是六个 bug 互相遮掩。

### Bug 1：房间切换失败（致命）

现象：创建一个新房间，切换过去，toast 却显示"已切换到「日常」"。消息也没变。

排查：打了三个 Agent 并行追踪代码路径，发现一个竞态——

`switchRoom` 把 `activeRoomId` 设成新房间 ID，然后调 `loadData()` 加载数据。但 `loadData` 里有一行：

```javascript
var ar = await idbGet('active_room_' + activeAgentId);
if (ar) activeRoomId = ar;  // ← 从 IDB 读到旧值，覆盖了新值！
```

`switchRoom` 只把新 ID 写进了**内存**，没写进 IDB。`loadData` 从 IDB 读到**旧房间 ID** → 覆盖内存 → 等于没切。修法：`loadData` 只在初始加载时从 IDB 恢复 `activeRoomId`，切房间时跳过。

### Bug 2：日历永远显示一月（致命）

现象：回忆页的日历不管什么时候打开，永远显示一月。明明有聊天记录的日期能看到绿点，但日历月份不对。

排查：

```javascript
if (year === undefined) { year = _timelineYear || now.getFullYear(); _timelineYear = year; }
if (month === undefined) { month = _timelineMonth; if (!_timelineYear) month = now.getMonth(); _timelineMonth = month; }
```

第一行把 `_timelineYear` 从 0 设成了 2026（truthy）。第二行 `!_timelineYear` → false → month 永远保持初始值 0（一月）。**第一行的赋值破坏了第二行的空值检测。**

修法：在年份赋值前先保存 `var wasBlank = !_timelineYear`，用 `wasBlank` 判断月份。

### Bug 3：回放按钮失灵

现象：日历显示了消息，点"▶️ 回放"却说"这天没有聊天记录"。

`toggleTimelineReplay` 检查 `_timelineMsgs.length`，但 `_timelineMsgs` 可能在渲染后被某个路径清空了。修法：回放前不信任缓存，每次从 `messages` 重新过滤。

### Bug 4：月份标签显示 `0月`、`13月`

导航箭头用 `_timelineMonth-1` 和 `_timelineMonth+1`，越界值直接拼进标签字符串。修法：`new Date(year, month, 1)` 标准化后再取月份。

### Bug 5：手机端房间列表点不了

桌面端正常，手机端点了没反应。原因是房间列表项没有 `event.stopPropagation()`——移动端的 touch 事件冒泡到父级 overlay 的 `onclick="hideRoomList()"`，列表先关了，`switchRoom` 没机会执行。修法：加 `event.stopPropagation()` + `touch-action: manipulation`。

### Bug 6：余额 0 被改成 1000

迁移时 `parseFloat(balance) || 1000`——JavaScript 的 `0` 是 falsy。修法：`!isNaN(bv)` 显式检查。

### 六个 bug 的共同特征

全是**状态管理**问题——内存和 IDB 不同步、变量初始化顺序依赖、缓存信任过度。核心教训：

1. **异步持久化不能 fire-and-forget 之后又立刻读回来**——竞态窗口比你想象的大
2. **`if (!x)` 在 JavaScript 里是地雷**——`0`、`''`、`false` 都是 falsy。该用 `=== undefined` 的时候别偷懒
3. **同一个函数服务于多个调用场景时，要注意副作用**——`loadData` 同时服务初始化、切房间、切智能体，各自的前提条件不同

修完这六个 bug 之后，桌面端和手机端行为完全一致了。用户说"成功了！！！！我爱你！！！"——那一瞬间觉得所有调试都值了。

## 二十七、共享待办：从"聊天"到"一起做事"

做完平行宇宙和时间线之后，我问了自己一个问题：这个应用除了聊天还能干嘛？

答案是可以加一个"工具"维度——让 AI 不只是跟你说话，而是帮你管理生活里的小事。待办清单就是最自然的切入点。

### 需求

一个简单的待办清单，但要和 AI 聊天打通：

- 手动添加、勾选完成、删除
- 按房间隔离——每个平行宇宙有自己的待办
- AI 在聊天时能看到你的待办列表，自然地催你、提醒你
- AI 可以帮你加待办……等等，这个要想想

### 设计上的纠结：AI 该不该帮你加待办？

最初的设计是 AI 可以通过 `[TODO]买牛奶[/TODO]` 标记自动添加待办，回复里嵌入标记 → 系统自动解析 → 静默加入列表。

做完之后想了一下——不太好。原因是：

1. **AI 可能过度解读。** 你随口说"好想喝奶茶"，AI 就给加了一条"喝奶茶"。但你根本没想把它写成待办。
2. **边界模糊。** 聊天是轻松的，待办是认真的。把两者混在一起，聊天变得有压力——每句话都可能被 AI "记下来"。
3. **手动更有掌控感。** 待办的心理学研究表明，自己写下来的任务更有动力完成。

所以改了一版：**AI 能看到待办，但不能修改。** 系统提示里注入待办上下文，AI 可以催你（"昨天说要买牛奶，还没买吧？👀"），但不能自己加。这更像一个有记忆的伙伴，而不是一个越权的管家。

这个改动很小——删掉系统提示里两行标记指令，移除回复处理器里的标记解析代码，前后不到十分钟。但设计上的意义比代码大多了：**AI 辅助但不替代，知道但不越界。**

### 数据模型

待办嵌在 room data 里，跟聊天消息同级存储：

```
room_{agentId}_{roomId} = {
  messages: [...],
  moodValue: 55,
  todos: [
    { id, text, done, createdAt, source, completedAt },
    ...
  ],
  ...
}
```

每个房间的待办完全独立。"日常"房间里的待办和"心事"房间里的互不影响。

### UI 设计

一个新 page，挂到底部导航栏（第五个 tab，✅ 待办），同时在"我"页面加一个入口显示进度。

```
┌─────────────────────────────┐
│ ‹ ✅ 待办        🧹 📤     │
├─────────────────────────────┤
│ ██████████░░░░░░  3/7      │  ← 进度条
├─────────────────────────────┤
│ [添加待办…]          [添加] │
├─────────────────────────────┤
│ ○ 买牛奶           👤    ✕  │
│ ✓ 给妈妈打电话     🤖    ✕  │  ← 已完成有删除线
│ ○ 看那部电影       👤    ✕  │
└─────────────────────────────┘
```

几个细节：

- **进度条**用了绿色渐变，和微信绿同色系。`transition: width .3s` 让进度变化有动画感。
- **勾选动画**：圆圈从灰色边框变成绿色实心+白色勾号，用 CSS transition，不额外写 JS 动画。
- **删除确认**：加了 `confirm()` 弹窗——直接删太危险，万一误触 ✕ 就没了。弹出时显示待办内容，已完成的会标注 `✅ 已完成`。
- **全清按钮**：标题栏的 🧹 一键清除所有已完成项，同样有确认弹窗。
- **导出**：📤 把整份清单复制到剪贴板（纯文本表格），方便贴到别的地方。

### 和清除聊天记录的联动

`clearAll()`（设置里的"清空聊天"）现在也清待办。确认对话框里加了一行 `✅ 待办清单`，让用户知道会一起清掉。

这是一个容易遗漏的细节——加了新数据，就得检查所有"清空/重置"路径是否覆盖到。不然用户清空聊天后发现待办还在，或者更糟——待办引用的聊天上下文已经没了，变成僵尸数据。

### 自检时修的小问题

写完之后跑了一遍自检，修了三个小问题：

1. **冗余查询：** `toggleTodo()` 里先 `for` 循环找到 item 改了 `done` 状态，然后又 `todos.find()` 再查一遍看 `done` 是 true 还是 false。把状态存在局部变量 `newDoneState` 里直接复用，少了一次数组遍历。

2. **空状态提示文字：** 原来的提示说"在聊天中告诉 AI，AI 会自动帮你添加待办"——但 AI 自动添加功能已经移除了。改成"输入待办事项，按回车或点添加。AI 聊天时能看到你的待办清单"。

3. **`addTodo` 的 `source` 字段：** 原本用 `text ? 'ai' : 'user'` 判断来源（有没有传参决定是手动还是 AI 加）。AI 添加路径移除后，这个三元表达式永远走 `'user'` 分支。没删——留着的话，以后想恢复 AI 添加功能改一行就行。

### 经验

待办功能代码量不大（~450 行新增），但它代表了应用方向上的一个转变：从纯聊天到"聊天 + 工具"。这是从"AI 女友/男友"类应用转向"AI 陪伴工作台"的第一步。

设计上的取舍（AI 能看到但不能改）比技术实现更重要。有时候少做一点比多做一点更对。

## 二十八、共享歌单：给 AI 一双听歌的耳朵

待办做完之后，歌单就是顺理成章的下一步了。两者本质上是一样的——"AI 能看到但不能改"的共享工具。只是歌单多了一步：平台识别 + 内嵌播放。

### 需求

- 粘贴链接 + 输入歌名 → 自动识别平台
- 支持内嵌播放（YouTube / B站 / 网易云 / QQ音乐），不支持嵌入的（酷狗）新标签页打开
- 歌单按房间隔离，和待办一样
- AI 能看到歌单，聊天时自然提及，但不帮加不帮删

### 平台检测：五个平台，一个数组

整个平台检测系统的核心是一个配置数组 `PLATFORM_DETECT`：

```
YouTube  → ▶️ iframe 嵌入  ✓
B站      → 📺 iframe 嵌入  ✓
网易云   → 🎶 外链播放器  ✓
QQ音乐   → 🎵 内嵌播放器  ✓
酷狗     → 🎤 新标签页打开（不支持嵌入）
```

每条记录有四个要素：URL 匹配正则、图标、提取 ID 的方法、生成嵌入链接的方法。加一个新平台就是在数组里加一行——比如酷狗就是用户提了一嘴之后加进去的，前后两分钟。

### 格式提示：让用户知道该贴什么

加了之后发现一个问题——不是每个人都记得各平台的 URL 格式。于是在输入框下方加了格式提示：

- 空输入时：显示所有平台的格式示例（`youtube.com/watch?v=xxx · bilibili.com/video/BVxxx …`）
- 输入链接时：自动检测并显示对应平台的示例
- 未识别时：橙色警告"将作为普通链接保存"

这对不熟悉 URL 的用户帮助很大，也减少了"我贴了链接为什么识别不了"的困惑。

### 播放器

页面顶部嵌入一个 iframe 播放区域。点击歌曲 → 提取平台 ID → 生成嵌入 URL → 加载 iframe → 歌曲那一行出现绿色左边框高亮。

关闭播放器（点 ✕）→ 清空 iframe src → 收起播放区 → 取消高亮。

一个小细节：`_currentPlayingId` 跟踪当前播放的歌曲 ID。切房间时必须重置这个状态并关闭播放器——否则旧房间的歌还在 iframe 里播，而歌单列表已经换成了新房间的数据，两边的 ID 对不上，高亮永远是错位的。

### 自检时修的问题

1. **切房间播放器泄漏（自检发现）：** `switchRoom` 里加了关闭播放器、清空 iframe、重置 `_currentPlayingId`。这是典型的"加新全局状态变量后没在所有重置路径里覆盖"——和之前 `todos` 在 `clearAll()` 里缺失是同一类错误。

2. **`playPlaylistItem` 冗余回退代码：** 主分支用 `getPlatformInfo` + `extract/embed` 方法检测平台并生成嵌入链接。下面还有一个硬编码的 fallback 块单独处理 YouTube 和 B站——但这两个平台在上面的主分支已经被正确处理了。删了 14 行死代码。

3. **`textContent` → `innerHTML`：** 格式提示需要换行和小字号 span，原来的 `textContent` 设值会原样显示 HTML 标签。换成 `innerHTML` 后正常渲染。因为提示内容是纯硬编码的（不含用户输入），没有 XSS 风险。

### 经验

歌单功能 ~390 行，和待办差不多。但它多了一层"外部平台适配"的复杂度——每个音乐/视频平台有自己的 URL 格式、ID 提取规则、嵌入策略。`PLATFORM_DETECT` 数组的设计让加新平台变成纯配置工作，不用改业务逻辑。

这也印证了之前待办章节的结论：**AI 辅助但不替代。** 歌单里的东西是你真正喜欢听的，不是你随口提了一句 AI 就帮你塞进去的。但这个歌单 AI 看得见——它知道你在听周杰伦，下次聊到演唱会时可以自然地接上话。

## 二十九、自检优化：图片、性能、兜底

歌单做完之后做了一轮全面的自检优化。这次不是修 bug，而是主动排查"能用但不够好"的地方。

### 图片上传：从 2MB 到 10MB，加上取消按钮

之前所有图片上传限制都是 2MB——那是 localStorage 时代的遗产。现在数据存在 IndexedDB 里，单条记录可以轻松到几百 MB，没有理由还限制 2MB。而且所有图片上传都有压缩流程（头像压缩到 200×200 JPEG 0.5，背景 max 800px，锁屏 max 400px），最终存进 IDB 的 base64 字符串其实很小。所以把三个入口的限制统一改成了 10MB：头像、聊天背景、锁屏壁纸。锁屏壁纸之前甚至没做大小检查，也补上了。

另一个问题：头像可以"更换"但不能"取消"。聊天背景和锁屏壁纸都有"恢复默认"按钮，唯独头像没有——你一旦换了自定义头像，就回不去默认 emoji 了。加了 `clearAvatar()` 函数，设置页"更换"旁边多了一个"恢复默认"，点了弹确认，确认后清掉 `dataUrl` 用回 emoji。

### 上下文窗口：30 条 → 50 条

`callDeepSeek` 里 `messages.slice(-30)` 构造对话上下文。30 条对于简单聊天足够了，但布雷斯的 system prompt 已经膨胀到包含人设、记忆库、心情、好感度、日记、朋友圈、待办清单、歌单……经常超过 2000 个 token。30 条上下文 + 2000 token system prompt + 400 token max_tokens，已经逼近 DeepSeek 的 8K 上下文窗口。但多 20 条上下文意味着 AI 能记住更早的对话伏笔，对于"布雷斯"这种需要维持角色一致性的场景很重要。

改 30 → 50 就一行代码，效果显著。

### API 错误兜底：从"坏了"到"走神了"

这是这次优化里用户体验收益最大的一项。

之前 `callDeepSeek` 的错误处理很粗暴：`if (!resp.ok) return null;`。上层拿到 null → 弹出 toast "请检查 API Key 是否正确"。

这个 toast 的潜台词是"应用出问题了"。但用户不想看到"出问题了"——他们想看到布雷斯只是"走神了"。

于是加了一个离线回复池：

```
API Key 失效 (401) → "你的 Key 好像过期了…去设置里换一个新的？我等你 🔑"
限流 (429)       → "消息发太快了…让我喘口气，等一下再找我 💨"
网络断开          → "刚才走神了，你再说一遍？🤔"
```

每个类型有 3-5 条随机备选语，不会重复。`callDeepSeek` 返回这些字符串而不是 null，上层把它们当正常 AI 回复渲染——用户看到的是布雷斯用拟人的方式解释为什么没回，而不是一个系统 toast。网络恢复后的 catch 分支也套了同样的逻辑。

**心理暗示比技术实现重要。** "应用出错"→ "布雷斯走神"，用户感受完全不同。

### 消息渲染：增量替代全量

这是性能层面的改动。

之前 `sendMsg` 的发消息流程：

```
用户消息 push → renderMessages() → 全量销毁+重建 DOM
AI 占位 push → renderMessages() → 全量销毁+重建 DOM（第二次！）
流式 token → updateBubbleText → 原地替换文字（OK）
```

发一条消息，整个消息列表重建了两次。聊天记录 300 条时，每次重建遍历 300 条消息、创建 300 个 DOM 节点，移动端有明显卡顿。

但 `appendMessageRow()` 函数本来就有了——它只追加一个新消息的 DOM 节点，处理日期分隔线，不做全量重建。不知道为什么之前 `sendMsg` 没用它。改成：

```
用户消息 push → appendMessageRow(userMsg) → 追加一个节点
AI 占位 push → appendMessageRow(aiMsg) → 追加一个节点
流式 token → updateBubbleText → 原地替换文字
```

`renderMessages()` 仍然保留用于初始加载、切房间、搜索、导入——这些都是低频操作，全量重建无所谓。高频的"发消息"路径走增量追加。

贴纸回复和主动消息的路径也一并改了。

### 这次跳过的

有几个建议评估后决定不做：

- **虚拟列表（Virtual Scroll）：** 工程量 ~300 行，现有懒加载（200 条阈值）+ 增量渲染已覆盖主要痛点。虚拟列表的增益主要在 1000+ 条的极端场景，而大部分用户的聊天记录不会到那个量级。
- **visualViewport 键盘适配：** 需要真机逐机型调试，桌面端无法验证。不是不做，是没法在现在做。
- **红包真实支付和定时消息持久化：** 纯前端应用的天花板，不做。

## 三十、APK 打包与双环境适配

做完自检优化之后，用 HBuilder X 把这个 HTML 打成了 APK。一个 8200 行的单文件，变成安装包装进手机——然后发现了好几个只在真机环境里才会暴露的问题。

### APK 环境 vs 浏览器环境

浏览器和 WebView 看起来都是 Web 技术栈，但底层 API 不同：

- 浏览器：`FileReader`、`Blob` download、`<a download>`、`navigator.clipboard`
- HBuilder WebView：多了 `plus.io`（文件 IO）、`plus.gallery`（相册）、`plus.device` 等原生桥接

所以需要一个环境检测：

```javascript
var _isApp = (function() {
  try { return !!(navigator.userAgent.indexOf('Html5Plus') !== -1 || window.plus); } catch(e) { return false; }
})();
```

之后所有"浏览器和 App 行为不同"的地方，都用 `if (_isApp)` 分支处理。

### Bug 1：智能体切换数据串台（致命）

这是打包 APK 之后发现的第一个大 bug，但它其实是代码逻辑问题，和环境无关——只是在真机上测试切换智能体频率更高，更容易触发。

根因：`switchAgent` 在切换前调了 `saveData()` 保存旧智能体数据，然后改 `activeAgentId`，再调 `loadData()` 加载新数据。但**没有清空内存里的旧变量**——`messages`、`moments`、`memoryStore`、`todos`、`playlist` 等 20+ 个变量原封不动留在内存里。如果新智能体还没在 IDB 存过数据，`loadData` 读不到东西就不赋值，旧数据残留在内存 → 串台。

修法：在 `loadData` 之前把所有 per-agent / per-room 变量全量清零——跟 `switchRoom` 一模一样的逻辑。同时关闭播放器、重置 `_currentPlayingId`。

这是一个典型的"状态没在所有退出路径里清理"的错误。之前 `clearAll` 漏了 `todos` 也是同一类。

### Bug 2：JSON 导入只弹相机

在浏览器里，`<input type="file" accept=".json">` 会弹出文件选择器、过滤显示 JSON 文件。但在 Android WebView 里，`.json` 扩展名不被系统文件选择器识别 → 系统不知道你要选文件 → 默认跳到相机。

修法：`accept="application/json,.json"`。MIME 类型 + 扩展名双保险，Android 能识别 `application/json`。

图片上传的 `accept="image/*"` 没有问题——Android 原生支持这个 MIME，会弹出相机 / 相册 / 文件管理器三个选项。

### Bug 3：导出文件名乱码

浏览器 download 机制用 `<a download="文件名.json">`，但在 HBuilder WebView 里，中文文件名经过 URL 编码后变成 `%E8%81%8A%E5%A4%A9%E5%A4%87%E4%BB%BD.json`，部分 Android 版本甚至直接变成乱码字符。

修法：App 环境不用浏览器 download，改用 `plus.io` 直接写到手机 `Downloads/` 目录。文件名做安全处理（去掉特殊字符和空格），用 ISO 日期格式避免中文。写了一个统一的 `saveFileToDevice(name, content, mimeType)` 函数，三个导出入口（聊天备份、待办清单、共享歌单）全部走它。

浏览器环境保持原来的 download 逻辑不变。

### 不需要改的地方

有一个重要的教训：**图片上传不需要动。** 一开始想用 `plus.gallery.pick()` 接管所有图片选择，写了一大堆适配代码。后来意识到 `accept="image/*"` 在 WebView 里本来就正常工作——系统弹出原生选择器，相机、相册、文件管理器三个选项都在。加了 50 行适配代码反而把选项限制成了只有相册。

全删了。回到最简单的 `triggerFileInput(id) { document.getElementById(id).click(); }`。

**不是每个环境差异都需要"适配"——有时候原生行为就是最好的行为。**

### APK 更新的数据持久性

HBuilder X 的云端证书绑定了**账号 + AppID（包名）**。只要不改 `manifest.json` 里的 AppID，每次云打包用的是同一张证书 → 覆盖安装 APK → IndexedDB 数据全部保留。

整个项目的 HBuilder 结构不超过三个文件：

```
小手机/
├── index.html      ← 布雷斯.html 复制过来改名
├── manifest.json   ← AppID + 配置（不能丢）
└── unpackage/      ← 打包输出
```

每次更新就是把新的 `布雷斯.html` 覆盖 `index.html`，然后云打包。

### 导出方案迭代：从 plus.io 到系统分享

第一版 App 导出用了 `plus.io.requestFileSystem(PUBLIC_DOWNLOADS, ...)` 直接写 Downloads 目录。真机上反馈 toast 显示"已保存"但文件不存在。

排查发现是 Android 10+ 的 scoped storage（分区存储）导致的。`PUBLIC_DOWNLOADS` 在旧 Android 上是真实的公共目录，在新版本上变成了受限区域。`plus.io` 的 write 回调确实执行了——但文件被写到了应用专属子目录，用户用文件管理器看不到。

改了两版：第二版用 `<a download>` 在 WebView 里触发下载，部分旧设备不支持。最终版分两路——先把文件写入 App 私有文档目录（`PRIVATE_DOC`，App 自己的沙盒，100% 写入成功），然后调起 Android 系统分享面板（`plus.share.sendWithSystem`）。用户自己选"保存到文件"或发微信、发邮件。

```
生成 JSON → 写入 App 私有目录 → 📤 弹出系统分享面板
                                      ↓
                         用户选：保存到文件 / 微信 / 邮件 / 网盘…
```

分享面板方案上线后，用户反馈下载通知弹了但文件下载失败。排查发现：Android 下载管理器是系统级进程，拿不到 WebView 内部的 Blob URL（`blob:...`）。下载管理器能看到下载请求，但解析不了 Blob URL → 下载失败。

**第四版（最终版）：** 区分环境，APK 不用 Blob URL。

- APK：把 JSON 转成 Base64 Data URL（`data:application/json;base64,...`）。Data URL 是自包含的——所有数据嵌在 URL 本身里，不依赖外部引用。Android 下载管理器能直接解析。
- 浏览器：继续用 Blob URL，更轻量。

Base64 编码的关键一行：

```javascript
var base64 = btoa(unescape(encodeURIComponent(content)));
```

`encodeURIComponent` 把中文转成 UTF-8 字节序列，`unescape` + `btoa` 完成 Base64 编码。这个组合是 JavaScript 里最兼容的 UTF-8 Base64 方案——`TextEncoder` 在旧 WebView 里不可用。

四版迭代，最后回到了最基础的一行：`<a download>`。只是把 URL 类型从 Blob 换成了 Data。有时候修 bug 不是加代码，是换一种原材料。

### 弹窗通知和主动消息的评估

讨论了一下要不要加 AI 回复弹窗通知和主动消息功能。

**弹窗通知：** 桌面浏览器可以用 `Notification` API，手机浏览器和 WebView 基本不可用（后台冻结）。真正有用的场景只有"桌面端切到其他标签页"——你在手机上用为主，这个场景占比太小。150 行代码换边缘场景，不划算。

**主动发消息：** 目前已有——早上 6-9 点早安、晚上 9-11 点晚安、超过 3 小时没说话送问候。触发机制是 `setInterval` 每 30 秒检查一次。问题是浏览器/WebView 进后台后定时器被冻结，所以**必须开着页面**才能工作。这是纯前端应用的天花板——真正的后台唤醒需要原生 `WorkManager` 或推送服务，不在单文件 HTML 的能力范围内。

## 三十一、钱包系统：礼物商店、账单和 AI 的罚单

待办和歌单是"一起管理生活"，钱包则更进一步——让 AI 和用户之间有了经济互动。不只是聊天，可以发红包、买礼物、被罚款、收到转账。

### 红包文案 AI 化

之前红包祝福语是硬编码的五句话："魔法部的奖金分你一半 🪄"、"拿去买小蛋糕 🍰"……不管什么智能体都随机抽。布雷斯（哈利·波特人设）说"魔法部奖金"很自然，但用户创建的其他角色——比如一个赛博朋克黑客——说这句话就完全出戏。

改成 AI 实时生成：发红包前用非流式 API 调用一次，传入当前智能体的完整人设，让 AI 写一句 15 字以内、符合角色性格的祝福语。布雷斯会说"魔法部季度奖金"，赫敏会说"图书馆借书钱省着点"，赛文会说"任务完成度达标奖励"。

API 挂了有一个通用 fallback 列表兜底，不含任何人设特定内容。

### 交易记录：每一笔钱都有来龙去脉

之前红包和签到只是改了余额数字，没有记录。现在加了 `addTransaction` 函数，所有余额变动自动记账：

```javascript
transactions.unshift({
  type: 'redpacket_in' | 'checkin' | 'gift_buy' | 'fine' | 'transfer_in' | ...
  amount: +10 或 -5,
  balance: 变动后余额,
  description: '拆红包：魔法部季度奖金',
  time: Date.now(),
});
```

每个改余额的地方（发红包、拆红包、签到、买礼物、AI 罚款、AI 转账）都加了一行 `addTransaction` 调用。账单页面按月统计收入/支出，支持全部/收入/支出筛选。

### 礼物商店

有了钱就得有地方花。礼物商店六件商品：

| 礼物 | 价格 | 效果 |
|------|:--:|------|
| ☕ 虚拟咖啡 | ¥5 | 😊+6 |
| 🍰 小蛋糕 | ¥10 | 😊+8 💕+1 |
| 🌹 玫瑰花 | ¥15 | 😊+12 💕+2 |
| 🎁 神秘礼盒 | ¥20 | 😊+10 💕+1 |
| 💌 手写信 | ¥25 | 😊+15 💕+3 |
| ⭐ 星星 | ¥30 | 😊+20 💕+4 |

点击购买 → 扣余额 → 进背包。背包里的礼物可以**使用**——点击后送给 AI，AI 的心情和好感度按礼物效果提升。同时系统提示里注入："她刚刚送了你 ⭐ 星星（你就是我的星星）"，AI 下一句回复会自然地感谢。

这个设计有一个微妙之处：礼物不是买完自动生效的。你需要**主动使用**——就像你真的把礼物递过去一样。AI 的感谢不是系统通知，而是融在对话里的自然回应。

### AI 罚款和转账

系统提示里加了一组规则，AI 可以动用户的钱包：

- **罚款 `[FINE]金额|原因[/FINE]`：** 用户说了"今天早睡"结果凌晨还在聊天 → AI 回复里带 `[FINE]5|说好的早睡呢[/FINE]` → 扣 5 块。限额 1-10 元，一天一次。
- **转账 `[TRANSFER]金额|原因[/TRANSFER]`：** 用户完成了所有待办 → AI 回复里带 `[TRANSFER]8|待办全勤奖[/TRANSFER]` → 到账 8 块。限额 1-15 元，一天一次。

标记在流式显示时实时剥离，用户看不到。解析后自动扣款/到账并写交易记录。

代码层面也有硬限制——即使 AI 忽略"一天一次"的规则，`executeWalletMarkers` 会检查当天是否已经有过同类型交易，拒绝多余的。

### 礼物系统的设计迭代：一种失败才学会的克制

礼物使用后的反馈机制经历了四版迭代，每一版都在做减法。

**第一版——静默生效。** 点了使用 → 改数字 → 没有任何可见反馈。用户不知道发生了什么，不满意。

**第二版——即时 AI 回复。** 点了使用 → 自动切到聊天页 → 调 API → AI 当场回复。实现上踩了三个坑：页面切换动画和 DOM 重建的时序冲突、自定义 SSE 流读取的递归 Promise 没处理好、`callDeepSeek` 内部会重建 system prompt 导致礼物上下文被覆盖。修了三次，仍然不可靠。

**第三版——插入系统消息。** 点使用 → 在聊天里插入一条特殊消息。问题是 `renderMessages` 不知道 `role: 'system'` 的消息怎么渲染，消息消失了。

**第四版（最终版）——等待用户说话。** 礼物使用后只做三件事：扣库存、改数值、在系统提示里设一个标记（`_lastUsedGift`）。用户下次发消息时，`buildSystemPrompt` 读标记 → 注入礼物上下文 → AI 自然回应 → 清除标记。

```
使用 ⭐ 星星 → toast "⭐ 星星 已送出 · 好感 +4"
     ↓
数值永久生效（心情 +20，好感 +4）
     ↓
你下次发消息 → AI 回复里自然感谢 → 标记清除
```

四版迭代的教训：**不是每个交互都需要即时反馈。** 有时候"等一下会回应"比"当场自动回复"更自然——就像你真的递了个礼物过去，对方不会立刻喊出感谢词，而是在接下来的对话里自然提到。

### 签到跨房间共享

签到这个功能之前有个漏洞：`checkinData` 存在 room data 里，切房间就重置。同一个智能体的不同房间可以各签一次——一天能签好几次。

修法：把 `checkinData` 从 room 级别升到 agent 级别（`agentKey('checkin')`）。同一个智能体的所有房间共享签到状态，切换智能体才重置。

这是数据建模里的一个经典问题：**什么该 per-room，什么该 per-agent？** 聊天记录、待办、歌单、账单 → room 级别。签到、余额、人设 → agent 级别。分错了就会出现"切房间重复签到"这种 bug。

## 三十二、图片裁剪：让用户自己选要哪一块

之前的图片上传有一个小问题：头像、聊天背景、锁屏壁纸都是自动从中心裁剪。如果图片是横构图、或者主体不在正中间，裁出来就歪了。

朋友反馈说头像"它不能自行截取，软件上面自己随机截到一个部分，不太完整"。于是就做了个裁剪组件。

### 设计

一个全屏浮层（`z-index: 999`），黑底，中间是裁剪区域，下面两个按钮：

```
选图片 → 弹出裁剪框
         ┌─────────────────┐
         │                 │
         │   [图片内容]    │  ← 单指拖拽移动
         │  ┌──────┐      │  ← 双指捏合缩放
         │  │ 裁剪区│      │  ← 滚轮缩放（桌面）
         │  └──────┘      │
         │                 │
         └─────────────────┘
        🖐 拖拽移动 · 双指缩放
           [取消]    [确定]
```

三个上传入口都接入，统用一个 `showImageCropper` 函数：

| 入口 | 形状 | 裁剪框尺寸 |
|------|:--:|:--:|
| 头像 | ⭕ 圆形 | 200px |
| 聊天背景 | ▢ 方形 | 400px |
| 锁屏壁纸 | ▢ 方形 | 400px |

确定后用 Canvas `drawImage` 按裁剪区域 + 缩放比例算出原图坐标，截出之后再走原来的压缩流程。取消就什么都没发生。

### 交互

同时支持触摸和鼠标：

| 平台 | 移动 | 缩放 |
|------|------|------|
| 手机 | 单指拖拽 | 双指捏合 |
| 桌面 | 鼠标拖拽 | 滚轮 |

触摸事件和鼠标事件各自独立挂在容器和 window 上，`cleanupCrop` 里全部卸载，不会残留。位置钳制（`clampCropPosition`）确保图片不会被拖出裁剪框。缩放范围 0.3x ~ 3x。

### 适配

裁剪组件用的是纯标准 Web API——Canvas、FileReader、Touch Events、Mouse Events。不涉及任何 `plus.*` 或平台特定代码。浏览器和 APK 行为完全一致。

`input.value = ''` 清空在 `reader.readAsDataURL` 之后同步执行，保证下次选同一张图也能触发 `onchange`。

### 经验

~220 行代码，三个入口各改了一行 `reader.onload`。关键设计是"提取再传入"——先把图片加载到裁剪组件里，用户在组件里操作完，把裁好的结果传给原来的压缩函数。这样裁剪组件完全不知道自己被谁调用，压缩函数也不知道图片经过了裁剪。解耦得很干净。

## 三十三、三个回头箭：回归 Bug 排查记

裁剪功能加上去之后，手机端出现了一连串奇怪的故障——所有上传按钮按不了、导入导出没反应、礼物只有咖啡能送出。花了大半天排查，三个 bug 根因各不相同，但有一个共同点：**都不是裁剪逻辑的问题，而是"加新东西时顺带改了别的，没意识到影响面"。**

### Bug 1：全屏透明层拦截所有触摸

裁剪浮层为了隐藏时能顺畅过渡，用了 `display: flex; opacity: 0; z-index: -1; pointer-events: none` 而不是 `display: none`。桌面端完全正常——`pointer-events: none` 让所有点击穿透。但某些 Android WebView 在触摸 hit-test 时不认 `pointer-events: none`——一个 `position: fixed; inset: 0` 的 flex 容器即使完全透明、z-index 为负，仍会拦截所有触摸事件。

整个手机端的导入、导出、上传按钮全部因为这个透明层失效——用户点任何按钮，触摸都被这个看不见的浮层吞了。

修法：回到 `display: none`。隐藏时不渲染，不需要任何触摸穿透技巧。

### Bug 2：`_isApp` 永远为 false

`_isApp` 是一个 IIFE，在脚本加载时同步执行：

```javascript
var _isApp = (function() {
  try { return !!(navigator.userAgent.indexOf('Html5Plus') !== -1 || window.plus); }
  catch(e) { return false; }
})();
```

但 HBuilder 的 `window.plus` 是**异步注入**的——`plusready` 事件触发之后才可用。IIFE 在脚本解析阶段运行，此时 `plus` 还不存在。如果 user agent 里也没有 `Html5Plus` 字符串（部分 WebView 配置或新版 HBuilder 可能没有），`_isApp` 就永远是 `false`。

后果：APK 里导出功能走浏览器路径（` <a download>`）→ WebView 里没有系统下载管理器 → 文件保存不触发。导入的 `el.click()` 也被 WebView 安全策略拦截 → 文件选择器弹不出来。

修法：加一行 `plusready` 监听，异步修正 `_isApp = true`。

### Bug 3：`adjustAffection` 未定义

`useGift` 函数里有这行：

```javascript
if (gift.affection > 0) adjustAffection(gift.affection);
```

但 `adjustAffection` 在整个 8900 行的文件里**从未被定义**。为什么一直没发现？因为咖啡的 `affection: 0`，守卫条件 `gift.affection > 0` 为 false，跳过了这个调用。咖啡能正常送出。

蛋糕（`affection: 1`）、玫瑰（`affection: 2`）、手写信、星星——全部崩在 `adjustAffection` 这一行。`ReferenceError` 导致函数提前返回，`_lastUsedGift` 没设，AI 永远不知道你送了礼物。更糟的是礼物已经从背包里扣掉了，`setMood` 里触发的 `saveData` 把扣除后的库存持久化了——**礼物被吃了，没有任何反馈。**

修法：加一行 `function adjustAffection(delta) { affectionLevel = Math.min(10, Math.max(1, affectionLevel + delta)); }`。

### 三个 bug 的共同特征

1. **不是逻辑错误，是"没考虑到"。** 裁剪浮层的 CSS 写法在桌面端完全正常；`_isApp` 在旧版 HBuilder 或 user agent 含关键字的设备上正常；`adjustAffection` 问题被咖啡的 `affection: 0` 完美掩盖。

2. **影响面被低估。** 改一个 CSS 属性 → 全站触摸失效。一个未定义函数 → 四件礼物全部报废。一个 IIFE 的执行时机 → 整个 APK 的导入导出瘫痪。

3. **缺乏防御性编码。** `adjustAffection` 如果先检查 `typeof adjustAffection === 'function'`，或者用一个 `try-catch`，至少不会静默失败。

1. **文件写入目录选错 = 功能废掉。** 写私有目录技术成功，用户找不到等于没用。
2. **HTML 嵌套错误是静默的。** 浏览器不报错，CSS 完全正确——但坐标系歪了。
3. **模拟点击不如真点击。** 透明 input 覆盖在 UI 上，零行 JS，永远不翻车。
4. **加了新消息类型必须去所有 AI 调用点加过滤。** 漏一个 AI 就会看到不该看的东西。

## 三十五、APK 导出功能调试：七版迭代，最后是 seek 的锅

三十四章说"导出统一"的时候，其实导出在 APK 上还没真正跑通。这一章记录的就是后面发生的事情——从"按键没反应"到"文件终于出现在手机里"，中间换了七种方案。

### 症状：按了导出，什么都没发生

APK 打包后点任何导出按钮，toast 不弹、分享面板不出、文件找不到。体感就是按了等于没按。

但在浏览器里一切正常。模拟器里也时好时坏。这说明不是函数调用链的问题——`onclick` 能触发、`saveFileToDevice` 能进去——是 H5+ 文件 API 在不同环境下的行为不一致。

### 第一版：PUBLIC_DOWNLOADS

最初想的是直接写到系统下载文件夹。用 `plus.io.requestFileSystem(4, 0, ...)`——类型 4 就是 `PUBLIC_DOWNLOADS`。

结果：文件没出现在下载目录。Android 10+ 的分区存储（scoped storage）限制了直接写入公共目录，H5+ 的 `requestFileSystem` 在这种限制下行为不确定——有时静默失败，有时写到应用专属子目录但路径看起来像公共目录。

### 第二版：_downloads/

换 `resolveLocalFileSystemURL('_downloads/')`，H5+ 的快捷路径。结果：模拟器上能用，真机上不行。不同 HBuilder 版本对 `_downloads/` 的映射不一致。

### 第三版：_doc/ + 分享面板

`_doc/` 是 App 私有文档目录，写入不需要任何权限。写完用 `plus.share.sendWithSystem` 把文件路径传给系统分享面板，用户自己选保存到哪。

这版按键终于有反应了！toast 弹了，分享面板也弹了。但分享面板点"保存到文件"后，文件管理器的搜索搜不到这个文件。需要手动导航到 `/storage/emulated/0/Android/data/plus.xxx/apps/xxx/doc/` 才能找到。

路径太深，用户不可能每次手动翻。

### 第四版：_doc/ + openFile

把分享面板换成 `plus.runtime.openFile`——直接调系统文本编辑器打开文件，用户从编辑器菜单另存。

结果：按键又没反应了。回退对比发现，`openFile` 在某些 HBuilder 版本会抛异常，而且异常没被外层 try-catch 抓到（异步回调里的错误），导致后续逻辑全挂。

### 第五版：纯文本分享

跳过文件 IO，用 `plus.share.sendWithSystem({content: content})` 直接分享文本。用户问："复制了之后怎么存为 json？"

确实——纯文本分享出去，接收方拿到的是文本，扩展名丢了。用户要的是 `.json` 文件。

### 第六版：回到 _doc/_ + 分享面板

既然第三版能跑通，就别折腾了。回到最简单的版本：写 `_doc/` → 弹分享面板。

但文件写入有一半概率失败——`writer.onerror` 触发，错误码为空。排查发现是 `writer.seek(0)` 的锅。H5+ 的 FileWriter 在 `seek(0)` 之后调 `write()`，某些版本会静默丢弃数据。去掉 `seek(0)`，直接 `writer.write(content)`——文件 100% 落盘。

**七版迭代，最后修了一行：删掉 `writer.seek(0)`。**

### 长图导出的关闭按钮也修了

`exportAsImage` 在 APK 上也有两个问题：关闭按钮被预览层遮挡（z-index 56 太低），保存走的是坏的文件 API。

修法：把按钮从 `#app` 移到 `document.body`，z-index 拉到 999，黑底白字固定在屏幕底部。加了一个"💾 保存 HTML"按钮走 `saveFileToDevice`（和其他导出一致）。点预览背景也能关闭。

### 最终可用的导出方案

```
APK 导出流程：
  生成内容 → _doc/ 写文件 → toast "已导出 ✅" → 弹分享面板
                                          ↓
                              用户选"保存到文件"或发微信
```

| 导出 | APK 行为 |
|------|------|
| 📋 待办 | 写 `_doc/` → 分享 |
| 🎵 歌单 | 同上 |
| 📔 日记 | 同上 |
| 📷 朋友圈 | 同上 |
| 💬 聊天 | 同上 |
| 🧠 记忆+配置 | 同上 |
| 📸 长图 | 预览 + 底部按钮关闭/保存 |

浏览器导出全程不动——`<a download>` 原样保留。

### 经验

1. **H5+ 文件 API 在不同版本间行为不一致。** `requestFileSystem`、`resolveLocalFileSystemURL`、`_downloads/`、`PUBLIC_DOWNLOADS`——同一个调用，模拟器和真机、Android 10 和 11、HBuilder 3.6 和 3.8，结果各不相同。最稳的是最保守的方案：私有目录 + 最少 API 调用。

2. **`writer.seek(0)` 是坑。** 这个调用在某些 H5+ 版本里会让后续 `write()` 静默失败。想清空文件用 `truncate(0)`，但新建文件根本不需要清空——直接写就行。

3. **分享面板是最可靠的"保存"方式。** 不依赖文件系统权限、不依赖 MediaStore 索引、不依赖系统下载管理器。用户自己决定文件存哪。

4. **诊断 toast 是调试利器。** 在函数入口加了一个 `showToast('导出中…')`，立刻就知道函数是否被调用、问题在哪个环节。确认通了之后删掉。

## 三十七、图片上传修复：裁剪器移除 + 等比缩放

用户反馈所有头像上传全部失效——用户头像、智能体头像、聊天背景、锁屏壁纸，浏览器和 APK 都不行。唯独朋友圈图片上传正常。

### 排查：不是 input 触发的问题

一开始怀疑是 `display:none` 的 file input 在 WebView 里 `.click()` 不触发——这是之前朋友圈图片上传的根因。于是把四个上传入口全部改成和朋友圈一样的 opacity-0 覆盖方案。结果还是不行。

打开浏览器 F12 控制台，没有任何报错。说明 onclick 触发了、文件选择器弹了、图片也读了。

### 定位：裁剪器

对照备份版本发现——能用的备份没有图片裁剪器（`showImageCropper`），不能用的当前版本有。裁剪器是一个全屏浮层，`position: fixed; inset: 0; z-index: 999`，让用户拖拽移动、双指缩放来选取裁剪区域。

问题出在 `file://` 协议下 Canvas 的 `toDataURL` 在某些浏览器/WebView 中受限。裁剪器内部用 `img.src = dataUrl` 加载图片再渲染到 Canvas——`file://` 协议下这个 data URL 可能被浏览器当作跨域资源拒绝加载，`img.onerror` 触发，裁剪器显示一片黑。

修了 `img.onerror` 处理、加了 overlay 状态重置——仍然"图片加载失败"。

### 方案：去掉裁剪器，改成等比缩放

四个上传函数（`uploadAvatar`、`setLockWallpaper`、`setChatBackground`，布雷斯头像也走 `uploadAvatar`）全部去掉 `showImageCropper` 调用，改成 FileReader → Image → Canvas 等比缩放 → 直接保存。

原来的中心裁切（取图片中间 200×200 正方形）也改成了等比缩放——整张图缩到目标尺寸以内，不切任何部分。头像最长边 200px，锁屏 400px，聊天背景 800px。JPEG 质量 0.5-0.6。

```javascript
// 改前：中心裁切
var size = Math.min(img.width, img.height, 200);
ctx.drawImage(img, (img.width-size)/2, (img.height-size)/2, size, size, 0, 0, size, size);

// 改后：等比缩放
var scale = Math.min(200 / img.width, 200 / img.height, 1);
canvas.width = Math.round(img.width * scale);
canvas.height = Math.round(img.height * scale);
ctx.drawImage(img, 0, 0, canvas.width, canvas.height);
```

### 恢复默认也补全了

用户头像之前没有"恢复默认"按钮——智能体头像、锁屏壁纸、聊天背景都有，唯独用户头像缺。`clearAvatar('user')` 函数早就写好了，只是 HTML 里没放按钮。补了一行。

### 经验

1. **`file://` 协议的坑比想象的多。** Canvas data URL 跨域、Blob URL 下载被拒、file input 的 `.click()` 被安全策略拦截——本地开发的便利性和浏览器安全沙箱一直在打架。
2. **复杂 UI 组件增加失败面。** 裁剪器在线上环境（HTTP/HTTPS）完全正常，在 `file://` 下挂了。全屏浮层 + Canvas 操作 + 触摸事件，三个环节每个都可能出问题。
3. **有备份真好。** 对照一眼就看出差异——裁剪器是多出来的那部分。没备份的话要排查很久。


## 三十八、脱敏通用版 Phone + 数据彻底隔离

项目写到这个程度，有人问"能不能给我一个能用的版本"。但布雷斯有完整的角色背景故事、个性化设定、甚至贴纸都是哈利波特主题——直接发出去不合适。

于是做了个脱敏通用版，叫 **Phone**。放在仓库 `assets/phone.html`，博客文章顶部也有下载链接。

### 脱敏了什么

| 内容 | 原版 | 脱敏版 |
|------|------|------|
| 人设 | 1200字布雷斯背景故事 | 100字通用AI助手 |
| 默认名 | 布雷斯 | AI助手 |
| 默认头像 | 🐍 | 🤖 |
| 贴纸 | 斯莱特林/魔法部/霍格沃茨 | 闪亮/工作/城堡 |
| 状态文字 | 在魔法部上班 | 工作中 |
| 代码注释 | 布雷斯相关 | 通用化 |

### 数据隔离：两个世界不能互通

这是最容易被忽略的问题。脱敏版和原版在同一个浏览器打开，数据会串吗？

答案是——如果不处理，一定会。原因有两个：

1. **IndexedDB**：两个 HTML 用同一个数据库名 `bles_db_v1`，读写同一份数据
2. **localStorage**：`file://` 协议下所有本地文件共享 localStorage，智能体列表 `bles_agents_list` 会被两个版本同时读写

修法就三行：

```
// IndexedDB
bles_db_v1 → phone_db_v1

// localStorage
bles_agents_list → phone_agents_list
bles_active_agent → phone_active_agent

// 迁移
禁用 localStorage→IndexedDB 迁移（全新应用不需要搬旧数据）
```

改完之后，两个版本在同一浏览器打开，各自有各自的智能体、聊天记录、设置。互不干扰。

### 内部 ID 不能随便改

脱敏时想把默认智能体的内部 ID 从 `'bres'` 改成 `'default'`——想着"这样更干净"。结果改了之后整个应用炸了。

朋友圈发帖用的是 `author: 'bres'`，红包用的是 `from: 'bres'`，头像渲染用的是 `bresProfile`，切换智能体用的是 `switchAgent("bres")`——二十多处硬编码引用了 `'bres'` 这个字符串。它不是用户看到的"布雷斯"名字，是系统内部的身份证号。

改回去。`'bres'` 留在代码里当内部标识，显示层用 `AI助手` + `🤖`。内部 ID 和显示名是两个概念——这是这次脱敏学到的最重要的一课。

## 三十九、时间线死循环：两个函数互相踢皮球

Phone 版跑到 HBuilder X 模拟器上之后，控制台刷刷报错：

```
Uncaught RangeError: Maximum call stack size exceeded at phone.html:5991
```

但应用还能正常用——聊天没崩，设置能开，朋友圈也行。就时间线页面偶尔抽风。

### 排查

报在第 5991 行，是 `showTimelineDate` 函数。看调用链：

```
showTimelineDate(dateStr)           ← 第 5991 行
  → stopTimelineReplay()            ← 第 5993 行
    → showTimelineDate(_timelineDate) ← 第 6057 行，又回来了！
      → stopTimelineReplay()
        → ...无穷无尽
```

死循环的形成条件很简单：

1. `showTimelineDate` 刚进来就给自己设了 `_timelineDate = dateStr`
2. 然后调 `stopTimelineReplay()`
3. `stopTimelineReplay` 末尾写了 `if (_timelineDate) showTimelineDate(_timelineDate)`——"回放停止后，恢复到当前正在看的那一天"
4. 但 `_timelineDate` 刚在步骤 1 被设置了，不是 null，于是一脚踢回 `showTimelineDate`
5. 重复步骤 1-4，栈爆了

这个设计意图是好的——回放结束后时间线要回到正在浏览的那一天。但它没考虑到 `showTimelineDate` 自己也在调 `stopTimelineReplay`。两个函数互相信任对方"不会调回来"，结果形成了完美的环形依赖。

### 为什么没崩？

浏览器（WebView）的 JS 引擎捕获了 `RangeError`，没有让整个进程挂掉——只是那个调用栈被丢弃了。所以时间线功能废了，但聊天主流程不受影响。这是个侥幸——如果这个错误出现在更核心的路径上，整个应用就没了。

### 修法

一行守卫，加在 `showTimelineDate` 最开头：

```javascript
function showTimelineDate(dateStr) {
  if (_timelineDate === dateStr) return;  // ← 就这一行
  _timelineDate = dateStr;
  stopTimelineReplay();
  // ...
}
```

逻辑：当 `stopTimelineReplay` 踢回来的时候，传入的 `dateStr` 和当前 `_timelineDate` 一模一样——因为 `_timelineDate` 刚在第一轮就被设成了这个值。守卫撞到"一样的日期"，直接返回。死循环断开。

### 教训

两个函数互相调用不是原罪——事件驱动的代码难免会有。关键是**永远给自己留一个出口**。守卫不需要多复杂，一行 `if (x === y) return;` 就够了。

而且这次让我意识到：**一个 bug 没崩掉整个应用，不代表它不是 bug。** 它可能只是运气好，刚好在一个可以被 WebView 安全捕获的位置爆了。换成另一个函数调用，可能就是白屏满天飞。

## 四十、时间线闪动：七种方案，最后是 opacity 救的

切到回忆页时，日历区域会闪一下——先看到空白，再弹出内容。APK 和浏览器都有。

### 七种失败

预渲染、延迟渲染、去 opacity、关动画、rAF 批处理、同步渲染、visibility toggle——全无效。

### 根因

页面切换流程：`classList.add('active')` → 页面可见 → `renderTimelineCalendar()` 渲染。页面先可见，内容后到位，浏览器在中途画了一帧空白。

### 最终方案

把顺序反过来——先渲染再可见：

```javascript
targetPage.style.opacity = '0';          // 不可见
targetPage.classList.add('active');       // 激活（用户看不到）
renderTimelineCalendar();                 // 渲染内容到不可见页面
requestAnimationFrame(() => {
  targetPage.style.opacity = '1';        // 0.25s 淡入
});
```

`opacity:0` 在 `active` 之前设，页面从未以空状态可见过。内容就绪后 0.25s 淡入。

时间线闪动修完之后，问了自己：功能够多了吗？还能加什么？列了个清单，挑出七项，一口气全做了。

### ⌨️ 快捷指令

输入框打 `/` 开头就是指令。一张映射表，匹配到就替换 prompt：

```javascript
var QUICK_COMMANDS = {
  '/总结': '请用2-3句话总结我们最近的聊天内容。',
  '/翻译': '请把下面这句话翻译成英文：',
  '/笑话': '给我讲一个短笑话。',
  '/夸我': '请用温暖的话夸夸我，2-3句就好。',
  '/晚安': '跟我说晚安，温暖一点。',
  '/早安': '跟我说早安，元气一点。',
};
```

在 `sendMsg` 开头加了一行 `if (msgText[0] === '/' && QUICK_COMMANDS[msgText])`——三十行搞定，用户不用记 prompt，打字就行。

### ⭐ 消息收藏

新数组 `starredMessages` 存收藏的消息 ID。长按消息的删除弹窗里多了个 ⭐ 按钮——点了收藏，再点取消。

AI 看到这段前缀就知道上下文，回复能精准接话。不像之前那样——用户说"吃了"，AI 不知道在回哪句。

原来的搜索只高亮第一个匹配结果。改成了遍历 `messages` 数组，收集所有匹配消息的 DOM 元素，搜索栏显示 `◀ 3/12 ▶`，点箭头翻页。每次翻页自动 `scrollIntoView` 到对应消息，高亮跟随。

如果部分匹配消息还没渲染（懒加载模式下），先 `renderShowAll = true` 展开全部，150ms 后再搜。

### 📝 摘要导出

设置页加了"📝 导出对话摘要"按钮。调一次 `callDeepSeek(summaryPrompt)` 非流式，结果 `saveFileToDevice` 存成 `.txt`。和所有导出一样走 `_doc/` 写入 + 分享面板，APK/浏览器自适应。

个人页"📊 年度报告"入口。弹窗显示当前房间数据：总消息数（用户/AI 分别多少）、第一天聊到什么时候、最晚聊到几点、送出礼物次数和暴击次数、红包收发次数。

纯数据聚合，不需要 AI。按房间隔离——切到"日常"和"心事"各看各的。

### 🏷️ 话题标签

每 10 分钟自动触发一次：取最近 30 条对话 → 发 `callDeepSeek` 让它返回 JSON 数组（如 `["学习","美食","音乐"]`）→ 标签计数累加到 `topicTags`。

## 四十二、十五个小游戏：聊天框里玩

快捷指令只解决了"让 AI 做某件事"，但没解决"跟 AI 一起玩"。

于是就加了游戏系统。核心思路：全部用 prompt 驱动，不写额外状态机（AI 本身就能记上下文）。在加号菜单里放了一个 🎮 小游戏入口。

### 游戏面板

半屏浮层，15 个游戏按五类分组：

| 分类 | 游戏 |
|------|------|
| 对抗 | 猜数字、石头剪刀布、井字棋 |
| 合作 | 一起编故事、密室逃脱 |
| 表演 | 冷笑话大赛、角色扮演、说唱 Battle |
| 知识 | 成语接龙、诗词接龙、飞花令、猜谜语、冷知识问答 |
| 策略 | 21 点、猜拳赌博 |

点一个 → 自动填充指令 → 发送 → AI 进入游戏模式。底部出现绿色游戏条，显示当前游戏名 + "结束"按钮。输入 `/endgame` 也能退出。

### 游戏 prompt 设计的坑

**猜数字**第一版是"你在心里想一个数，我来猜"——让用户想数、AI 问问题。用户说这不对，应该是 AI 出题。改了。

**石头剪刀布**第一版是"我出了…石头！"——AI 先亮牌。问题是 AI 亮牌之后用户看到才出，AI 没法真的"同时出"。改成了用户先出，AI 再回应——虽然 AI 理论上可以根据用户的选择"作弊"（因为用户先亮了），但在聊天游戏里这不算问题，因为 AI 不会真的赢——它会根据对话氛围选择输赢。

**21 点**第一版让 AI "随机生成"发牌。但 AI 不能真的随机——它只是编一个数字。如果用户较真记牌，AI 会前后矛盾。改成了固定起始牌（7 和 5），后续要牌由 AI 根据游戏逻辑合理编。

**所有 prompt**都过了一遍"你""我"指代——确保"你"=用户、"我"=AI，不搞反。

### 怎么接入的

游戏指令也是 `/` 前缀，和快捷指令共用逻辑：`/guess` `/rps` `/ttt` `/story` 等等。`sendMsg` 里一行 `else if (GAME_PROMPTS[msgText.substring(1)])` 就全部接入了。

十五个 prompt 存在 `GAME_PROMPTS` 对象里，游戏元数据（名称、分类、描述）在 `GAMES` 数组里。加新游戏就是在两个结构里各加一条。

### 顺手修的小东西

**游戏面板 ✕ 关闭**：原来只能在底部滑到最后点"关闭"，加了顶部 ✕，点完即关。

**游戏条挡输入框**：底部绿色游戏条在 `bottom:60px`，手机端刚好遮住输入区域。移到 `110px`，和输入框错开。

**⬆⬇ 浮动滚动按钮**：聊天消息多了之后，想快速回顶部或回底部很麻烦。加了两个半透明圆按钮，滚动时出现、3 秒不动自动消失。⬇ 按钮之前调用 `scrollChatToBottom()`——这个函数有距离判断（离底部 < 400px 才滚），导致离底部远时按钮失效。改成 `scrollTop = scrollHeight` 直接强制滚到底，不判断距离。桌面端加上了 `mouseenter` 触发，鼠标滑入消息区也显示按钮。

**长按按钮挤**：加了收藏和引用后，长按弹窗有三个按钮（↩ ⭐ 删除）。窄屏上三个按钮挤在一起。加了 `gap:6px`、缩小 `padding` 和 `font-size`，三个按钮不再贴脸。

**年度报告弹窗**：原来用 `alert()` 弹系统对话框——丑，且不能复制内容。改成自定义卡片弹窗，和收藏弹窗一样的风格：深色遮罩 + 白色圆角卡片 + 关闭按钮。数据按房间隔离展示，标注"以上为「日常」房间数据"。

**话题标签质量**：原来 prompt 只说"提取2-5个话题标签"，AI 偶尔返回英文词或单个字。改成"必须用简体中文（2-4个字），不要英文、不要单字、不要数字"，并给了具体例子。提取质量明显提升。

**CSS display 冲突**：滚动按钮的 inline style 里同时写了 `display:none` 和 `display:flex`——后者覆盖前者，导致按钮始终可见但内容为空（一个没有 flex-direction 的 flex 容器）。拆开：初始 `display:none`，JS 显示时设 `display:flex`。

## 四十三、字卡系统：没有 API 也能聊

这个应用从头到尾都依赖 DeepSeek API。不填 Key 的时候，聊天是空气泡、点写日记弹"请先设置 API Key"、朋友圈自动发帖和主动消息直接静默跳过、红包礼物也全被 `!apiKey` 门槛挡死。

用户提了一个需求：能不能做一套"字卡"——每个智能体的每个房间有一套自己的话术卡，没有 API 的时候聊天、日记、朋友圈全部用字卡兜底。于是有了这一章。

### 字卡格式：；触发词；回复

一开始想的是"纯随机抽取"——所有话术丢一个池子里，用户发啥都闭眼抽。用户一句话点醒：纯随机聊几句就露馅，"吃了吗"对上"我好难过"显得像弱智。

改成**关键词优先 + 随机兜底**。每张卡两个字段：

```
；触发词；回复内容
```

- `；晚安；晚安~ 做个好梦` —— 用户消息里出现"晚安"就优先抽这类卡
- `；；今天天气不错呢` —— 没有触发词的"通用卡"，只参与随机兜底

两种格式都支持，批量粘贴一行一张：

```
；晚安；晚安~ 做个好梦，早点休息呀 🌙
；；今天天气不错呢
；在干嘛；在想你呢~
；；吃饭了没，别饿着
```

### 一键识别

字卡管理面板里有一个多行文本框，粘贴一大段 → 点"批量导入" → 自动拆成一张张卡入库。解析器只有两个函数，核心逻辑十几行：

```javascript
function parseWordCardLine(line) {
  var trimmed = line.trim();
  if (!trimmed || trimmed[0] !== '；') return null;   // 不以；开头跳过
  var parts = trimmed.slice(1).split('；');
  if (parts.length < 2) return null;                   // 至少"触发词+回复"
  var trigger = parts[0].trim();
  var reply = parts.slice(1).join('；').trim();        // 回复里再带；也能正确合并
  if (!reply) return null;
  return { trigger: trigger, reply: reply };
}
```

三个边界想清楚了：
- **回复内容里自己带 `；`**？用 `slice(1).join('；')` 合并，只拆开头的分号。
- **空触发词的通用卡**（`；；xxx`）？`parts[0]` 是空串，识别成通用卡。
- **空行、注释行、不以分号开头的行**？直接跳过，不影响其他行。

### 存储：每房间独立

字卡和消息、日记同级，都是**每房间一份**，存进 IndexedDB 的 room blob。

```javascript
let wordCards = []; // [{ id, trigger, reply }]
```

麻烦的是五个桩点——每加一个房间级数据就要在五个地方各补一行：`saveRoomData`（存）、`loadData`（读）、`switchRoom`（切房间清空）、`switchAgent`（切智能体清空）、`clearAll`（清聊天）。这五处是纯样板，漏一处就是"切房间字卡串台"。

### 匹配逻辑

```javascript
function pickWordCard(userText) {
  if (!wordCards.length) return null;
  var lt = (userText || '').toLowerCase();
  var matches = wordCards.filter(function(c) {
    return c.trigger && lt.indexOf(c.trigger.toLowerCase()) !== -1;  // 子串匹配
  });
  if (matches.length > 0) return matches[Math.floor(Math.random() * matches.length)].reply;
  return wordCards[Math.floor(Math.random() * wordCards.length)].reply;
}
```

第一步把所有"触发词出现在用户消息里"的卡筛出来，随机抽一张；一条都匹配不上，就从全池随机兜底。注意兜底**包含有触发词的卡**——这是刻意为之。触发词只是"优先"，不是"排他"，否则卡池抽起来太死板。

### 六个接入点

字卡要兜底的地方不止聊天。把所有依赖 API 的入口梳理了一遍，一共六个。

**① 聊天**：`sendMsg` 里无 API 且有字卡时，跳过 API 调用，600-1400ms 打字延迟后直接贴字卡回复。这个延迟不能省——秒回不像真人。

**② 主动消息**：早晚问候、久未联系，原来 `checkProactiveMessage` 第一行就 `if (!apiKey) return`。加字卡分支，无 API 时从字卡池抽一条当主动消息。

**③ 日记**：`doWriteDiary` 原来无 API 直接弹 toast 拒绝。离线分支改成：随机抽一张字卡当"心情锚点" + 把最近几条用户消息拼成"聊了聊：xxx"。虽然比不上 AI 写的，但至少能写、像那么回事。

**④ 朋友圈发帖**：`autoPostMoment` 无 API 时从字卡池随机抽一句发出去。

**⑤ 朋友圈互动**：AI 给用户点赞本来就是纯本地操作。评论和回复原来走 API，无 API 时从字卡池抽。这里有个坑，后面讲。

**⑥ 红包**：AI 主动发红包原来无 API 直接 return，改成用本地 fallback 祝福语（"一点小心意 💕"）直接发。AI 领红包是纯本地操作——标记已领 + 本地感谢语池——却挂了个没意义的 `!apiKey` 门槛，一起去了。

### 管理面板

Plus 菜单和"我"页面各加一个"📇 字卡管理"入口。半屏浮层，从上到下：统计行（"共 X 张卡，其中 Y 张有触发词"）→ 批量导入文本框 → 卡列表 → 清空/关闭按钮。

每张卡一行，显示触发词（绿色）和回复内容，无触发词的标 `[无触发词·通用卡]`，右边 ✕ 单删。切页自动关面板（在 `switchPage` 的 overlay 关闭列表里补了一行）。

### 这次踩的坑（Bug 细节全流程）

**空气泡**：第一版聊天接入只写了 `if (!apiKey && wordCards.length > 0)`。如果用户既没填 Key 又一张卡都没导入，流程会掉进 `callDeepSeek`——它第一行 `if (!apiKey) return null`，返回 null 后 `sendMsg` 的 `.then` 里 `if (fullReply)` 判断跳过，AI 占位气泡就永远空着。这是**原有的隐藏 bug**，字卡系统让它现了形。修法：无 API 时不管有没有卡都走本地兜底——有卡抽卡，没卡 `getOfflineReply('default')`。

**评论空请求**：`autoInteractMoments` 无 API 无字卡时，会一路走到 `fetch`——发一个必然 401 的请求再静默失败。加 `if (!apiKey) return;`。

**主动消息不发**：`checkProactiveMessage` 的 `!apiKey` 门槛挡在函数开头，离线永远不发。把它挪到 API 分支内部，前面加字卡分支。

**红包领不了**：`maybeAIClaimRedPacket` 明明是纯本地（标记 `opened` + 本地感谢语），却被 `if (!apiKey) return` 挡住。去掉门槛。

**礼物不回复**：用户实测发现的。离线送礼物，原设计是 `_pendingGifts` 队列等"下次发消息"才确认——用户送完礼物 AI 没反应。改成离线时**立即**用字卡回复"谢谢你的 🌹 玫瑰！🥰"。还有个连锁坑：立即回复后如果不把这条礼物从 `_pendingGifts` 里清掉，用户下次发消息还会再收到一次感谢——**重复感谢**，要 `filter` 掉。

**手写信不写日记**：手写信（💌）的日记触发藏在 `if (!isSending && apiKey)` 门里，离线送手写信根本不触发。挪到 else 分支，离线也调 `doWriteDiary`（它自己会走字卡离线路径）。

**无意义的 API 门槛**：定时消息用的是用户自己填的文本，根本不调 API，却挂着 `!apiKey` 门槛——离线定时消息全废。送礼物也是，整个流程是本地逻辑（扣库存、调心情、粒子动画、字卡回复），却被门槛挡在门外。这两个暴露一个共性：**写代码时看到"这个功能要 AI 生成"就下意识加 `!apiKey`，没检查它是不是真的依赖 API。**

### 自检：语法 + 单测

收尾用 Node 跑了两遍验证：
- 用 `new Function()` 解析整个 `<script>`，确认没写坏语法；
- 把解析器和匹配逻辑抽出来跑单测：4 行混合格式解析出 4 张卡、回复带 `；` 正确合并、无效行返回 null、关键词命中 200 次全抽对卡、无匹配时全池随机。

### 小结

字卡系统一共约 400 行。最大的收获不是代码，是意识到**无 API 兜底最怕"静默失败"**——空气泡、空请求、不回复，全是"看起来没坏但什么都没发生"。每接入一个功能都要问一句：没有 API 的时候，这个入口是"有可见的兜底"，还是"悄悄什么都没做"？

## 四十四、字卡二期：每行一个 + JSON 导入 + 自动去重

四十三章把字卡系统跑通了，用户上手用了一天，提了三个体验上的需求：

1. **输入别打 `；`**——每行开头那个分号太反人类，能不能每行直接写？
2. **支持 JSON 文件导入**——别人整理好的字卡可能是一份 JSON，想一键塞进来。
3. **自动去重**——导来导去怕重复，能不能重复的自动跳过？

三个都是"用户怎么输更快、别让我重复"的问题。这章挨个做。

### 格式：每行一个

旧格式每行以 `；` 开头：

```
；晚安；晚安~ 做个好梦
；；今天天气不错呢
```

用户觉得开头那个 `；` 是多余的动作。新格式更自然，**有关键词就用 `；` 隔开，没有就直接写句子**：

```
晚安~ 做个好梦          ← 没分号 = 通用卡
在干嘛；在想你呢~      ← 有分号 = 关键词；句子
今天天气不错呢
吃了吗；别饿着自己 🍚
```

关键是不能把旧数据搞坏。解析器改成"两种情况都认"：

```javascript
function parseWordCardLine(line) {
  var trimmed = line.trim();
  if (!trimmed) return null;
  if (trimmed[0] === '；') {
    // 旧格式：；trigger；reply / ；；reply（老数据兼容）
    var parts = trimmed.slice(1).split('；');
    ...
  }
  var idx = trimmed.indexOf('；');
  if (idx === -1) {
    return { trigger: '', reply: trimmed };   // 纯句子 = 通用卡
  }
  return { trigger: trimmed.slice(0, idx).trim(), reply: trimmed.slice(idx + 1).trim() };
}
```

行以 `；` 开头走旧解析，否则看行里有没有 `；`——有就拆关键词和句子，没有就整行当通用卡。**新老格式并存，导入面板的提示文案也改成了新格式。**

### JSON 一键导入

面板里加了个"📄 JSON"按钮，选文件 → 读 → 解析 → 入库。为了对用户的数据宽容，支持三种结构：

```json
// ① 对象数组（最常见）
[ { "trigger": "晚安", "reply": "晚安~" }, ... ]

// ② 纯字符串数组（全是通用卡）
[ "句子1", "句子2", ... ]

// ③ 包裹字段
{ "cards": [ ... ] }
```

字段名也做了兼容——`trigger` 和 `keyword` 都认，`reply`、`text`、`content` 都认：

```javascript
trigger = item.trigger || item.keyword || '';
reply   = item.reply || item.text || item.content || '';
```

不认识结构的 JSON 给个明确报错，不静默吞掉；空回复的条目直接丢弃。

### 自动去重（用户点名要的）

去重规则：**触发词 + 回复完全相同才算重复**，导入时对比现有池子，重复的跳过，提示"导入 X 张，跳过 Y 张重复"。

```javascript
function dedupeWordCards(newCards, existing) {
  var seen = {};
  for (var i = 0; i < existing.length; i++) {
    seen[existing[i].trigger + '|' + existing[i].reply] = true;
  }
  // 新的卡，key 重复就跳过，否则收下并记入 seen
}
```

这里有个细节：key 用 `触发词|回复` 拼接。如果直接拼成 `触发词+回复`，`{"晚安","晚安~"}` 和 `{"晚安 安","~"}` 这类会撞在一起误判成重复——虽然概率低，但用分隔符 `|` 兜住。**注意这个分隔符选的是普通可见字符，不能选控制字符，原因见下面的 Bug 记录。**

去重不只对批量导入生效：
- **批内重复**也去（`seen` 会累加本次已接受的卡）；
- **单条新增**同样走去重——手输一条和现有重复的，直接提示"这张卡已存在"。

### 单条新增

原来只能批量粘贴，想只加一张也得走文本框。面板顶部加了一行：触发词输入框 + 回复输入框 + "添加"按钮，点一下入库。

### Bug 细节全流程

**NUL 字节事故**：去重函数一开始用 `'\u0000'`（空字符）当 key 分隔符——它在 JS 里完全合法，能保证拼接不歧义。但问题是这个字卡写入 `phone.html` 文件时，变成了**真正的 0x00 字节**。编辑器把它当二进制，`grep` 直接说"binary file matches"，整个文件被工具链当成了非文本。最后改用可见的 `|` 分隔符，文件恢复正常。教训：**要写进磁盘文件的代码，别用控制字符**，哪怕 JS 引擎能跑，工具链会翻脸。

**JSON 字段兼容补丁**：第一版只认 `trigger` / `reply`，用户拿来的 JSON 里字段叫 `keyword` / `text`，导入全空。补上别名后正常。教训：**对用户数据宽容，多认几个字段名比要求对方按你的格式来靠谱。**

**去重粒度**：一开始想"回复一样就算重复"——太激进，两条内容相近但不同的卡会被误杀。改成"触发词+回复都相同"才判定重复，误杀率降到接近零。

### 验证

解析器、去重、JSON 解析各用 Node 单测过一遍：5 种输入格式解析正确、批内去重（两条相同导入 1 条）、跨池去重（跳过已在池里的）、错误 JSON 和错误结构给出明确错误。跑完 `new Function()` 全量语法检查通过。

### 小结

二期一共约 60 行。三个需求全是"输入体验"的活——**格式更自然、数据更宽容、重复不用管**。功能本身不复杂，复杂的是兼容：老数据不能坏、用户的 JSON 字段名不能假设、重复判定不能太松也不能太严。做工具类功能，跟用户较劲不如对自己宽松。
