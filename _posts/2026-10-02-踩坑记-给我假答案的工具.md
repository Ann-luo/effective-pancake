## 0. 为什么要单独写这篇

今天做的事本身不算难——接几个 API、渲染个视频。

**但中间有七八次，我被工具给出的"错误信息"带偏了方向**，每次都要花十几分钟才绕回来。

这些坑有个共同点：**报错信息是真的，但它指向的原因跟真实原因没关系。**

比如"网络连不上"，其实网络好得很，是工具自己有问题。

所以我单独记一篇，**下次再看到这些报错，能立刻反应过来。**

## 1. 最阴的坑：PowerShell 说"全网都连不上"

### 现象

有一次我需要确认几个网站到底能不能访问——因为要判断某些方案是否可行，**这个结论会影响后面的技术选型**。

于是我写了段 PowerShell：

```powershell
$targets = @(
  @{n='Google';  u='https://generativelanguage.googleapis.com/'},
  @{n='GitHub';  u='https://github.com/'},
  @{n='Agnes';   u='https://apihub.agnes-ai.com/v1/models'}
)
foreach($t in $targets){
  try{
    $r = Invoke-WebRequest $t.u -UseBasicParsing -TimeoutSec 10
    "OK   $($t.n) → HTTP $($r.StatusCode)"
  }catch{
    "FAIL $($t.n) → $($_.Exception.Message)"
  }
}
```

**结果：全军覆没。**

```
FAIL Google → The SSL connection could not be established
FAIL GitHub → The SSL connection could not be established
FAIL Agnes  → The SSL connection could not be established
```

**当时我的判断是：这机器访问不了 Google（被墙），可能也上不了网。**

差一点就基于这个结论改方案了——比如放弃用 Gemini、改用国内服务。

### 真实原因

**PowerShell 自己的 TLS 有问题，跟网络一点关系没有。**

我换 Node 试了同一批地址，**同一台机器、同一时刻**：

```javascript
for (const [n, u] of targets) {
  try {
    const r = await fetch(u);
    console.log('OK  ', n, 'HTTP', r.status);
  } catch (e) {
    console.log('FAIL', n, (e.cause && e.cause.code) || e.message);
  }
}
```

结果：

```
OK   Agnes 国际站            HTTP 401   1448ms
OK   Google generativelanguage  HTTP 404    878ms
OK   Google AI Studio       HTTP 302   1087ms
OK   GitHub                 HTTP 200   1958ms
OK   YouTube                HTTP 200   1013ms
```

**全部通。** Google 那几行是我后来实测的，**完全能访问**。

### 为什么危险

它不报"PowerShell 有问题"，它报"SSL connection could not be established"——**看起来就像是网络层的问题**。

而且我这里还叠了个巧合：这台机器的注册表里有代理残留（`127.0.0.1:7897`），所以更容易让人以为是代理没开导致的连不上。

**实际是 PowerShell 5.1 那套 .NET 的 TLS 栈跟这些站点的握手有问题。**

### 怎么办

**测网络连通性，一律用 Node，别用 PowerShell 的 `Invoke-WebRequest` / `Invoke-RestMethod`。**

```powershell
# ✅ 这样测才准
node -e "fetch('https://github.com').then(r=>console.log(r.status)).catch(e=>console.log('FAIL',e.message))"
```

**判断标准：如果 PowerShell 说连不上，但 pip / npm / node 都正常，那问题在 PowerShell。**

> 💡 顺带一提：同一天我在 `Invoke-WebRequest` 上下载文件也失败了（"Authentication failed"），换 Node 的 `fetch` 写文件立刻成功。**这台机器上 PowerShell 的 HTTPS 就是不可信。**

## 2. 沙箱坑一：程序不能"看"另一个程序的输出

### 现象

我想给一个长时间运行的任务加日志包装——写个脚本启动子进程，把输出同时打到屏幕和文件。

```javascript
const p = spawn(process.execPath, ['agnes.js', ...args], {
  cwd: __dirname,
  stdio: ['ignore', 'pipe', 'pipe'],    // ← 罪魁祸首
});
p.stdout.on('data', (buf) => {
  process.stdout.write(buf);
  fs.appendFileSync(LOG, buf);
});
```

报错：

```
Error: spawn EPERM
    at ChildProcess.spawn (node:internal/child_process:421:22)
  errno: -4048,
  code: 'EPERM',
  syscall: 'spawn'
```

**`EPERM` 是"权限不足"，但这里跟文件权限没关系。**

### 真实原因

**沙箱禁止程序通过命名管道（pipe）捕获另一个程序的输出。**

`stdio: 'pipe'` 在底层用的是匿名管道，在这个受限环境里被拒了。

**注意：`stdio: 'inherit'`（直接继承）和 `'ignore'` 是允许的。**

### 怎么办

**别写包装脚本。** 直接跑命令，用 **shell 自己的重定向**：

```powershell
node agnes.js video "提示词" *> video-run.log
```

`*>` 是 PowerShell 的"所有输出重定向"，**这是 shell 层的行为，不受沙箱限制**。

想看进度就随时读那个日志文件：

```powershell
Get-Content video-run.log -Tail 10
```

> ⚠️ 关键点：**这个 EPERM 是既定的沙箱边界，不要反复重试**。看到就换写法。
> 我当时试了两次，浪费了时间。

## 3. 沙箱坑二：写了文件，但保存不下来

### 现象

一段跑了 18 分钟的任务，最后一步要把结果存到某个目录：

```
[生视频] ✅ 任务完成
[错误] EPERM: operation not permitted, open 'D:\...\视频\video-20261002-152101.mp4'
```

**生成成功了，但存不下来。** 18 分钟眼看白费。

### 原因

沙箱的写权限**是按目录授权的**。

我之前为了把生成的图片存到 `图片\` 目录，申请了一次授权——**但那只覆盖了 `图片\` 目录**。后来新增的 `视频\` 目录**从来没被授权过**。

**教训：每次写到新目录，都可能需要单独授权。**

### 怎么救回来的

**这次运气好**——那个服务的视频 URL **不会过期**。

我用任务 ID 重新查了一次接口：

```javascript
const r = await fetch(
  `https://apihub.agnes-ai.com/agnesapi?video_id=task_wCw8EIa5...&model_name=agnes-video-2.5-flash`,
  { headers: { Authorization: `Bearer ${KEY}` } }
);
// {"status":"completed","url":"https://platform-outputs.agnes-ai.space/videos/....mp4"}
```

**URL 还在。** 直接下载，3.18 MB 的视频到手。

### 改进

改脚本：**生成成功后，第一时间把 URL 写进文件**，再去尝试下载。

```javascript
if (url) {
  console.log(`[生视频] 视频就绪，URL=${url}`);
  try {
    fs.writeFileSync(path.join(__dirname, 'last-video-url.txt'), url + '\n');
  } catch {}

  try {
    // 下载...
  } catch (e) {
    console.error(`[生视频] ⚠️ 下载失败: ${e.message}`);
    console.error(`[生视频] URL 已保存在 last-video-url.txt，权限修好后可重新下载`);
    throw new Error(`视频已生成但保存失败。URL=${url}`);
  }
}
```

> 💡 **通用经验：凡是"生成成本很高"的东西，成功的第一时间就把标识（URL / ID）落盘。** 别等最后一步。

## 4. 接口坑：注册成功也可能是"假"成功

### 现象

我在探测一个服务的注册接口，**用了一个明显是假的邮箱做测试**：

```
zz-domain-probe-001@outlook.com
```

**结果它返回了成功**：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "api_key": {
      "key": "as_sk_22a25f0a51613fb7b547a4a8a8e075f5",   ← 真的给了 key
      ...
    }
  }
}
```

### 这意味着什么

**1. 我在人家系统里创建了一个垃圾账号。**

探测接口是我的测试手段，但这个接口**是真的建号的**——而且连邮箱真实性都不校验（只发个密码邮件过去，收不到也无所谓）。

**2. 我意外验证了一件有用的事**：用户之前用 `@outlook.com` 在**网页上**注册被拒（报"域名不允许"），但**API 端点对同一个域名是放行的**。

所以那个"域名不允许"报错**只存在于网页前端**，走 API 就能绕过去。——这也算因祸得福：**我用一个不该用的测试，撞出了用户那个问题的解法。**

### 教训

**探测"会写数据"的接口之前，先想清楚它会不会真的产生副作用。**

- 只读接口（GET / 查询）→ 随便测
- **写接口（注册 / 创建 / 提交）→ 先查文档，或者用会被服务端拒绝的假数据测**

我这次运气好，那个假账号没什么危害（无非是数据库里多一行）。**但如果是个会发短信、会扣费的接口呢？**

## 5. ffmpeg 音频：四个错误连环套

这块我在另一篇里详细写了，这里只列结论：

| # | 我写的 | 为什么错 | 正确做法 |
|---|---|---|---|
| 1 | `tremolo=f=0.06` | 该滤镜 `f` 最低 0.1Hz | 改用 `aevalsrc` 振幅调制 |
| 2 | `sin(2π(f₀−k·t)·t)` | 频率不是线性的，相位要积分 | `sin(2π(f₀t − kt²/2))` |
| 3 | `-i "音源[标签]"` | `[标签]` 是 filtergraph 语法 | 标签只写在 `-filter_complex` 里 |
| 4 | 音源索引从 0 开始 | **第一个 `-i` 是视频文件，占了 index 0** | 音源从 **1** 开始 |

**这四个是连着踩的**——修好一个立刻撞下一个。加起来花了大概四十分钟。

> 💡 教训：**ffmpeg 的报错信息通常很准**（"Value 0.06 out of range [0.1 - 20000]" 直接告诉你范围），
> **但它不会告诉你"你整个思路错了"。** 遇到这类连环报错，**停下来重新想架构，而不是一个个补**。

## 6. 一个"反向"的坑：服务端超时只有 10 秒

### 现象

我试着让一个视觉模型"看"一个视频，直接把视频 URL 给了它：

```javascript
{ type: 'video_url', video_url: { url: 'https://.../Big_Buck_Bunny.webm' } }   // 59 MB
```

等了 **103 秒**后报错：

```
An exception occurred while loading VIDEO data at index 0:
HTTPSConnectionPool(host='...'): Read timed out. (read timeout=10)
```

**`read timeout=10`——服务端自己拉取这个 URL 的超时只有 10 秒。**

59 MB 的视频，10 秒肯定拉不完。

### 怎么办

**别让服务端去拉，自己下载下来再传。**

我改成：先把视频下载到本地 → 读成 base64 → 用 data URI 传给模型。

```javascript
const buf = fs.readFileSync(localFile);
const b64 = buf.toString('base64');
const videoUrl = `data:video/mp4;base64,${b64}`;
```

**效果对比：**

| 方式 | 结果 |
|---|---|
| 直接给 URL（59 MB） | ❌ 103 秒后超时 |
| 直接给 URL（0.99 MB） | ✅ 5.7 秒成功 |
| base64 直传（0.95 MB） | ✅ 10.4 秒成功 |
| base64 直传（5.26 MB） | ❌ 18.8 秒后 500 错误 |

**摸出来的边界：2 MB 以内最稳，5 MB 以上必挂。**

> 💡 经验：**"服务端帮你拉 URL"这种设计，通常都有很短的超时和大小限制。**
> 自己能下载的东西，**自己下好再传**，可控得多。

## 7. 总结：一张表

| 报错 / 现象 | 看起来像 | 实际是 | 怎么办 |
|---|---|---|---|
| `SSL connection could not be established` | 网络不通 / 被墙 | **PowerShell 自己的 TLS 问题** | 换 `node -e "fetch(...)"` 测 |
| `spawn EPERM` | 权限不足 | **沙箱禁止 pipe 捕获子进程输出** | 用 shell 重定向 `*>`，别写包装脚本 |
| `EPERM open 'D:\...\文件'` | 文件被占用 | **沙箱按目录授权，新目录没授权** | 申请该目录权限；重要产物先生成 URL/ID 落盘 |
| 注册接口返回成功（假邮箱） | 测试通过 | **它真的建号了** | 写类接口别用假数据随便测 |
| `Value 0.06 out of range [0.1 - 20000]` | 参数写错 | 确实写错，但**思路整体不对** | 停下来重新想，别一个个补 |
| `Read timed out (read timeout=10)` | 网络慢 | **服务端拉取超时只有 10 秒** | 自己下载后 base64 直传 |

## 8. 最后说两句

今天最大的收获**不是做出了什么，而是学会怀疑工具的报告**。

那句"SSL connection could not be established"，如果我信了，会得出"这机器上不了 Google"的结论——**完全错误，而且会误导后面所有决策。**

**所以养成一个习惯：**

> **当工具报错说"做不到"时，换个工具再试一次。**

- PowerShell 说连不上 → 用 Node 试
- 一个包管理器装不上 → 换另一个
- 一个接口报错 → 用 curl 手打一遍看原始响应

**交叉验证的成本很低（就一条命令），但能避免在错误的方向上走很远。**
