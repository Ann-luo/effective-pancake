## 一、先说结论（懒人版）

1. **心潮读/写记忆库那条腿，从上线起 100% 失败**：`daytime_emergence_failed` 6 次、`ombre_read_failed` 5 次、
   `ombre_write_failed` 5 次、`context_ombre_read_failed` 3 次 —— **成功 0 次**。
2. **根因在一行代码**：记忆库的 MCP 是「无会话」模式（源码里 `stateless_http=True`，作者**故意**这么设的），
   它的 `initialize` **按设计不返回** session id；而心潮客户端里有一行
   `if (!this.sessionId) throw new Error('… did not return a session id')` —— 每次都在这里炸。
3. **补丁打在客户端，不打服务端**：改服务端会**直接弄坏另一个自写的程序**（它不握手、直接发请求，
   服务端一旦要求会话，它当场 400）。
4. **改 4 处，围绕一个新加的 `this.initialized` 标记**。修完才发现：**心潮有 5 处调用点都靠这条腿** ——
   我以为只修一个功能，一查是 5 个。
5. **记忆星图也是被同一个 bug 卡死的**（它优先走一条服务端不存在的路由，实测 404，退回走 MCP），
   补丁后实测 **122 颗星**；而且**不用给服务端打那个 `pulse` 补丁** —— 源码里没有截断。

## 二、现象：它一次都没成功过

心潮是 2026-10-10 上线的一个自托管的「AI 动态心智状态层」。
它做的事挺多：十二维驱动力、念头池、疲惫、睡眠、梦境余韵。
而它要"像真的记得住事"，就得能**读写记忆库** —— 读记忆当素材，写梦回去。

上线第二天，用户问了一句"今天怎么样"。我顺手去数了一遍它的失败计数，然后愣住了：

```text
daytime_emergence_failed    6      ← 白天涌现（主动推念头到手机），全灭
ombre_read_failed           5
ombre_write_failed          5
context_ombre_read_failed   3
成功                             0
```

**失败 19 次，成功 0 次。**

它不报错、不崩溃、不影响别的功能。日志是安静的。
所以如果不去数这些计数器，它能一直这么"跑"下去 —— 表面 healthy，实际那条腿是空的。

> 这里有个值得记下来的点：**"服务 healthy"和"功能在工作"是两件事。**
> 容器状态会告诉你进程活着，不会告诉你它有没有在做该做的事。

## 三、根因：记忆库是「无会话」模式，而客户端硬要一个会话

去看心潮的日志，真正的错误信息是：

```text
Error: … did not return a session id
```

（前半段是记忆库的名字，这里不重要。）

顺着这条错误去读两边的源码，事情就很清楚了 —— **两边各自都没错**：

| 谁 | 做了什么 | 有没有错 |
|---|---|---|
| **记忆库（服务端）** | MCP 跑在「无会话」模式（源码里 `stateless_http=True`）。`initialize` **按设计不返回** `Mcp-Session-Id`，每个请求各自独立。它自己的日志里写 `Terminating session: None` | ❌ 没错。作者是**故意**这么设的 —— 为了兼容那些会**吞掉 `tools/list` 异常**的客户端 |
| **心潮（客户端）** | `initialize()` 之后**硬要求**必须有 session id，没有就抛错 | ❌ 也不该算"错"，但**它假设错了** |

所以这是**两个都合理的假设撞在一起**：一边按自己的设计不给会话，一边按自己的假设必须要会话。

我实测确认过服务端那条路是好的：

```text
不带 session 直接发 tools/list  → 200，18 个工具
不带 session 直接调 breath      → 200，能拿回记忆正文
```

**服务端一点问题都没有。** 它本来就支持"你随便来，我不记你是谁"。

## 四、改了什么：4 处改动

补丁打在 `src/ombre-client.js`（心潮侧）。**4 处，全都围绕新增的一个 `this.initialized` 标记：**

| 位置 | 改动 |
|---|---|
| 构造函数 | 新增 `this.initialized = false;` |
| `initialize()` 开头 | `if (this.sessionId)` → `if (this.sessionId \|\| this.initialized)` |
| `initialize()` 中间 | **删掉**那行 `if (!this.sessionId) throw new Error('… did not return a session id');` → 改成 `this.initialized = true;` |
| `call()` 重试那行 | `this.sessionId = null;` 后面补 `this.initialized = false;`（不然重试不会真的重握手） |

第 4 处最容易漏，也最值得说：

```js
// call() 里重试的那段（改后）
this.sessionId = null;
this.initialized = false;   // ← 补上这行，重试才会真的重新握手
```

只把抛错那行删掉、不补这一处的话，**逻辑上会"看起来能跑"**：
第一次握手被标记成已完成，之后网络抖动触发重试时，`initialize()` 会因为 `this.initialized` 已经是 `true` 而**直接跳过重握手** ——
于是它带着一个失效的连接继续跑，症状跟没修一样，只是更难查。

改完**必须重建镜像**：

```bash
docker compose up -d --build --no-deps xinchao
```

> ⚠️ **不能只 `restart`，也不能只 `--force-recreate`。** 心潮的源码是 `COPY` 进镜像的，不是挂载的 ——
> 不 `--build` 的话容器里跑的还是旧代码。（这个坑前一天打补丁 1 的时候就踩过一次，白测了两轮。）
>
> 另外**重建后要等进程起来**：刚重建完就去打接口会拿到 401，那是启动竞态，不是补丁没生效。

原文件备份在服务器上，工作区也留了一份补丁版的，方便重装时直接放回去。

## 五、我以为只修一个功能，一查是 5 个

补丁打完，我去做自检 —— 想确认"读记忆"这条路通了。然后发现事情比我想的大。

**心潮有 5 处代码在读/写记忆库，全都走 `ombre-client.js` 这一条路：**

| 位置 | 干什么 |
|---|---|
| `server.js:129` | 上下文材料（`recentMaterial`）—— 新窗口开始时给的记忆背景 |
| `server.js:147` | `storeDream` —— 把梦写回记忆库 |
| `server.js:207` | `thoughtMaterial` —— **自主念头** |
| `server.js:259` | `daytimeMaterial` —— **白天涌现**（主动推念头到手机） |
| `server.js:508` | `recentContinuityMaterial` —— **换窗连续性** |

也就是说：**这 5 个功能从上线起全都是死的，而它们各自看起来都只是"今天没什么可说的"。**

- 上下文材料没了 → 新窗口开起来"想不太起来之前的事"，像是它记性差
- 自主念头没了 → 念头池不涨，像是"它今天比较安静"
- 白天涌现没了 → 手机一天没响，像是"今天没什么好推的"（其实那 6 次失败全在这）
- 换窗连续性没了 → 换窗口之后接不上话，像是"上下文丢了"
- `storeDream` 没了 → 梦写不进记忆

**没有一个症状会指向"客户端少读了一个 session id"。** 这就是它能活一整天的原因。

## 六、记忆星图也是被同一个 bug 卡死的

还有个更意外的：**网页上那张「记忆星图」一直空着，根因是同一个。**

星图取数据有两条路：

```text
第一条路（首选）：请求记忆库的 /api/bucket-map
                  → 实测 404，那条路由在我们这个版本里根本不存在

第二条路（退回）：调 MCP 的 pulse 工具，然后解析返回的文本

但 pulse 也是 MCP 调用 —— 以前照样撞那个 session id 报错
                  → 于是星图一直是空的
```

**我一度以为要改服务端源码加那条路由。** 补丁打完之后再看：

```text
GET /v1/dashboard/memory-map
  第一次  → available=False  reason=building   （触发后台建图）
  25 秒后 → available=True   stars=122  total=122   ✅
```

**122 颗星。** 退回方案是完整的，那条 404 的路由**不用补**。

（顺便：第一次请求返回 `available=False, reason=building` 是**正常的** —— 建图是后台跑的，
第一次请求只是"踢一脚"，得等一会儿再问。别把它当成失败。）

## 七、顺便推翻了一条上游注释的担心

这是今天第二个"我以为要改服务端"的地方。

`ombre-client.js` 里有一段注释，写着退回方案不靠谱：

> 老版没有这条路由时退回 pulse 文本解析（**pulse 是人类摘要，桶多时不含逐桶行，解析出 0 颗星** ——
> 所以结构化路由才是正路）

**这条注释在劝我给服务端打补丁。** 但既然补丁后实测出了 122 颗星，说明它至少对我们这个版本不成立。
于是我去读源码验证，而不是就这么算了：

```python
# 记忆库 pulse 的实现（/app/src/tools/anchor/core.py 里）
"\n".join(normal_lines)
```

**`"\n".join(...)` —— 没有任何 `limit`、没有 `slice`、没有截断。**
它就是老老实实把所有桶每个一行拼起来。

实测也对得上：

```text
头部统计的桶数：122
pulse 实际列出的行数：122     ← 一个不少
```

**结论：不用去给服务端打那个补丁，退回方案是完整的。**

唯一的上限是心潮自己这边渲染用的 `MAX_MAP_STARS = 400` —— 那是**画面上的设计**（星图画不下那么多），
不是数据被丢了。这两件事很容易混，值得分清楚。

## 八、实测（补丁之后）

以下全部是改完之后真跑出来的：

```text
心潮 xinchao_context  → 200
                        返回里出现 [近期连续性] + [bucket_id:xxxxxxxxxxxx] + [梦境余韵]
记忆库侧日志           → 同一个来源四条 POST /mcp 全 200/202
                        （initialize → notification → tools/call）
心潮日志               → 无任何 ombre_*_failed
记忆星图               → stars=122  total=122   ✅
```

**最想单独说的一条：手机会议那条「白天涌现」第一次真正工作了。**

```text
08:55:52   bark_sent        ← 转发层日志
推送优先级 priority=4        ← 会弹窗的那一档（默认 3 只响一声、落进通知栏）
```

这一条以前是 **6 次失败、0 次成功**。现在它真的响在手机上了。

> 这里有个容易忽略的细节：**"送到了"和"弹窗了"不是一回事。**
> 我们这套推送里，`priority` 低于 4 只会静默落进通知栏 ——
> 我们曾经 **12 条消息里 11 条没设优先级**，等于从来没弹过。
> 所以看到 `bark_sent` 只是第一步，还要确认 `priority=4`。

## 九、为什么改客户端、不改服务端

这一节的结论是**用户拍板的**，我来说清为什么这个方向是对的。

修的时候有两条路，看上去"改服务端"更省事（一行配置的事），但实际不行：

| | 改服务端（把「无会话」改成「有会话」） | 改客户端（我们最后做的） |
|---|---|---|
| 影响面 | **会直接弄坏梦境桥** | 只影响心潮自己 |
| 为什么 | 梦境桥是我们自己写的程序，它**不握手、直接 POST `tools/call`**。服务端一旦要求会话，它当场 **400** | 客户端本来就该兼容服务端的模式 |
| 属于谁的代码 | 别人的项目，改了就背一个补丁 | 我们的部署，改动可逆、有备份 |
| 作者的意图 | ⚠️ 无会话是**作者刻意设的**（源码注释写明是为兼容某类客户端） | 客户端的假设本来就错了 |

**所以方向是明确的：让客户端去适应服务端的模式，而不是反过来改服务端去适应客户端。**

> ⚠️ 这条我单独强调：**「无会话」不是故障，是设计。**
> 看到 `did not return a session id` 的第一反应不该是"去把它修成有会话的" ——
> 那会当场弄坏另一个正跑得好好的程序。

## 十、最后

今天真正值钱的一条经验，不是那 4 处改动，而是这个：

**一个 bug 的影响范围，不要靠猜，要靠查。**
我以为是"读记忆坏了"，一查是 5 个功能；我以为"星图是另一个问题"，一查是同一个根因。

而它能藏一天的原因是：**它的症状全都长得像"今天没什么事"** ——
念头不涨、手机不响、星图空着，这些都不会报警。

还有一个更小的教训，在这条链子最末端：
**上游代码里的注释也会过时。** 那条"pulse 会截断"的注释如果照信，我会去给一个不存在的毛病打补丁 ——
而验证它只需要读一眼 `"\n".join(normal_lines)`，加数一下 122 行。
