## 先说结论

这次折腾其实包含两个完全不同的问题：

### 问题一：图片为什么发不进去

不是 Codex 不支持图片，也不是 DeepSeek 不支持图片。

真正的问题是：CC Switch 旧版本生成了一份错误的模型能力表，把 DeepSeek 标成了“纯文本模型”。Codex 看到这份表，就在上传图片前把图片拦住了。

CC Switch 更新后，模型能力表变成：

```json
"input_modalities": ["text", "image"]
```

图片随后就能正常识别。我发了一张纯洋红色测试图，模型回答了 `Pink`。

### 问题二：Codex 为什么突然变英文

中文设置其实已经写进去了：

```toml
[desktop]
localeOverride = "zh-CN"
```

但界面还是英文。

继续往下查才发现，真正的原因在 Codex++：

- Codex 新版使用 `getLayer("72216192")` 读取界面国际化开关。
- Codex++ 1.3.0 却还在修改 `getDynamicConfig("72216192")`。
- 两个接口不是一回事，所以 Codex++ 虽然显示“强制中文界面已开启”，实际上根本没有生效。

最后使用了一个 Codex++ 用户脚本，同时兼容 `getLayer` 和 `getDynamicConfig`，重启之后中文恢复正常。

## 一、我的运行链路到底是谁在工作

这次排查里最容易混的，不是代码，而是三个软件之间的关系。

先画一条最简单的链路：

```text
Codex Desktop
    ↓
CC Switch 本地代理
    ↓
DeepSeek API
```

同时还有 Codex++：

```text
Codex++
    ↓
负责启动 Codex
    ↓
往 Codex 页面里注入界面增强和中文补丁
```

大白话解释：

| 软件 | 它到底干什么 |
|---|---|
| Codex | 主程序，就是平时看到的聊天和代码界面 |
| CC Switch | 模型转换插头，把 Codex 的请求转发给第三方模型 |
| Codex++ | Codex 的启动器和增强工具，负责界面补丁、菜单增强、中文强制等 |

所以当时当前对话的真实关系是：

```text
Codex 界面
   ↓
CC Switch 的 127.0.0.1:15721 代理
   ↓
DeepSeek API
```

Codex++ 不在模型转发链路上，但它负责启动 Codex，并在页面运行时做修改。

## 二、图片问题是怎么查出来的

### 1. 现象

给 Codex 上传图片时，界面提示：

```text
当前模型不支持图片
```

但用户明确知道，DeepSeek 是支持图片识别的。

这时不能直接说“模型不支持”，因为提示来源可能有三层：

1. Codex 自己判断不支持。
2. CC Switch 告诉 Codex 不支持。
3. 请求根本没发到 DeepSeek，就被中间层替换了。

---

### 2. 第一步：看 Codex 当前使用哪个模型

配置文件里能看到：

```toml
model_provider = "custom"
model = "deepseek-v4-flash"
model_catalog_json = "cc-switch-model-catalog.json"
```

大白话：

- 当前不是官方 OpenAI 模型。
- 当前模型叫 `deepseek-v4-flash`。
- 模型能力不是 Codex 猜的，而是从 `cc-switch-model-catalog.json` 读的。

---

### 3. 第二步：看模型能力表

旧版本的模型目录里写着：

```json
"input_modalities": ["text"]
```

这表示：

```text
这个模型只能输入文字
```

Codex 看到这里没有 `image`，自然不会允许图片进入请求。

所以界面提示并不是凭空出现的。

---

### 4. 第三步：确认代理端口是谁在监听

本地代理是：

```text
127.0.0.1:15721
```

用 PowerShell 查端口占用：

```powershell
Get-NetTCPConnection -LocalPort 15721 -State Listen
```

结果对应的是：

```text
cc-switch.exe
```

结论很明确：

```text
模型请求经过 CC Switch
```

---

### 5. 第四步：看 CC Switch 日志

日志里出现了一句非常关键的话：

```text
[Media] Replaced 1 image block(s) with [Unsupported Image]
for text-only provider=..., model=deepseek-v4-flash
```

这句话的意思不是 DeepSeek 拒绝图片，而是：

```text
CC Switch 在请求发出前，
就把图片换成了 [Unsupported Image]。
```

也就是说，图片根本没送到 DeepSeek。

---

### 6. 第五步：更新 CC Switch 后再测试

CC Switch 升级到 3.20.4 后，模型目录变成了：

```json
"input_modalities": ["text", "image"]
```

然后直接向本地代理发送一张纯洋红色测试图，模型回答：

```text
Pink
```

这证明：

- DeepSeek 能识别图片。
- 图片链路是通的。
- 之前的问题确实出在 CC Switch 的模型能力表。

---

## 三、图片问题的小结

这类问题不要看到“不支持”就直接怀疑模型。

正确的排查顺序是：

```text
先看 Codex 当前模型
再查模型能力表
再确认端口属于谁
再查代理日志
最后绕过界面直接测试接口
```

只要中间任何一层把图片过滤了，模型本身都看不到图片。

## 四、顺手说一个安全问题：不要把 API Key 写死在源码里

排查过程中发现，Codex++ 的一个 wrapper 源码里存在明文 API Key。

这里不展示真实内容。只讲风险：

- API Key 等同于账号额度。
- 明文写在 `.cs`、`.json`、`.bat`、`.py` 等文件里，任何能读这个目录的程序都能拿到。
- 如果目录被同步、备份、上传 GitHub，密钥就直接泄露。
- 别人拿到后可能会消耗你的额度。

比较安全的做法：

1. 不要把 Key 写进源码。
2. 放在系统环境变量里。
3. 或者使用密钥管理工具。
4. 如果曾经提交过 GitHub，换掉旧 Key，不要只删文件。

大白话：

```text
文件删掉不等于密钥没泄露，
因为 Git 历史里可能还留着。
```

## 五、Codex 突然变英文的问题

图片问题解决后，新的问题出现了：

```text
Codex 界面突然变英文。
```

设置里明明已经选了中文，还是英文。

---

### 1. 第一反应：检查配置

Codex 配置文件里有：

```toml
[desktop]
localeOverride = "zh-CN"
```

看起来完全正确。

但是界面不改。

这说明：

```text
配置写对了，
不代表运行时真的应用了。
```

---

### 2. 第二步：检查 Codex++ 的强制中文设置

Codex++ 设置文件里也有：

```json
"codexAppForceChineseLocale": true
```

也就是说，开关确实开了。

但界面依然英文。

这时就不能继续猜了，只能看日志。

---

### 3. 第三步：看 Codex++ 注入日志

旧版 Codex++ 日志反复出现：

```text
launcher.ensure_injection_retry_failed
No injectable Codex page target found
```

大白话：

```text
Codex++ 找到了 Codex 进程，
但没能成功往它的页面里注入中文补丁。
```

原因很可能是：

- Codex 新版本更新了内部结构。
- Codex++ 旧版本还没适配。
- 调试端口和页面目标虽然存在，但注入逻辑不匹配。

后来 Codex++ 更新到 1.3.0，注入终于成功。

但中文还是没恢复。

---

## 六、真正的根因：getLayer 和 getDynamicConfig

继续检查 Codex 新版前端代码，发现界面语言处理逻辑是：

```js
o = Yh("72216192");
s = o.get("enable_i18n", false);
l = o.get("locale_source", "IDE");
```

而 `Yh` 实际封装的是：

```js
client.getLayer(name, options)
```

也就是说，Codex 新版使用的是：

```js
getLayer("72216192")
```

但 Codex++ 1.3.0 修改的是：

```js
getDynamicConfig("72216192")
```

这两个接口名字很像，但不是一回事。

最终就变成：

- Codex++ 说：我改了。
- Codex 说：你改的不是我在用的那个。
- 用户看到：设置是中文，但界面还是英文。

---

## 七、最终修复：用户脚本同时兼容两个接口

为了让 Codex++ 不再改错对象，我们加了一个用户脚本：

```text
C:\Users\<用户名>\AppData\Roaming\Codex++\user_scripts\force-zh.js
```

它的核心思路有四步：

1. 修改 `navigator.language`，让页面看到 `zh-CN`。
2. 包装 `getLayer`，强制返回：

   ```json
   {
     "enable_i18n": true,
     "locale_source": "SYSTEM"
   }
   ```

3. 同时包装 `getDynamicConfig`，兼容可能还调用旧接口的情况。
4. 定时检查 Statsig 客户端，避免它初始化得比补丁晚。

核心逻辑可以简化成下面这样：

```js
const I18N_LAYER = "72216192";

function patchConfigObject(config) {
  if (!config || typeof config !== "object") return config;

  config.value = {
    ...(config.value || {}),
    enable_i18n: true,
    locale_source: "SYSTEM",
  };

  if (typeof config.get === "function" && !config.__forceZhPatch) {
    const originalGet = config.get.bind(config);

    config.get = (key, fallback) => {
      if (key === "enable_i18n") return true;
      if (key === "locale_source") return "SYSTEM";
      return originalGet(key, fallback);
    };

    config.__forceZhPatch = true;
  }

  return config;
}
```

然后同时包装：

```js
client.getLayer = (name, options) => {
  const layer = originalGetLayer(name, options);
  return name === I18N_LAYER ? patchConfigObject(layer) : layer;
};

client.getDynamicConfig = (name, options) => {
  const config = originalGetDynamicConfig(name, options);
  return name === I18N_LAYER ? patchConfigObject(config) : config;
};
```

重启 Codex 和 Codex++ 后，中文终于恢复。

## 八、以后每次打开 Codex 要不要先开 Codex++ 和 CC Switch

这个问题要分开看。

### 如果你还在用 DeepSeek 等第三方模型

需要 CC Switch。

因为 Codex 的请求要经过：

```text
127.0.0.1:15721
```

CC Switch 不运行，端口就不在，Codex 会连不上当前模型。

### 如果你要用 Codex++ 的增强和中文补丁

需要 Codex++。

而且最稳的方式是：

```text
从 Codex++ 启动 Codex
```

因为中文补丁是 Codex++ 注入进去的。

### 最省事的启动顺序

1. 先启动 CC Switch。
2. 再启动 Codex++ Manager。
3. 从 Codex++ 点击打开 Codex。

如果嫌麻烦，可以：

- 把 CC Switch 设置成开机自启。
- 把 Codex++ 设置成开机自启。
- 平时只点 Codex++ 启动 Codex。

如果以后切回官方 OpenAI 模型，不再用第三方模型，那么 CC Switch 可以不开，但 Codex++ 仍然建议保留，除非你不需要界面增强和强制中文。

## 九、这次排查最重要的几个教训

### 1. “不支持图片”不一定是模型不支持

也可能是中间层提前拦截了。

### 2. 配置文件正确，不代表界面已经应用

`localeOverride` 写对了，只是第一步。运行时还要有 `enable_i18n`。

### 3. 第三方增强工具通常依赖内部接口

Codex 更新后，内部接口可能改名字、改参数、改行为。Codex++ 这类工具不一定第一时间跟上。

### 4. 日志比猜测可靠

这次两个关键线索都来自日志：

```text
[Media] Replaced 1 image block(s) with [Unsupported Image]
```

```text
No injectable Codex page target found
```

### 5. 补丁要改对接口

`getDynamicConfig` 和 `getLayer` 看起来很像，但调用对象完全不同。

## 十、如果以后再出现类似问题，怎么快速定位

### 图片又发不进去

检查这几项：

1. Codex 当前模型是什么。
2. CC Switch 模型目录里有没有：

   ```json
   "input_modalities": ["text", "image"]
   ```

3. `127.0.0.1:15721` 是不是 CC Switch 在监听。
4. 日志里有没有：

   ```text
   [Unsupported Image]
   ```

### 界面又变英文

检查这几项：

1. Codex 设置里 `localeOverride` 是不是 `zh-CN`。
2. Codex++ 的“强制中文界面”是不是开着。
3. Codex++ 日志里有没有注入失败。
4. `force-zh.js` 是否还在。
5. Codex 新版是否又换了内部接口。

## 最后总结

这次不是单一 bug，而是两个独立问题叠在一起：

```text
图片问题 = CC Switch 模型能力表错误
中文问题 = Codex++ 修改了错误的运行时接口
```

图片问题的修复路径是：

```text
检查模型目录
→ 发现只支持 text
→ 更新 CC Switch
→ 增加 image
→ DeepSeek 成功识别图片
```

中文问题的修复路径是：

```text
确认 localeOverride = zh-CN
→ 检查 Codex++ 注入
→ 分析 Codex 新版前端
→ 发现使用 getLayer
→ 用户脚本同时兼容 getLayer 和 getDynamicConfig
→ 重启后恢复中文
```

以后再遇到“设置明明是对的，但软件就是不生效”，可以记住一句话：

> 设置正确只是起点，真正决定结果的，是运行时有没有读到、有没有改对、有没有作用到正在显示的那个界面。
