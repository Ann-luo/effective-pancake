## 0. 先说结论（懒人版）

如果你也用的 DSH 桌面版，想装社区插件，记住这五条能省你几个小时：

1. **桌面版的 profile 由 Electron 应用独占管理**，在终端里跑 `dsh plugin --profile desktop add xxx` **会被拒绝**。
2. 装插件要**同时改两处**：`package.json` 的 `dependencies`（装包）和 `dsh.profile.bundles`（注册加载）。**只改前者 = 装了个寂寞。**
3. DSH 从 `0.2.0-rc.1` 起有**兼容闸门**：插件声明的 `@deepseek-ai/dsh*` peer 范围不覆盖你的版本 → **整个插件被静默跳过**（不报错，功能直接消失）。
4. 装完**必须完全重启 DSH**，然后 **Ctrl+Shift+R 硬刷新**浏览器。
5. 插件作者的 README 有时比代码更乐观。**代码才是真相。**

下面是我这一路的完整过程，包括所有翻车现场。

## 1. 起因：想给 DSH 美化一下

一开始我的需求特别朴素：「去 GitHub 上找找有没有给 DSH 用的美化插件，要成熟的。」

结果这一句话引出了一堆事。因为在 DSH 生态里，"美化"至少分成**三个完全不同的方向**：

| 方向 | 干什么 | 代表插件 |
|---|---|---|
| **换肤** | 改配色、玻璃质感、圆角、字体 | `dsh-dream-skin` |
| **背景壁纸** | 在聊天界面后方铺一张图/一段视频 | `dsh-plugin-wallpaper-engine` |
| **开屏动画** | 打开新对话时播一段片头视频 | `dsh-boot-animation` |

**这三个不能互相替代**。我一开始以为"壁纸插件"能顺手把开屏动画也解决了，或者反过来——都不是。

> 💡 **给新手的提醒**：搜插件之前先在纸上写清楚你到底要改哪个东西。"界面好看"太模糊了，会把你带到沟里。

## 2. 第一步：怎么判断一个插件"成熟"

GitHub 搜索结果里全是"XX主题""XX皮肤"，光看 README 个个都像神器。**别信 README，看数据。**

我最后用的是这几条硬指标：

| 指标 | 怎么看 | 我的及格线 |
|---|---|---|
| **Star 数** | 仓库首页左上角 | > 100 |
| **最后提交时间** | 仓库首页右侧 "last commit" | 一个月内 |
| **有没有 LICENSE** | 文件列表 | 必须有（最好 MIT / BSD） |
| **open issues 数** | Issues 标签 | 别太多，几十个说明积压严重 |
| **仓库是否 archived** | 顶部横幅 | 归档的直接放弃 |

### 用 GitHub API 批量对比（这一步很省事）

手动点开十几个仓库一个个看太慢了。可以直接调 GitHub 的搜索 API：

```
https://api.github.com/search/repositories?q=dsh+theme&sort=stars&order=desc&per_page=30
```

返回的 JSON 里每一行都有 `stargazers_count`、`pushed_at`（最后推送时间）、`open_issues_count`、`license`。

**我在这一步捞到的几个典型数据**（都是当天查的）：

| 插件 | Star | 最后提交 | 结论 |
|---|---|---|---|
| `dsh-TUI` | 3830 | 当天 | 活跃，可用 |
| `dsh-plugin-wallpaper-engine` | 409 | 前一天 | 活跃，可用 |
| `dsh-dream-skin` | 196 | 前一天 | 活跃，可用 |
| 某透明玻璃主题 | 409 | **两个月前** | ⚠️ 看着 star 高，其实停更了 |

**教训**：Star 高 ≠ 活跃。那个 409 star 的透明主题两个月没提交、积压 25 个 issue，我一开始差点推荐它。

## 3. 第一次翻车：给出了错误的安装命令

我兴冲冲地查完一圈，给了这样的安装命令：

```bash
dsh plugin --profile web add dsh-skin-market
```

**然后发现：这台机器上根本没有 `web` 这个 profile。**

真相是——我实际用的是**官方桌面版**，profile 只有 `desktop` 一个。社区里所有 README 写的 `--profile web` 那是给命令行版 `dsh web` 用的。

> ⚠️ **后面所有命令里的 `--profile <名字>` 和 `<DSH安装目录>` 都要按你自己的机器替换。**
> 第 15 节第一步有探测命令，别照抄。

### 怎么查自己有哪些 profile

```powershell
Get-ChildItem "$env:USERPROFILE\.dsh\profiles" -Directory | Select-Object -ExpandProperty Name
```

输出 `desktop` → 你是桌面版；输出 `web` → 你是命令行版。

> 💡 **这一步千万别跳过**。用错 profile 名，命令要么报错，要么（更糟）装到一个你根本不用的 profile 里，然后你死活找不到效果。

## 4. 第二次翻车：终端命令被应用拒绝

知道 profile 名是 `desktop` 之后，我想当然地跑：

```powershell
dsh plugin --profile desktop add dsh-boot-animation
```

报错：

```
EPERM: operation not permitted, open
'C:\Users\<用户名>\.dsh\profiles\desktop\package.json.lock'
```

我先以为是权限不够，折腾了半天。后来用 `--dump-config` 试了一下，看到了真正的错误：

```
error: profile "desktop" is managed exclusively by the Electron application
```

**翻译：desktop 这个 profile 被 Electron 应用独占管理，命令行不许碰。**

这是**设计如此**，不是 bug。官方桌面版的插件管理走的是应用内部的插件服务，终端只能干看着。

### 那怎么办？两条路

**路线 A：在应用内的插件市场里点（推荐）**
桌面版自带一个插件市场（搜索框 + `全部 (4.4k)` 那种界面），能装的就点一下，最省事。

**路线 B：直接改 profile 的 `package.json`（当市场里没有时）**
我就是走的这条。

## 5. 关键知识点：装插件必须同时改两处

这是整篇文章**最值钱的一条**。我一开始只改了 `dependencies`，结果插件装上了、进程也重启了，**但是完全没反应**。

### 为什么？

DSH 的插件分两层：

```
profile/
├── package.json          ← 这里有两块，都要改
│   ├── dependencies      ← 「装这个包」（相当于 npm install）
│   └── dsh.profile.bundles  ← 「启动时加载哪些插件」
└── node_modules/         ← 实际的包
```

**只加 `dependencies`，包确实装上了，但它不在启动列表里，DSH 启动时根本不会去看它。**

### 改完长这样

```json
{
  "name": "dsh-profile-desktop",
  "private": true,
  "dependencies": {
    "dsh-boot-animation": "link:D:/path/to/local/clone",
    "dsh-plugin-wallpaper-engine": "1.1.0"
  },
  "dsh": {
    "profile": {
      "bundles": [
        "@deepseek-ai/dsh-base",
        "@deepseek-ai/dsh-web-app",
        "dsh-boot-animation",
        "dsh-plugin-wallpaper-engine"
      ]
    }
  }
}
```

改完在 profile 目录里跑一次 `pnpm install` 就建好链接了。

> ⚠️ **动手前先备份 `package.json`**。这是我每次必做的第一件事：
> ```powershell
> Copy-Item package.json "package.json.bak-$(Get-Date -Format yyyyMMdd-HHmm)"
> ```

## 6. 安装方式的选择（三种，差别很大）

搞明白 profile 结构后，我发现插件有三种装法，各有各的坑：

| 方式 | 怎么写 | 什么时候用 | 坑 |
|---|---|---|---|
| **npm 正式包** | `"包名": "1.1.0"` | 作者发过 npm（**首选**） | 见下面第 7 节的版本坑 |
| **GitHub 源码** | 下载 zip 解压，用 `"link:绝对路径"` | 没发 npm 的 | 要么自带构建产物，要么你得自己 build |
| **git clone** | `git clone` 后 link | 同上 | 我这边 git 连不上 github.com ⚠️ |

> 判断一个插件有没有发 npm：直接访问 `https://registry.npmjs.org/<包名>`，
> 返回 JSON 就是发了，返回 `{"error":"Not found"}` 就是没发。
> 比如 `dsh-boot-animation` 就是**没发 npm**的那个（我实测返回 404）。

### 关于 git 连不上

```powershell
git clone https://github.com/xxx/yyy.git
# fatal: unable to access '...': Failed to connect to github.com:443 after 21100 ms
```

但有意思的是，**同一个网络下浏览器访问 GitHub 完全正常**。所以这是 git 那条通道的问题，不是网络断了。

**绕过办法**：用 GitHub 的归档下载接口（走的是 codeload 域名，通道不一样）：

```powershell
Invoke-WebRequest -Uri "https://codeload.github.com/<owner>/<repo>/zip/refs/heads/main" -OutFile "repo.zip"
Expand-Archive -Path "repo.zip" -DestinationPath "."
```

实测 18 MB 的仓库几秒就下来了。

> 💡 下载 zip 前先看 `package.json` 里的 `files` 字段和仓库目录结构——**如果 `lib/` 目录已经提交进仓库，那就说明作者把构建产物也放进去了，你不用自己编译。**

## 7. 最阴的坑：pnpm 的 24 小时冷静期

这个坑特别值得单独说，因为它**不报错**。

`pnpm` 有个 `minimumReleaseAge`（新版本冷静期）机制：**刚发布不到 24 小时的新版本，不带版本号的安装会被静默解析成上一个"成熟"版本。**

实际表现：

```bash
# 你以为装的是最新的 9.29.0
dsh plugin --profile web add dsh-dream-skin

# 实际上输出里只有一行提示，很容易看漏：
+ dsh-dream-skin ^9.27.1
(9.29.0 is available)
```

然后那个旧版 `9.27.1` 的兼容范围不覆盖你的新宿主 → **被兼容闸门拒绝 → 装上了但什么都不显示。**

**解决办法：写死版本号。**

```bash
dsh plugin --profile web add dsh-dream-skin@9.29.0
```

显式写版本号会让 pnpm 自动把它加进 profile 的 `minimumReleaseAgeExclude`，不再退回旧版。我在实测里看到 pnpm 输出了这一行确认：

```
Added 1 entry to minimumReleaseAgeExclude in pnpm-workspace.yaml
  dsh-plugin-wallpaper-engine@1.1.0
```

## 8. 核心机制：DSH 的「兼容闸门」

这是整篇文章**技术上最有价值的发现**。

### 现象

有个插件明明装上了、profile 里也有、重启也做了，但**功能完全消失**，而且**没有任何错误提示**。

### 真相

我把 DSH 的 `app.asar` 拆开，找到了宿主里真正干活的函数 `evaluatePluginCompatibility()`：

```javascript
function evaluatePluginCompatibility(manifest, exemptions = {}, runtimeVersion = ...) {
  // ① 没有 peerDependencies 字段 → 直接放行
  if (!Object.hasOwn(fields, "peerDependencies")) return void 0;

  for (const [name, range] of Object.entries(dependencies)) {
    // ② 只看 @deepseek-ai/dsh 和 @deepseek-ai/dsh-* 开头的
    if (name !== "@deepseek-ai/dsh" && !name.startsWith("@deepseek-ai/dsh-")) continue;

    // ③ 用 semver 逐个校验，任何一个不满足就记下来
    if (requirement.trim() === "" ||
        !semver.satisfies(runtimeVersion, requirement, { includePrerelease: true }))
      peers[name] = range;
  }

  // ④ 只要有任何一个不满足 → 返回不兼容信息 → 宿主整个跳过这个插件
  if (Object.keys(peers).length === 0) return void 0;
  return { name, version, runtimeVersion, peers, exempted: ... };
}
```

**三条关键规则：**

1. **完全没有 `peerDependencies` 的插件 → 直接放行**，连检查都不做。
2. **只检查 `@deepseek-ai/dsh*` 开头的依赖**，其他的一概不管。
3. **只要有一条不满足 → 整个插件被跳过**（不是降级、不是警告，是直接不加载）。

### 这解释了我遇到的一切

| 插件 | 声明的 dsh peer | 结果 |
|---|---|---|
| `dsh-dream-skin` 旧版 | `^0.1.0-rc.6`（等价 `<0.2.0-0`） | ❌ 被拒，功能消失 |
| `dsh-dream-skin` 9.29.0 | `>=0.1.0-rc.6 <0.3.0-0` | ✅ 覆盖 `0.2.0-rc.2`，通过 |
| `dsh-boot-animation` | **一条都没声明** | ✅ 连闸门都碰不到 |
| `dsh-plugin-wallpaper-engine` | `>=0.1.0-rc.6`（开口上限） | ✅ 通过 |

### 怎么自己查（升级前必做）

```powershell
# 看你装的插件声明了什么范围
Get-Content "$env:USERPROFILE\.dsh\profiles\<你的profile名>\node_modules\<插件名>\package.json" |
  Select-String -Pattern "peerDependencies" -Context 0,10
```

对照你的 DSH 版本（我的是 `0.2.0-rc.2`），**只要范围覆盖得住就没事**。

## 9. 怎么知道 DSH 的版本（以及踩的坑）

`resources\version` 文件里写的是 **`44.0.0`** —— 那是 **Electron 的版本**，不是 DSH 的。

真正的版本要从 `app.asar` 里读：

```powershell
# app.asar 是个归档文件，头部是 JSON 索引
$asar = '<DSH安装目录>\resources\app.asar'
$fs = [System.IO.File]::OpenRead($asar)
$br = New-Object System.IO.BinaryReader($fs)
# 跳过前 12 字节，第 13-16 字节是头部 JSON 的长度
$null=$br.ReadInt32(); $null=$br.ReadInt32(); $null=$br.ReadInt32()
$hdrSize = $br.ReadInt32()
$hdr = [System.Text.Encoding]::UTF8.GetString($br.ReadBytes($hdrSize))
# 在头部 JSON 里找目标 package.json 的 offset/size，再读出来解析
```

或者更省事——**直接读 `app.asar.unpacked` 目录里的包**：

```powershell
Get-Content '<DSH安装目录>\resources\app.asar.unpacked\dsh\node_modules\@deepseek-ai\dsh-desktop-host\package.json' |
  ConvertFrom-Json | Select-Object version
```

我的结果是 `0.2.0-rc.2`。

> 💡 **顺便一个冷知识**：`app-update.yml` 里能看到更新通道。我的是 `channel: nightly`（每日构建），所以 DSH 本身更新频率会比较高。

## 10. 开屏动画插件：装是装上了，但为什么不播

这个插件（`dsh-boot-animation`）最后装成功了，但中间有一段特别迷惑的经历：**钉住的会话能播，新对话不播。**

### 先看它的播放规则（源码里就这几行）

```javascript
// ① 钉住的会话：每次进入都播
if (pinned !== null && pinned === sessionId) {
  if (!entered) return;
  void store.playMode('active', 'pinned');
  return;
}

// ② 新对话：只播一次，播过就记账
if (isNewConversation && !hasPlayed(sessionId)) {
  markPlayed(sessionId);          // ← 注意这行的位置！
  void store.playMode('active', 'new-conversation');
}
```

### 两个发现

**发现一：它没有"开机即播"。** 所谓开屏动画，是**进入新对话时**播，不是 DSH 一启动就播。所以"我开机没看到动画"其实是**正常行为**。

**发现二：`markPlayed()` 写在真正播放之前。**

这意味着：**只要有一次触发了、但画面没真的显示出来**（解码慢、被别的东西挡住、你正好切窗口了……），这个会话就被**永久标记为"已播"**。之后你再进、再刷新，都因为 `hasPlayed === true` 而跳过——**而且不会有任何提示**。

那个"播过"的记录存在 `localStorage`：

```javascript
// 查看
localStorage.getItem('dsh-boot-animation:played')

// 清掉重来
localStorage.removeItem('dsh-boot-animation:played')
```

### 怎么诊断（这招通用）

插件的诊断日志默认是关的（源码里 `export const DEBUG = false`），但**有几行是"永远打印"的**。我在浏览器按 F12 打开控制台，看到：

```
[dsh-boot-animation] play {"clipId":"builtin:cyberpunk","reason":"selected", ...}
[dsh-boot-animation] first frame painted {"ms":193,"readyState":4, ...}
```

**这两行合起来说明：动画确实在播、而且首帧 193 毫秒就画出来了。**

> 💡 **通用调试技巧**：判断一个前端插件"有没有跑起来"，不要去猜，**打开控制台看它有没有打印**。有 `play` + `first frame painted` 就说明整条链路是通的。

### 最终结论

`isNewConversation` 这个判断在 `0.2.0-rc.2` 上**不生效**（静默失配，作者在 CHANGELOG 里也承认这个字段在 0.2.0 挪过位置）。作者自己的注释写得很实在：

> 读一个已经不存在的字段**不报错**，只返回 `undefined`，判断恒为假 —— 所以症状不是崩溃或报错，而是**沉默**。

**解决方案：日常用「钉住」。** 点侧边栏底部的 🎞 图标，变绿之后每次进这个会话都会播——这条路径不检查"播过没有"，稳定可靠。

## 11. 从插件里把内嵌视频导出来

这个插件把四段片头**以 base64 内嵌在代码里**（`lib/clips.data.js`，11 MB），不落盘成 mp4。我想把它们存到桌面，于是写了个脚本解码：

```javascript
const fs = require('fs');
const text = fs.readFileSync('lib/clips.data.js', 'utf8');

// 文件长这样：export const cyberpunk = "AAAAIGZ0eXBpc29t..."
const m = /export\s+const\s+cyberpunk\s*=\s*"([A-Za-z0-9+/=]+)"/.exec(text);
const buf = Buffer.from(m[1], 'base64');
fs.writeFileSync('导出的视频.mp4', buf);
```

### 光导出不够，还得校验

解码出来的字节到底是不是完整的视频？我做了三重校验：

| 检查 | 方法 | 期望 |
|---|---|---|
| **大小对不对** | 和 `clips.meta.js` 里记的 `bytes` 字段比 | 完全一致 |
| **是不是合法 MP4** | 第 5-8 字节是不是 `ftyp` | 是 |
| **是不是 faststart** | `moov` 的位置是否在 `mdat` 之前 | 是 |

```javascript
console.log('box[0] =', buf.slice(4, 8).toString('latin1'));   // 期望 ftyp
const moovAt = buf.indexOf(Buffer.from('moov'));
const mdatAt = buf.indexOf(Buffer.from('mdat'));
console.log('faststart =', moovAt < mdatAt);
```

四段全部通过，而且 **sha256 与元数据里记录的完全一致**：

| 文件 | 大小 | sha256 前 16 位 |
|---|---|---|
| 品牌片头 | 1.25 MB | `b22de4810e195b50` |
| 赛博朋克片头 | 1.77 MB | `beabf5956e0b467e` |
| 数字角色苏醒 | 2.48 MB | `ff5afe0dabc16e09` |
| 启动问题 | 3.15 MB | `ba72c501021444cd` |

> 💡 **`faststart` 为什么重要**：MP4 的索引表（`moov`）如果在文件**末尾**，浏览器必须把整个文件下完才能出画面 → 表现为"黑屏"。用 ffmpeg 无损重排一下就好：
> ```bash
> ffmpeg -i 原片.mp4 -c copy -movflags +faststart 修好的.mp4
> ```

## 12. 壁纸插件：自己上传视频当动态壁纸

这个是我最后装的，也是最满意的。

### 它其实不需要 Wallpaper Engine

我一开始被名字骗了，以为必须有 Steam 上那个 Wallpaper Engine 才能用。结果它的 README 里明确写着：

> 没有 Wallpaper Engine？……你**仍然可以**只用「自定义壁纸」功能上传自己的图片/视频当背景。

**支持 JPG / PNG / MP4。** 这就是我要的"自定义动态壁纸"。

### ⚠️ 视频必须是 H.264

现代浏览器解不了 HEVC/H.265、ProRes、部分 mkv。表现是**黑屏或有声无画**。

```bash
ffmpeg -i 原片.mp4 -c:v libx264 -c:a aac -movflags +faststart 修好的.mp4
```

### 一个反直觉的行为

**换壁纸后，插件会自动切换全局深色/浅色**（按壁纸主色判断）。

第一次遇到会以为"我的主题被改了"。不想被管：**在 DSH 设置里手动选一次深色或浅色**，这张壁纸就不再自动切了。

## 13. 差点被忽略的环境问题：Windows 文件权限

这个跟插件无关，但是**最耽误事的一个**。

### 现象

所有 PowerShell 命令都起不来：

```
Error: SetNamedSecurityInfoW failed (Win32 5): grantWrite(...)
```

连 `echo hello` 都执行不了。**报错信息完全看不出原因。**

### 排查

用诊断脚本读了工作区及其每一级父目录的权限，发现工作区**缺了 `WRITE_OWNER`（取得所有权）权限**：

```
OBJECT=D:\...\default-workspace
  WRITE_DAC=True WRITE_OWNER=False     ← 问题在这
```

DSH 的沙箱机制需要这两项权限才能给工作区授权，缺一个就全盘歇菜。

### 修复

用专门的修复脚本（它会先备份原权限、改完验证、并生成回滚命令）：

```powershell
& '<脚本路径>\diagnose-windows-sandbox-acl.ps1' `
  -Path 'D:\...\default-workspace' `
  -AllowRoot 'D:\...\default-workspace' `
  -Out 'D:\...\acl-recovery'
```

修复后 `WRITE_OWNER=True`，shell 立刻恢复。

> 💡 **关键点**：这个脚本要在**非受限模式**下跑，因为它自己就要写权限。而且它**会留备份和回滚命令**——改权限这种事，一定要有退路。

## 14. 沙箱权限：为什么 Agent 不能自己收紧

安装过程中我需要往工作区之外写文件（改 profile 的 `package.json`），这需要**临时放宽沙箱**。

我一开始以为"放宽了之后再让它切回去就行了"——**不行**。

**Agent 只能申请放宽，不能给自己收紧。** 这是刻意设计的：如果 Agent 能自己调自己的权限策略，那这道闸门就没有意义了。

**收回权限只能由人在 GUI 里操作**（设置 → 文件访问/权限 → 改回"工作区写入"）。

> 💡 这个设计我觉得挺对的。默认收紧、需要时申请、人工放行——比"默认全开"安全太多了。

## 15. 最后的完整流程（可以直接抄）

如果你也想在 DSH 桌面版装社区插件，完整流程：

### 第一步：查环境（**别跳过，后面所有命令都要用这里的值**）

```powershell
# ① 你有哪个 profile？（输出 desktop 或 web）
Get-ChildItem "$env:USERPROFILE\.dsh\profiles" -Directory | Select-Object -ExpandProperty Name

# ② 运行时程序在哪？（下面装插件要用）
$node = Get-ChildItem "$env:USERPROFILE\.dsh\dsh-runtimes" -Recurse -Filter node.exe -ErrorAction SilentlyContinue |
        Select-Object -First 1 -ExpandProperty FullName
$pnpm = Get-ChildItem "$env:USERPROFILE\.dsh\dsh-runtimes" -Recurse -Filter pnpm.mjs -ErrorAction SilentlyContinue |
        Select-Object -First 1 -ExpandProperty FullName
Write-Host "node = $node"
Write-Host "pnpm = $pnpm"
```

> 💡 **为什么不能照抄我原来的命令**：我脱敏前的原文里写的是我自己机器上的绝对路径。
> 换台机器就找不到那个目录了。**上面这两行是"探测"，不是"硬编码"。**

### 第二步：判断插件能不能用

- 看它的 `peerDependencies` 里 `@deepseek-ai/dsh*` 的范围覆不覆盖你的版本
- 没有 `peerDependencies` → 一定能过
- 有 → 手动比对

### 第三步：装（同时改两处）

**先把 profile 名换成你第一步查到的那个**（下面以 `desktop` 为例）：

```powershell
$profile = "$env:USERPROFILE\.dsh\profiles\desktop"   # ← 换成你的 profile 名
Copy-Item "$profile\package.json" "$profile\package.json.bak"   # 先备份！
```

然后改 `$profile\package.json`：

```json
"dependencies": {
  "插件包名": "精确版本号"
},
"dsh": {
  "profile": {
    "bundles": [ "...原有...", "插件包名" ]
  }
}
```

再安装（用第一步探测到的 `$node` / `$pnpm`）：

```powershell
cd $profile
& $node $pnpm install
```

### 第四步：重启 + 硬刷新

1. **完全退出** DSH（不是最小化）
2. 重新打开
3. **Ctrl+Shift+R**（硬刷新，普通 F5 不够）

### 第五步：验证

去设置里找插件提供的界面（比如「Wallpaper Engine」页签、侧边栏的 🎞 图标）。

**找得到 = 成功；找不到 = 大概率被兼容闸门跳过了**，回去查第二步。

> 💡 **验证不通过时按这个顺序查**：
> 1. `bundles` 里有没有这个包名？（第 5 节的坑）
> 2. peer 范围覆不覆盖？（第 8 节的坑）
> 3. 硬刷新了吗？完全退出重启了吗？
> 4. 打开 F12 控制台看有没有该插件的日志

## 16. 几个通用的教训

### ① README 是作者写的，代码是机器跑的

我这次有两三次被 README 带偏（比如"必须装 Wallpaper Engine"，其实不需要）。**遇到矛盾时以代码为准。**

### ② 静默失败最要命

这次遇到的三个大坑——兼容闸门、`markPlayed` 抢跑、`isNewConversation` 失配——**全都不报错**。

症状都是"功能没出现"，原因却完全不同。所以：

> **凡是"没反应"的问题，第一步永远是打开控制台看有没有日志，第二步是找到那个判断条件的源码。**

### ③ 报错信息经常是指向错误的方向

`EPERM ... package.json.lock` 看着像权限问题，实际是"这个 profile 不许命令行碰"。
`SetNamedSecurityInfoW failed` 看着像安全软件拦截，实际是缺一个权限位。

**真要找原因，得往上游追。**

### ④ 改任何配置之前先备份

我每次改 `package.json` 之前都 `Copy-Item` 一份带时间戳的备份。整场下来备份了四次，一次都没用上——但这就是它存在的意义。

### ⑤ 一次只装一个插件

我中途一次装两个，出问题时得花时间分辨是谁的锅。**装一个、重启、验证、再装下一个。**

### ⑥ 别急着更新

你现在的版本只要能跑，就不必追新。真要更新，顺序是：

> **先更新 DSH → 再更新插件**（反了会撞上不兼容的 API）
>
> 更新前用第二步的方法检查一遍兼容范围。
