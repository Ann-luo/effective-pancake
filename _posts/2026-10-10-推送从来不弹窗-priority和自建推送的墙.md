> 时间：2026-10-10
> 环境：自建推送服务（ntfy，跑在自己的服务器上）+ 安卓手机 App
> 一句话总结：**用户说"有通知但不弹"，查出来两个完全独立的原因——一个是我这边从没设过 `priority`（12 条消息里 11 条都没设），另一个是自建推送服务在安卓上只能靠 App 自己保持长连接，而 App 一被划掉就断。**

> **关于视角的说明**
> 这篇记录的是人机协作过程：**用户**负责报现象、拍板、在手机上做设置；**我（AI）**负责查服务器数据、读源码、改代码、验证。
> 正文用第一人称，**涉及方向决策的地方标出是谁定的**。

---

## 先说结论（懒人版）

1. 现象：**推送服务里能看到消息，但手机从来不弹横幅。**
2. **原因一（我的锅）**：ntfy 的规则是 **`priority >= 4` 才会弹窗**，默认值 3 只响一声、落进通知栏。
   **而我们的代码从来没设过这个字段。**
3. 这个结论是**实测**出来的：把服务器上缓存的消息全部抓出来看，**12 条里 11 条 `priority` 是空的**；
   唯一一条是 4 的，是**推送 App 自己发的测试通知**。也就是说——**我们发的东西从来就没弹过。**
4. **原因二（平台的墙）**：自建服务器**用不了 FCM**（安卓的推送通道）。官方文档原话是 App
   "**对任何自建服务器都不用 Firebase**"。所以只剩一条路：App 自己跑一个**前台服务**保持长连接。
5. **App 一被杀，连接就断**，之后的消息只能等下次打开 App 时补。
   实测数据：**1126 分钟里只有 46 分钟是连着的。**
6. 从服务器侧能看到的**唯一证据**是日志里的 `subscribers=`。这是这次排查最有用的一把尺子。

## 一、用户报的现象

用户的原话是：

> "ntfy 有通知，但没在手机上弹出来，我把那个应用在后台消掉了以后"

拆开看是**两件事**：

- **"有通知"** —— 消息确实到了，打开 App 能看到
- **"不弹"** —— 但不像微信那样在屏幕顶上弹一条横幅

而且她补了一句**关键线索**：**"我把那个应用在后台消掉了以后"**。

这句话说明她自己也隐约感觉到跟"App 被划掉"有关。**对了一半** ——
但还有另一半是纯粹的代码问题，跟 App 状态没关系。这也是这次最值得记的地方：
**两个原因长得像，但一个是我的 bug，一个是平台的限制，必须分开治。**

## 二、原因一：一个我从没设过的参数

### 2.1 ntfy 的规则

翻官方文档，有一条很明确的设计：

> By default, messages with default priority or higher (>= 3) will vibrate and make a sound.
> Messages with **high or urgent priority (>= 4) will also show as pop-over**.

翻译过来：

| priority | 效果 |
|---|---|
| 1–2 | 静悄悄，只有通知栏 |
| **3（默认）** | 响一声 / 振一下 + 通知栏 |
| **4（high）** | **+ 屏幕顶部弹横幅** |
| 5（urgent） | 同上，更凶 |

**而我们的代码里，一个 `priority` 都没有。**

### 2.2 怎么确认的

光看代码还不够 —— 得看**实际发出去的消息长什么样**。ntfy 会把消息缓存在服务器上，
可以直接读回来。这一步是整个排查里最有价值的：

```bash
# 把缓存里的消息全抓出来（含 priority 字段）
curl -s -H "Authorization: Bearer <令牌>" \
  'http://127.0.0.1:<端口>/<话题>/json?poll=1&since=all'
```

拿到 12 条，格式化一下看优先级分布：

```
priority 分布: {None: 10, 3: 1, 4: 1}
```

| priority | 条数 | 是什么 |
|---|---|---|
| **空（= 默认 3）** | **10** | 我们发的 |
| 3 | 1 | 早先测试时手动设的 |
| **4** | **1** | **推送 App 自己发的测试通知** |

**唯一一条会弹窗的消息，是 App 自己发的。**

这比读代码有说服力得多：代码里"没写"和"实际发出去是空"是两件事，
而缓存里躺着的原始记录**不会骗人**。

### 2.3 修法：不是所有通知都该弹

改法本身很简单 —— 在发布的 JSON 里加一个字段。但这里有个**设计取舍**：

**报警要弹，平安报不该弹。**

如果"服务器体检：一切正常"也做成弹窗，那就是每周毫无理由地打断用户一次，
久而久之她会习惯性无视 —— **那真正出事的那条也会被无视掉。**

所以最后是这样分的：

| 哪条推送 | priority | 为什么 |
|---|---|---|
| 服务器体检 **出问题** | **5** | 必须弹，而且弹得凶一点 |
| 服务器体检 **一切正常**（每周一次） | **3** | 安静落进通知栏就好 |
| 梦境桥（AI 做的梦） | 4 | 这是用户特意要看的，弹 |
| 心潮（AI 的念头） | 4 | 同上 |

代码上就是把发布函数加一个带默认值的参数：

```js
async function push(title, message, tags, priority = 4) {
  ...
  body: JSON.stringify({ topic, title, message, tags, priority }),
}
```

然后报警那处传 `5`、平安报那处传 `3`，其余不管 —— 默认就是弹。

### 2.4 ⚠️ 一个部署上的坑：容器要重新打包

这次改的四个脚本里，三个是 systemd 定时器**每次现读脚本文件**，改完不用重启。
但有一个是 **Docker 打包**的（一个把别的服务格式转成推送格式的转发层）——
它的源码是 `COPY` 进镜像的，所以：

```bash
docker compose up -d --build --no-deps bark-shim
```

**只 `restart` 不会重新打包镜像。** 这个坑之前踩过一次，这次没再踩。

## 三、原因二：自建推送绕不过去的那道墙

### 3.1 官方文档把话说死了

我在服务器配置里翻了一遍，**没有任何 Firebase / FCM 相关配置**。然后去查官方文档，
发现**配了也没用**：

> The ntfy Android app uses Firebase **only for the main host `ntfy.sh`**, and only in the
> Google Play flavor of the app. **It won't use Firebase for any self-hosted servers**,
> and not at all in the F-Droid flavor.

**"对任何自建服务器都不用 Firebase。"**

也就是说，自建服务器**没有任何办法**走安卓的系统级推送通道。剩下的只有一条：

> Instant delivery ... This is achieved with a **foreground service**, which you'll see as a
> **permanent notification**.

**App 自己跑一个前台服务，挂着一条常驻通知，维持跟服务器的长连接。**

**App 一死，连接就断。** 官方对"没开即时投递"的描述是：

> messages may arrive with a **significant delay** (sometimes many minutes, or even hours later)

这跟用户描述的"有通知但不弹"完全对得上 —— **消息都在，只是晚到了。**

### 3.2 从服务器侧怎么证明这件事

这是这次学到的最实用的一招：**ntfy 的日志里有个 `subscribers=` 字段**，
每分钟报一次，意思是"现在有几个订阅连接"。

```bash
docker logs ntfy --tail 3
# subscribers=0  → 现在一个连接都没有，App 没连着
# subscribers>=1 → 有人连着，即时投递是活的
```

**这是我（服务器侧）能看到的唯一证据。** App 内部状态、有没有被系统限制，
服务器一概看不见 —— 但"有没有连着"是能看见的。

累计统计一拉出来，问题一目了然：

```
1126  subscribers=0
  46  subscribers=1
```

**1164 分钟里只有 46 分钟是连着的（4%）。** 也就是说绝大部分时间它是断的，
难怪消息都要等到打开 App 才补上。

### 3.3 用户侧的设置

原因一是我改代码就完事，原因二**必须用户在手机上做**。给她的清单（按重要性）：

1. **别从最近任务里划掉它** —— 更省事的是**把它锁定**（下拉卡片 → 点锁图标），划都划不掉
2. **电池 → 不受限制**（关掉电池优化）
3. **国产 ROM 还有两层额外开关**：允许**自启动** + 允许**后台运行**
4. 那条**常驻通知**要留着 —— 它就是"连接活着"的指示灯，关掉等于关掉即时投递

> 这里有个概念要跟用户讲清楚：**"保持前台"不等于"界面必须开着"。**
> 准确说法是**"进程必须活着"**。切到别的 App、锁屏、干别的，都不影响；
> 唯一不能做的就是**把它弄死**。

### 3.4 验证

用户设完回来说"挂好了"。这时候不能只看一眼现在连没连 —— 得看**能不能一直连着**：

```
19:53  subscribers=0
19:54  subscribers=0
19:55  subscribers=0     ← 她在做设置
19:56  subscribers=1
...
20:07  subscribers=1     ← 连续 12 分钟没断
```

**12 分钟连续不断**，对比之前的"清一色 0"，这就是决定性的差异。
（顺便说，19:53–19:55 那三分钟的空档正好就是她在操作的时候，时间也对得上。）

## 四、那有没有别的路？——没有

用户问了一个很自然的问题：**"也就是说我们必须保持前台是吗"**。

我查了一圈，答案是：**对自建推送来说，没有别的路。**

想在国产安卓上做到"**App 被杀也能秒收到**"，现实里只有两条：

| 方案 | 代价 |
|---|---|
| 接**厂商推送**（华为 / 小米 / OPPO / vivo Push）或第三方推送（个推、极光） | 得让 App 内置对应 SDK —— **ntfy 没接**，我们自己也改不了 |
| 走**微信**这类有系统级推送的通道（Server酱 / WxPusher 之类） | 消息**要经过第三方服务器** |

**第二条我主动排除了。** 理由和之前砍掉第三方看板完全一样：
这个推送里跑的是 AI 的梦、AI 的念头，而那些内容**是从记忆库里取材生成的**。
把它们送到别人的机器上过一遍，等于把私人内容交出去。

**所以结论是**：保持进程活着，是目前**唯一不经过第三方**的办法。
这不是我们服务器的缺陷，**任何一个自建推送服务在国内安卓上都这样。**

## 五、这件事真正的教训

### 5.1 静默失败是最贵的失败

一个字段没写，功能就**整个形同虚设** —— 而且它不报错、不崩溃、日志里一切正常。

更麻烦的是它会**伪装成"本来就这样"**：用户看到"有通知啊"，就会以为
"哦，推送大概就是不弹的吧"。**如果她没来问这一句，这个 Bug 会一直躺在那儿。**

所以排查这类问题时，**别只读代码，去读真实发出去的数据。**
代码里"没写这个字段"和"实际发出去是空的"是两回事，而后者才是用户看到的东西。

### 5.2 分清"我的 bug"和"平台的限制"

这次两个原因**现象一模一样**（都是"不弹/不及时"），但性质完全不同：

- **priority 没设** → 我的 bug，改代码就完事，**而且它放大了第二个问题**
- **FCM 不可用** → 平台的墙，只能靠设备侧配置绕过

**如果不分开，就会一直修不好**：比如只让用户去关电池优化，那弹窗依然不会有；
或者只改 priority，那 App 一被杀还是收不到。

排查的时候先把现象**拆成互不依赖的几条**，一条条验证 ——
**"看起来是同一个问题"往往是最容易骗人的地方。**
