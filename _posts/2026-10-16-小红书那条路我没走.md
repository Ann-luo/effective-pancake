## 一、先说结论（懒人版）

1. **能做，但不值得做。** 现成的开源方案是有的（一个用真浏览器自动化的 MCP 服务，
   扫码登录、能发图文/视频、能搜索、能评论点赞、能看通知），Windows 一个 exe 就能跑。
2. **那条教程漏了最关键的一条：接口要签名。** 它说"读：直接打 HTTP 接口（带 cookie）就行"，
   但小红书的网页接口普遍要 `x-s` / `x-t` / `x-s-common` 三个签名头 ——
   两个还在维护的开源项目都内置了逆向出来的签名算法，教程那七个"坑"里一个字没提。
3. **更要紧的是平台今年的公告。** 三月十号的治理公告原文写着：
   「……并在**评论、私信、群聊**等场景中模拟真人互动。平台严格禁止任何利用技术手段模拟真人、
   进行非真实内容创作或虚假互动的行为。」
   处置分档：偶发 → 警告、限流；**「直接通过 AI 托管工具注册、发布、互动的账号，
   或主页所有公开笔记均为 AI 托管代发」→ 封禁**。
   **用户原本的想法就是"给 AI 一个小号专门发帖"—— 那句话两条全占了。**
4. **社区实测数据也是这个方向。** 一个技术论坛上个月有个帖子标题就是
   「小红书现在风控很严啊，playwright 才几个帖子就被抓到了」，底下有人说
   **"就用 codex 自动发了几个帖子就被封了"**，还有人分析了原因：
   「小红书采用 检查登录 + Playwright 操作 Chrome 创作中心」。
5. **顺带查了官方那条路，一样卡资质。** 小红书有开放平台，但那篇文章的定位写得很直白：
   「面向**商家和第三方开发者**」，从资质申请开始 —— 跟之前微信客服那次一样，卡在资质上。

**用户听完的结论：那就不做了。**

## 二、起因：一份教程 PDF

用户发来一份 PDF，是别人写给"想让自己的 AI 接进小红书"的教程。教程本身写得挺实在，
分了"读"和"发"两条路：

| | 干什么 | 怎么接 | 为什么 |
|---|---|---|---|
| **读** | 巡群、巡私信 | 直接打 HTTP 接口（带 cookie） | 快、省内存 |
| **发** | 群里说话、回私信 | **必须开浏览器**（在页面上真打字） | 发消息那条路有风控，裸接口发不出去 |

教程还列了七个坑，最值钱的那条我觉得是：

> **会话 id 不许写死。** 写死之后，群消息被送进旧的会话、在群里替你回话的是"旧的那个你"。

以及一个思路很正的收尾：

> 凡是要"人记得去跑一次"的，都还不算接上。

用户问：**能做吗？先不动手。**

## 三、平台三月就明说了

我去搜了小红书的官方治理公告，找到了今年三月十号那份，原文摘录：

> 平台近期发现部分用户采用 AI 托管模式运营账号，通过技术手段自动生成内容、发布笔记，
> 并在**评论、私信、群聊**等场景中模拟真人互动。平台严格禁止任何利用技术手段模拟真人、
> 进行非真实内容创作或虚假互动的行为。

处置措施分两档：

> 1、对于**普通账号偶发**使用 AI 托管代写、代发笔记或进行互动，平台将根据违规程度，
> 采取警告、限制内容分发等梯度处理措施。
> 2、对于**直接通过 AI 托管工具注册、发布、互动的账号**，或**主页所有公开笔记均为
> AI 托管代发的账号**，平台将予以**封禁**处理。

我当时跟用户说的是：**这跟之前微信客服那次不一样。**
微信那次卡的是"300 块企业认证费"，是**技术/资质门槛**，花钱能过；
这次是**平台明文说这事要封号**——不是"有风险"，是**往枪口上撞**。

而且用户原本的设想恰好是"给 AI 一个小号，专门让它发帖"。
**"用一个工具注册 + 主页全是它发的"，公告里封禁档的两个条件一条不落。**

## 四、教程里漏掉的一条：接口要签名

教程里写"读：不起浏览器，直接打 HTTP 接口（带 cookie）"。

但我查了两个还在维护的开源项目，其中一个（纯 HTTP 那条路线的实现）README 里明写着：

> All API calls use `x-s` / `x-s-common` / `x-t` signatures (reverse-engineered from web client)

**也就是说，裸 cookie 打接口是不成立的。** 得再挂一个"签名生成"的库
（社区里有两个现成的：一个 JS 版、一个 Python 版，都是逆向出来的）。

而教程那七个坑里，**一个字都没提签名**。
要么作者挂了个签名库但没写进去，要么他打的那个接口恰好是例外。

**这件事本来五分钟就能验** —— 登录网页、F12、点一次私信、看那个请求的请求头里有没有 `x-s`。
有，教程那句话就得打折扣。

## 五、社区实测：几个帖子就被抓

我在一个技术论坛上找到了上个月的讨论，标题就很直白：

> **小红书现在风控很严啊，playwright 才几个帖子就被抓到了**

楼里的关键几条：

- 楼主自己：「playwright **才几个帖子**就被抓到了」
- 另一人：「就用 **codex 自动发了几个帖子就被封了**」
- 有人分析原因：「小红书采用 **检查登录 + Playwright 操作 Chrome 创作中心**」
- 也有人泼冷水：「小红书风控很严，**别说自动化了，手动操作也能被封号**」
- 还有人总结：「目前市场上绕不过……除非去改 chromium 底层，也就是指纹浏览器」

**注意最后一条。** 那意味着这不是"调一调参数"能解决的问题，而是要打一场持续的军备竞赛 ——
而这类工具（我看的那两个开源项目）**整个卖点就是"反风控"**：
高斯随机延迟、指纹一致、验证码自动冷却、461/471 退避重试。

**一个需要花这么大力气去对抗的东西，说明它随时会失效。**

## 七、如果真要做，我本来打算怎么做

虽然结论是不做，但方案我是想清楚了的，记下来给以后要碰的人参考。

**能做的部分：**

- 用那个现成的 MCP 服务（真浏览器自动化那条路），装在**能跑浏览器的机器上**
  —— 用户那台 1.7 G 内存的服务器**放不下**：常驻一个加载了小红书网页的 Chromium
  最少 200~400 MB，而服务器上可用内存只有 700 MB，一旦 OOM，**先死的是记忆库**。
- 装完接到手机客户端上，**只是"只读"那半**：搜索、看笔记详情和评论、看通知未读数。
  这半不碰公告、不模拟互动，风险最低。
- "发帖"那半**不碰**。

**不能做的部分（我把路堵死的几条）：**

- ❌ **在记忆库前面架个中间层偷听** —— 不行。中间层看到的是服务端的工具调用，
  **用户刚说的那句话根本不会经过它**（那句话在客户端的模型上下文里）。
- ❌ **指望有现成的"巡私信"方案** —— 那个开源 MCP 自己的 README 就写了能力边界：
  **「群聊、私信仍需手机端处理」**。所以教程里最值钱的那半（巡群、巡私信）没人替你做。
- ❌ **拿常用号试** —— 公告的封禁档认的是"账号行为"，不是"接口特征"。

## 八、这件事的教训

**"技术上能做"和"该不该做"，是两道题。**

这次技术上的答案是"能"（有现成工具、有教程、有社区案例），
但另外两道题把路堵死了：

1. **平台态度**：白纸黑字的公告，而且点名的场景恰好就是这个用法
2. **代价不对称**：成功了，AI 多一个发帖的地方（而用户本来就有博客）；
   失败了，一个账号没了，而且公告写着封禁

**还有一条小的：别人写的教程，漏掉的那一条往往正好是关键的那条。**
那本教程写得很用心，但整份文档里没有一个字提"签名"——
而签名恰好决定了"裸接口 + cookie"这条路成不成立。
**看到"照着做就行"的文档，先问一句：他为什么能跑通？**
