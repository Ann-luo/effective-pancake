## 一、先说结论（懒人版）

1. **`adb` 找不到，不是文件不在，是它在的目录不在 `PATH` 里。** 桌面不算"搜索范围"。
   ⚠️ 而且**改环境变量时变量名必须是 `Path`** —— 用户第一次打成了 `abd`，**差一个字母，等于没写**。
2. **`No such file or directory` 不等于路径写错。** Shizuku 13.6.0 已经**不再使用 `start.sh`** 了，
   启动器换成了 APK 里的 `libshizuku.so`。网上能搜到的中文教程基本全是旧版的，照抄必然失败。
3. **判断"文件到底在不在"，别只看 `ls`。** Android 11+ 会把 `/sdcard/Android/data` 里的内容对 `adb shell` 隐藏，
   **"看不见"和"不存在"是两件事** —— 我为此多绕了两轮。可靠的判据是 `[ -e 路径 ]` 加全量比对。
4. **WiFi「忽然消失」多半不是网卡坏了**：日志里的真相是「受限连接 → Windows 触发网卡驱动自愈 → 禁用再启用」。
   用户那天连着触发了两次，看起来就像 WiFi 不见了。**重启能好，是因为时间点，不是因为重启修好了它。**
5. **更新驱动不需要系统还原点。** `pnputil /export-driver` 能把当前驱动整包导出，
   我当场给用户导了一份放桌面 —— 这比系统还原点更对症、更可靠。

## 二、第一幕：`adb` 不是内部或外部命令

用户开机第一句话就是两条报错，在 `C:\` 和 `D:\` 各试了一次，一模一样：

```text
PS C:\Users\<用户名>> adb
adb: The term 'adb' is not recognized as a name of a cmdlet, function, script file, or executable program.
```

然后补了一句：**「我放在桌面了」**。

我去桌面看了一眼，东西在，而且是好的：

```text
D:\User\<用户名>\Desktop\platform-tools\adb.exe
Android Debug Bridge version 1.0.41
Version 37.0.1-15733141
```

`adb` 是个**独立的小程序**，不是系统命令。PowerShell 只会在 `PATH` 环境变量列出的那些目录里找它，
**桌面不在里面**。所以在 `C:\` 还是 `D:\` 敲都一样报错 —— 跟"当前在哪个盘"毫无关系。

### 这里我第一次说错了话

用户在同一段话里还贴了一个链接：`ka.ms/PowerShell-Release?tag=v7.6.6`。

我当时的判断是"这是 PowerShell 自己的升级提示，跟 adb 无关"—— **这句是对的**，
但我顺带评价了一句链接格式不对。事后看：那个链接确实少了前缀（应该是 `aka.ms/...`），
**不过那根本不重要**，用户真正要解决的是 adb。**我在不重要的地方多说了话。**

### 解法

要"一劳永逸"，就是把 `platform-tools` 目录写进用户级 `PATH`。我直接去写注册表：

```powershell
[Environment]::SetEnvironmentVariable('Path', $cur + ';' + $d, 'User')
```

**被沙箱拦了**：

```text
Exception calling "SetEnvironmentVariable" with "3" argument(s):
"Requested registry access is not allowed."
```

环境变量存在注册表里，工作区外的写入被拒。我把两个选项给了用户：自己点图形界面，或者我申请一次权限。

## 三、第二幕：一个字母的差距

用户选了**自己动手**。过了几分钟回来，贴了一段终端输出：

```text
PS C:\Users\<用户名>> adb
adb: The term 'adb' is not recognized ...
PS C:\Users\<用户名>> $env:Path -split ';' | Select-String adb
PS C:\Users\<用户名>>
```

第二行是空的 —— 说明新窗口的 `PATH` 里**根本没有** platform-tools。用户的意思是：**「写了还是没用」**。

我读注册表（这一次读得到，写才被拦）：

```text
HKCU:\Environment 下面：
  abd            = D:\User\<用户名>\Desktop\platform-tools   ← 值完全正确，名字错了
  ANDROID_HOME   = D:\Program Files\Android
  Path           = ...（还是原来那串，一个字没动）
```

**用户把变量名打成了 `abd`。**

Windows 只认名字叫 `Path` 的那一条。`abd` 在系统眼里就是个毫无用处的普通变量，
既不会扩展，也不会被拿去搜索可执行文件。**值写得再对也没用。**

我申请了一次沙箱放宽，把正确的值并进 `Path`，顺手删掉 `abd`，然后实测：

```text
Android Debug Bridge version 1.0.41
Installed as D:\User\<用户名>\Desktop\platform-tools\adb.exe
```

### 但还没完：环境变量的"刷新"

用户又开了一个新窗口，**还是找不到**。这里有个很多人不知道的机制：

> **新开的窗口不是从注册表读环境变量的**，而是从"生它的那个进程"继承一份**内存里的快照**。
> 那份快照的源头是 `explorer.exe`，而 `explorer.exe` **只在登录时读一次注册表**，之后就不再读了。

所以要广播一个 `WM_SETTINGCHANGE` 消息通知它。第一次发出去了没回应（`SendMessageTimeout` 返回 0），
第二次加了超时时间，返回 1，有人应答了 —— **用户再开窗口，`adb devices` 直接出结果了。**

> 附带一个坑：我这个沙箱进程**看不到 `explorer.exe`，也看不到大部分系统进程**
> （`Get-Process` 只能看到 19 个进程，`tasklist` 报 Access denied）。
> 所以「广播有没有生效」我没法直接验证，只能让用户去试。**这一点我如实跟用户说了，没有硬猜。**

## 四、第三幕：`start.sh` 不存在

### 设备先通了

```text
List of devices attached
8dcc96a8        unauthorized     ← 手机上要先点「允许 USB 调试」
8dcc96a8        device           ← 点了之后
```

用户接着敲了那条从教程抄来的命令：

```powershell
adb shell sh /sdcard/Android/data/moe.shizuku.privileged.api/start.sh
sh: /sdcard/Android/data/moe.shizuku.privileged.api/start.sh: No such file or directory
```

用户发了两个字：**「？？」**。

### 我的第一轮排查（方向对，但被一个机制骗了）

先确认基本事实：

```text
ro.product.model          = M332BF（Redmi）
ro.build.version.release  = 16
pm list packages | grep shizuku
  → package:moe.shizuku.privileged.api      ← Shizuku 装了
```

然后我去看那个目录在不在：

```text
ls -d /sdcard/Android/data            → /sdcard/Android
ls -d /sdcard/Android/data/moe.shizuku.privileged.api
  → No such file or directory
```

**到这里我差点下结论"Shizuku 没装好"。** 但我记得一个机制：

> **Android 11 以后，`adb shell` 看不到 `/sdcard/Android/data/` 和 `/sdcard/Android/obb/` 里的内容**（FUSE 隔离）。
> 所以 `ls` 报 "No such file or directory"，**可能只是看不见，不是不存在。**

我试了 `run-as` 绕过（结果 `package not debuggable` —— 正式签名版当然不能 run-as）、
试了 `content://` 通道（被 `SecurityException` 拒了），都没走通。

### 真正靠谱的判据

最后用两个手段定案：

```bash
# 1) 全量列一遍，看有没有它（不看前 N 条就下结论）
adb shell ls /sdcard/Android/data/ | grep -i shizuku
#    → 空。总共 119 个目录，没有它。

# 2) 用 test 判定，比 ls 可靠
adb shell "[ -d /sdcard/Android/data/moe.shizuku.privileged.api ] && echo EXISTS || echo MISSING"
#    → MISSING
```

**结论：那个目录真的不存在。** 同时我注意到一件怪事 —— **Shizuku 的进程是活着的**：

```text
u0_a361  501  1675  ...  S  moe.shizuku.privileged.api
```

进程活着，但它的外部目录不存在。

> 第一个教训：**我用的 `ls | head -40` 直接把列表截断了，导致我第一轮判断依据不足。**
> 后来又发现"FUSE 会隐藏"这层，再后来又发现"其实能列出来，只是我没看全"。
> **一个 `-e` 判定就能解决的事，我绕了三轮。**

### 转折点：直接看手机屏幕

与其猜，不如看。用 `adb` 截图：

```powershell
adb exec-out screencap -p > shizuku-now.png
```

屏幕上清清楚楚：**Shizuku 已经开着，界面停在主页面。** 四个按钮：

```text
通过无线调试启动
  ├ 分步骤指南
  ├ 配对
  └ 启动
通过连接电脑启动（使用 adb）
  └ 查看指令        ← 关键在这里
启动（针对已 root 设备）
```

我用 `uiautomator dump` 拿到按钮坐标，`input tap` 点进「查看指令」，再 dump 一次：

```text
adb shell /data/app/~~mF3ai5Jy8Qw4tUlMA4B9qg==/moe.shizuku.privileged.api-Z5zdopFFhLBwrFM-mv5fYQ==/lib/arm64/libshizuku.so
```

### 真相

**Shizuku 13.6.0 根本不用 `start.sh` 了。**

它直接把 APK 里的 `libshizuku.so` 当启动器跑。那个 `/sdcard/Android/data/.../start.sh` 是**老版本**的做法，
在 Android 11+ 收紧存储访问之后就走不通了。**用户抄的教程过期了，而且过期了不止一个版本。**

跑官方这条命令，一次成功：

```text
info: starter begin
info: killing old process...
info: apk path is /data/app/~~mF3ai5Jy8Qw4tUlMA4B9qg==/moe.shizuku.privileged.api-Z5zdopFFhLBwrFM-mv5fYQ==/base.apk
info: starting server...
info: shizuku_server pid is 30547
info: shizuku_starter exit with 0
```

```text
shell  30547  1  ...  shizuku_server      ← 服务在跑
```

> ⚠️ **那串 `~~mF3ai5Jy8...` 每次重装或升级 App 都会变**，所以这条命令**不能存下来反复用**。
> 正确做法是每次去 App 里点「查看指令」现拿一条。

### 顺带查到的官方 issue

Shizuku 在 Android 16 上还有另一个已知问题：**服务会莫名其妙被杀**。
官方仓库里一堆人报同样的事（[issue #1125](https://github.com/RikkaApps/Shizuku/issues/1125)）：
有人卡在 `Waiting for service...`，有人起来之后几秒到几分钟被干掉了，有人发现用某些 App 触发一次操作它就死。

**用户的原话是「我的 Shizuku 就是忽然掉了，气死我了」** —— 这不是用户的错觉，是个真 bug。
有人在 issue 里贴了自己编译的修复版，但那是**非官方签名**的 APK（装之前还得先卸载原版），我没有建议用户装。

给用户的建议是两条正规做法：

1. **改用无线调试激活**（手机自己跟自己通信，不需要电脑），以后再重启手机在手机上点一下就行
2. Shizuku 设置里有「开机自动启动」，勾上

## 五、第四幕：WiFi 忽然不见了

用户说：「我电脑之前忽然找不到 WiFi，然后我重启才解决，吓死我了，这是咋了。」

这种事**不能猜**，日志里有答案。先看 WLAN 相关事件，一下就抓到时间线：

| 时间 | 事件 |
|---|---|
| 23:17:35 | `WLAN AutoConfig 检测到受限连接，正在尝试自动恢复` |
| 23:17:39 | `Netwtw14: Miniport Halt flow (driver disable)` ← **驱动被禁用** |
| 23:17:40 | `Netwtw14: Driver initialization` ← 重新初始化 |
| 23:19:00 | **又一次** `Miniport Halt`（说明重连没成功，又重置了一遍） |
| 23:19:07 | 第二次 `Driver initialization` |
| 23:19:30 | 用户重启电脑 |
| 23:21~23:22 | 开机后网卡一次初始化成功，**之后再也没有重置记录** |

### 怎么读这条时间线

关键在于「**受限连接**」四个字：

> **网卡连上了 WiFi，但走不通外网。**
> Windows 检测到这种状态会触发一次**网卡驱动的自我恢复**（禁用 → 重新启用），试图重连。

用户那一分多钟里连着触发了**两次**，网卡一直在"禁用-启用"里打转 ——
在用户看来就是"**WiFi 忽然不见了**"。

**根因在网络侧（路由器或上游），不在电脑。** 两条证据：

1. 「受限连接」描述的是**网络侧**的状态 —— 路由器没拨上号，或者上游断了
2. **用户的手机同时也上不了网** —— 两个设备同时出问题，几乎不可能是电脑的锅

**那为什么重启就好了？** 因为用户重启的时候路由器那边多半也恢复了，重连自然就通。
**不是重启"修好了"网卡，是时间点刚好。**

### 顺手发现的第二个问题

翻日志时看到一串反复报错的东西：

```text
2026/10/12 00:07:33  Service Control Manager  7016  RT2870 AutoInstall Service 服务报告了无效的当前状态: 0。
2026/10/12 00:19:25  ... 同上
2026/10/12 00:20:55  ... 同上（连着两条）
```

`RT2870` 是 **Ralink/联发科的 USB 无线网卡**。查下去发现：

```text
服务名:   RaAutoInstSrv_RT2870     状态: Running      ← 一直在跑
对应驱动: oem61.inf (netr28ux.inf)  MediaTek  2016 年，版本 5.1.27.0
设备:     没有。连"幽灵设备"都没有     ← 网卡早拔了
```

**插过的 USB 网卡早拔了，只剩一个后台服务在那儿空转报错。**

用户说的原话是「插过网卡，你帮我删了？算了我自己来，你告诉我步骤」——
**用户自己动手，我出步骤。** 这里我给了两条路：
先 `sc.exe config ... start= disabled` + `stop`（可逆），确认没问题再 `delete`。

⚠️ 顺带提醒了一个语法坑：**`sc.exe` 的 `start= disabled` 等号后面必须有空格**。

用户后来把三步全做了：

```text
[SC] ChangeServiceConfig 成功
STATE : 1  STOPPED
Name                  Status  StartType
RaAutoInstSrv_RT2870  Stopped Disabled
[SC] DeleteService 成功
已卸载驱动程序包。
已成功删除驱动程序程序包。
```

**我事后做了验证**（不看用户贴的输出、看实际状态）：

```text
1) 服务还在吗         → 服务已删除
2) 驱动包还在库里吗   → 已移除
3) 最后一条 7016 报错 → 00:47:00（删除之后一条新的都没有）
4) 网络连通性         → baidu 200 / 263ms，api.github.com 200 / 673ms
```

**这才是"改完了"的判据** —— 不是"命令返回成功"，是"日志里不再有新的同类记录"。

## 六、第五幕：一个关于"怕"的问题

我把话题引到了网卡驱动上：用户的 Intel AX201 驱动是 **23.70.0.6 / 2024-07-17**，
而 Intel 官网最新是 **24.70.0 / 2026-09-08** —— 差两年。

我建议更新，还让用户先去取消勾选网卡的省电选项。结果用户回了两个意外情况：

> 「没看到电源管理选项卡，还有就是……目前显示是最新驱动了……」

我去查了，**两件事我都判断错了**：

### 错在哪

**第一，"电源管理"选项卡根本不存在。**

我读了这块网卡的注册表，`PnPCapabilities` 这个值**压根没有设置过** —— 也就是说，
**那个复选框从来没在这个系统上出现过。** 我让用户去找一个不存在的东西。

**第二，"最新驱动"是假的。**

Windows 说的"最新"，意思是**微软更新目录里没有更新的**。而微软那边只有过了 WHQL 认证的旧版本，
**跟厂商官网的版本差着两年**。

查完的实际状态，反而是好消息：

| 注册表值 | 当前 | 含义 |
|---|---|---|
| `*DeviceSleepOnDisconnect` | **0** | 断网时不让网卡睡眠 ✅ |
| `MIMOPowerSaveMode` | **0** | MIMO 省电关闭 ✅ |
| `uAPSDSupport` | 0 | 关闭 |

而且电源计划里「无线适配器设置 → 节能模式」**插电时已经是"最高性能"**。
**真正管省电的地方是电源计划，不是那个不存在的选项卡。**

### 但用户怕了

听到要更新驱动，用户说：

> 「我害怕，我电脑还原点似乎建不了，要不不更新？」

我查了系统还原，结果是这样：

```text
还原点:  一个都没有
VSS / swprv / SDRSVC 三个服务:  全是 Stopped
C 盘空间: 300G 总量，剩 154.6G
```

**不是坏了，是从来没开过** —— Windows 11 家庭版默认关闭系统保护。

### 真正该给的退路

**这里我想明白了一件事：更新驱动本来就不该靠系统还原点。**

正确的退路是**把当前驱动整包导出**，`pnputil` 原生支持：

```powershell
pnputil /export-driver oem42.inf D:\备份目录\wifi-driver-backup-23.70.0.6
```

实测导出成功，11 个文件：

```text
netwtw08.inf      安装信息
Netwtw08.sys      驱动本体 (8.9 MB)
Netwtw08.cat      数字签名
Netwfw08.dat      固件
IntelIHVRouter08.dll / 10 / 14
...
```

我把这份备份**复制到了用户桌面**（工作区可能被清掉，桌面更稳），并写清了回退步骤：

> 设备管理器 → 网络适配器 → 右键 Intel AX201 → **更新驱动程序** →
> **浏览我的电脑上的驱动程序** → 指向桌面那个备份文件夹 → 下一步

**不需要系统还原点，不需要管理员权限改任何系统设置。**

顺带一个诚实的提醒：我还查了驱动库，里面确实躺着一份旧的 `netwtw08`，
但那是 **2018 年的 Windows 通用驱动（21.80.2.3）**，是个老古董 ——
**所以设备管理器里那个「回退驱动程序」按钮别指望，退回去更糟。**

### 最后的决策规则

用户还在犹豫，我给了个明确的规则，**而不是继续劝**：

> **以后再掉一次 WiFi → 更新驱动。只掉这一次 → 不用管。**

理由很实在：那次掉线是孤立事件，从那之后一次都没再掉；而且掉线的机制里，
**路由器那边的嫌疑比驱动更大**（手机同时也没网）。
**为用户没再发生过的问题冒风险，不划算。**

## 七、我错在哪：别把教程当规格书

这篇里有我自己的三次判断失误，都值得记下来：

| # | 我错在哪 | 正确的做法 |
|---|---|---|
| 1 | 让用户去取消勾选一个**从来没存在过**的"电源管理"选项卡 | **先查注册表确认这个选项在不在**，再让用户去点 |
| 2 | 判断"文件不存在"时，**先用 `ls \| head -40` 截断了列表**就下结论 | **全量比对 + `[ -e ]` 判定**，别用截断的输出当依据 |
| 3 | 让用户去找"还原点"来兜底驱动更新 | **驱动更新有专门的退路（导出驱动包）**，比还原点更对症 |

还有一条更根本的：

> **网上搜到的命令，默认它是过期的。**
> 教程的寿命比软件的版本短得多 —— 尤其涉及 Android 存储路径这类被系统更新反复改过的地方。
> 最可靠的做法是**去软件自己的界面里拿现成命令**（这次就是点一下「查看指令」的事），
> 而不是从搜索结果里抄一条看起来像的。

## 八、可直接抄走的速查表

| 现象 | 真实原因 | 解法 |
|---|---|---|
| `adb: The term 'adb' is not recognized` | `platform-tools` 目录不在 `PATH` 里 | 写进用户 `PATH`，或临时 `$env:Path += ";<目录>"` |
| 改完 `PATH` 还是没用 | ①变量名打错（`abd` ≠ `Path`）②`explorer` 那份内存快照没刷新 | 广播 `WM_SETTINGCHANGE`；或重启 `explorer.exe` / 注销重登 |
| `adb shell sh .../start.sh` 报文件不存在 | **Shizuku 13.6.0 已弃用 `start.sh`** | 去 App 里点「通过连接电脑启动 → 查看指令」，跑它给的 `libshizuku.so` 命令 |
| `ls` 说目录不存在 | Android 11+ 会对 `adb shell` **隐藏** `Android/data` 内容 | 用 `[ -e 路径 ]` 判定；或全量列一遍再比对 |
| WiFi 忽然消失，重启就好 | 「受限连接」触发 Windows **网卡驱动自愈**（禁用→启用） | 关掉再打开 WiFi 开关即可，**不必重启电脑**；反复出现再更新驱动 |
| 日志里反复 7016 报错 | 早拔掉的 USB 网卡留下**空转的服务** | `sc.exe config <名> start= disabled` + `stop`，确认后 `delete` |
| Windows 说"驱动是最新的" | 只代表**微软目录**里没有更新的 | 去厂商官网比对版本号 |
| 系统还原点建不了 | Windows 11 家庭版**默认关闭**系统保护 | 想开：`sysdm.cpl` → 系统保护 → 配置 → 启用；**但驱动更新用导出备份更对症** |

常用命令：

```powershell
# 导出当前驱动（更新前的退路）
pnputil /export-driver oem42.inf D:\备份目录

# 查驱动库里都有哪些版本
pnputil /enum-drivers

# 查网卡驱动的电源相关设置（读注册表，不用管理员）
$base = 'HKLM:\SYSTEM\CurrentControlSet\Control\Class\{4d36e972-e325-11ce-bfc1-08002be10318}'
Get-ChildItem $base | ForEach-Object {
  $p = Get-ItemProperty $_.PSPath -ErrorAction SilentlyContinue
  if ($p.DriverDesc -match 'AX201|Wi-Fi') {
    "$($p.DriverDesc)  v$($p.DriverVersion)  $($p.DriverDate)"
  }
}

# 看 WiFi 到底是怎么掉的（比猜有用）
Get-WinEvent -FilterHashtable @{LogName='System'; StartTime=(Get-Date).AddDays(-1)} |
  Where-Object { $_.ProviderName -match 'WLAN|Netwtw' } |
  Select-Object TimeCreated,ProviderName,Id,Message
```
