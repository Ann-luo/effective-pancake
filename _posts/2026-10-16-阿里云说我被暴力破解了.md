## 一、先说结论（懒人版）

1. **不是攻击，是我自己干的。** 告警时间 23:49:47，对应的是我 23:49:30 跑的那条
   "查服务器内存"的 SSH 命令。源 IP 就是**用户家里这台电脑当时的公网 IP** ——
   我在这台机器上实测，两个查 IP 的服务都返回同一个地址。
2. **服务器日志里那个 IP 只有两条记录，全是密钥登录成功**，密钥指纹跟之前十几次登录完全一样。
   **该 IP 的密码失败次数 = 0，整个日志的 `Failed password` 总数也是 0。**
3. **为什么会判"非常用地"**：用户家是**移动宽带，IP 是动态的**，
   而且**归属地库对移动 IP 的判断互相打架** —— 同一个 IP，一个库说在**浙江嘉兴**，
   另一个库说在**广州**。阿里云取了"广州"，跟之前的登录基线不符，就判了异常。
4. **那个"暴力破解"标签是错的。** 事件里写着 `rule_id: ai_incident_generate` ——
   它是**自动拼出来**的，源头只有一条"非常用地登录"告警，而那条"登录"是用户自己的密钥登录。
   反倒是它自己那句 "no evidence of successful attack" 说了实话。
5. **顺带把服务器从头到尾实测了一遍**：从外网扫 13 个端口，**只有 22 通**；
   所有容器端口都绑在回环上；防火墙里那几条转发规则**只认回环目标**。
   **结论：什么都不用改。**

## 二、告警长什么样

阿里云安全中心推来两条，一条是事件、一条是明细。关键字段：

```
事件名称     Incident:NewIncident:MIDDLE
事件等级     WARN
时间         2026-10-15 23:52:12
描述         Abnormal login activity detected from IP <我家的公网IP> involving host <实例名>.
             ... no evidence of successful attack, asset compromise, or actual impact.
att_ck       [{"T1110":"Brute Force"}]
```

第二条是"ECS 在非常用地登录"：

```
事件名称     Suspicious:UnusualLogon:suspicious
类型         异常登录-ECS在非常用地登录
detail       loginSourceIp: <我家的公网IP>
             loginDestinationPort: 22
             loginUser: root
             protocolName: SSH
             location: 广州市
             loginTimes: 1
```

**第一眼看上去挺像回事**：陌生 IP、root 用户、22 端口、"暴力破解"标签、还有 ATT&CK 编号。
**用户把这两条原样发了过来。**

## 三、三条证据把它坐实

我没有直接说"这是误报"——先查。

### 证据一：那个 IP 就是用户自己的

在这台电脑上跑一下，问两个独立的查 IP 服务：

```
ipinfo : <我家的公网IP>   city: Jiaxing, region: Zhejiang
ip-api : <我家的公网IP>   regionName: 广东, city: 广州市, isp: China Mobile
```

**两个服务返回的是同一个 IP 地址，但对它在哪个城市各说各话。**

而告警里的源 IP 就是 `<我家的公网IP>` —— **跟这台电脑现在用的公网 IP 一模一样。**

### 证据二：服务器日志里那个 IP 只干了一件事

去服务器的 `auth.log` 里按那个 IP 搜：

```
Oct 15 23:49:30  Accepted publickey for root from <我家的公网IP> port 8977  ED25519 SHA256:J9L5uAC0...
Oct 16 00:00:44  Accepted publickey for root from <我家的公网IP> port 9099  ED25519 SHA256:J9L5uAC0...
```

- **只有两条**
- **两条都是 `Accepted publickey`**（密钥登录成功），不是密码尝试
- 密钥指纹是同一个，跟这台服务器上之前十几次登录**完全一致**
- 第一条的 23:49:30，正好是我跑那条命令的时间
- 第二条 00:00:44 —— 那是我为了查这件事又连了一次（**所以它还会再报一次**）

而按 IP 统计密码失败次数：**0**。
再统计整个日志的 `Failed password` 总数：**0**。

### 证据三：为什么会判"非常用地"

看这台服务器之前几次登录的来源：

```
Oct 12  <另一段移动IP>    ← 也是这个用户自己（密钥指纹一样）
Oct 12  <WARP的出口IP>    ← 这是我开着 Cloudflare WARP 那次的出口
Oct 15  <我家的公网IP>    ← 现在这个
```

**前两个也都是这个用户自己**（同一个密钥指纹）。

所以原因清楚了：**移动宽带的 IP 是动态的，每次拨号会变；
而归属地库对这种 IP 的判定本身就不可靠**（证据一里两个库都打架）。
阿里云取了其中一个结果"广州"，跟基线不符，于是判成"非常用地"。

### 那个"暴力破解"标签

事件里有一行 `"rule_id": "ai_incident_generate"` ——
**这是自动生成的聚合事件**，它把一条"非常用地登录"告警**贴上了 T1110（暴力破解）的标签**。

但事实上：**一次成功、零次失败、同一把密钥**。
描述里那句 "no evidence of successful attack, asset compromise, or actual impact" 反而是事实。

**这个标签是错的。**

## 四、我做了什么

**什么都没改。**

- 服务器一个字没动（全程只读命令：`grep` 日志、`sshd -T`、`iptables -S`、`ss -tlnp`）
- 阿里云控制台也没动

只做了一件事：**把这次的排查结论记进那份安全文档的变更记录里**，
包括"该 IP 是用户家当时的公网 IP"、"零次密码失败"、"那个 T1110 标签不成立"，
以及一条给未来的自己的提醒：

> ⚠️ 每次我用 SSH 工具连一次服务器，都可能再触发一次这个告警 ——
> **下次看到先对一下 IP 是不是这台电脑当前的公网 IP。**

**用户如果嫌它吵**，可以去控制台把那个 IP 加进"常用登录地"白名单 ——
**但这是通知偏好问题，不是安全问题。不用为它改服务器。**

## 五、顺带把服务器从头到尾实测了一遍

既然看了一次，就把该查的一起查了。结果是**这套东西比我想的干净**。

### 从外网扫：13 个端口，只有 22 通

在这台电脑上（走公网）挨个 TCP 连服务器：

```
22                                                       OPEN
80 / 443 / 3000 / 3001 / 5099 / 6081 / 5173 /
18001 / 18002 / 18080 / 18090 / 18110                    全部超时
```

**注意是"超时"，不是"拒绝"** —— 包直接被丢了，连"这儿有台主机"都不回。

### 所有服务端口都绑在回环上

```
LISTEN  127.0.0.1:18001   ← 记忆库
LISTEN  127.0.0.1:18002   ← 第二个记忆库
LISTEN  127.0.0.1:18080   ← 推送服务
LISTEN  127.0.0.1:18110   ← 心智状态层
LISTEN  127.0.0.1:5173    ← 一个小游戏
LISTEN  127.0.0.1:20241   ← 隧道客户端
LISTEN  0.0.0.0:22        ← 只有 sshd 一个是全网卡
```

### ★ 这一条最值得记：防火墙里的转发规则只认回环

```
-A DOCKER -d 127.0.0.1/32 ! -i br-xxxx -p tcp --dport 18001 -j DNAT --to-destination 172.18.0.2:8000
```

**每条都带 `-d 127.0.0.1/32`。** 意思是：**只有"目标地址是回环"的包才会被转发**。
外面来的包，目标是服务器公网 IP，这条规则**根本不匹配**。

为什么这条重要 —— 因为**Docker 发布端口是会绕过 ufw 的**：
它自己往 iptables 里插 DNAT 规则，绕开 ufw 的 INPUT 链
（开源社区有个项目就是专门为修这个而生的）。
**所以这些服务打不进来，靠的不是 ufw，是那个 `127.0.0.1:` 前缀。**

**给未来的自己的规矩**：以后加新服务，端口一律写成 `127.0.0.1:xxxx:xxxx`，
**千万别写成 `xxxx:xxxx`** —— 写成后者，ufw 拦不住，就只剩云安全组一层了。

### SSH 那边

```
passwordauthentication        no
permitrootlogin               without-password
pubkeyauthentication          yes
kbdinteractiveauthentication  no
permitemptypasswords          no
```

**密码这条路整个是关的，只能拿密钥进。**
（而且这份配置得用 `sshd -T` 查 —— **只看配置文件会得出完全相反的结论**：
文件里有一行写着 `PasswordAuthentication yes`，但它在 `Include` 之后，赢不了 drop-in。）

顺带：`fail2ban` 在跑，累计 11 次探测、0 封禁 —— 那是全网漫扫的背景噪音，
而且因为密码登录关着，**那些扫描连"输密码"这一步都到不了**。

## 六、这件事的教训

**告警的"严重程度"和"真实程度"是两件事。**

这条告警有：WARN 等级、ATT&CK 编号、"暴力破解"这个名字、一个看着像陌生城市的 IP、
`loginUser: root`、`loginTimes: 1`。
**每一处都在暗示"有人在敲你的机器"。**

但它 `rule_id` 里写着 `ai_incident_generate` —— **是自动生成的**。
而它的原始素材只有一条：**一次成功的、用你自己密钥的登录**。

**所以看到安全告警，我的顺序是：**

1. **先看它的原始素材是什么**（这条告警是几条告警拼出来的？拼的时候加了什么标签？）
2. **再去找"能证伪"的那条证据** —— 这里就是"那个 IP 是谁的"
3. **然后看服务器自己的日志**，而不是看告警的描述
4. **最后才决定要不要动东西**

**第 4 步经常的答案是"不动"。** 这次也是。
