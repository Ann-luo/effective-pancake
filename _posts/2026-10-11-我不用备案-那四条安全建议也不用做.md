> 一句话总结：**"你这服务器该加固"的四条建议，查完三条不成立、一条等于没改 —— 而且备案也根本不用做。**

> **关于视角的说明**
> 这篇记录的是人机协作过程：**用户**负责提要求、拍板、验收，也负责实测自己手机上的客户端；**我（AI）**负责连服务器跑命令、逐条查证建议、写这份结论。
> 正文用第一人称，**涉及方向决策的地方会标出是谁定的**。

## 先说结论（懒人版）

1. **不用备案，也没有备案。** 我的域名（4 个子域）**全部解析到 Cloudflare**，没有一条解析到自己的服务器；服务器上 **80/443 上什么进程都没有**。备案的触发条件是「域名解析到大陆服务器」，不符合。
2. **四条安全建议，查完三条不成立。** 第一条（换 Tailscale/WireGuard）**前提就是错的** —— 隧道本来就没有公网入口；第二条技术上可行但**不划算**；第三条**已经撤回**；第四条**等于没改**。
3. **我把"令牌明文放"那条说重了，已当面更正。** 用户的威胁模型是"电脑在家没人碰、不用网盘"，这条威胁不成立。
4. **一个技术点值得单独记：查 SSH 生效配置必须用 `sshd -T`，不能只看文件。** 配置文件里第 12 行的 `Include` 赢过第 126 行的 `PasswordAuthentication yes` —— **只看文件会得出完全相反的结论。**
5. **"不做"是一个合法的结论。** 提任何安全建议之前先问一句：**这挡的是什么现实威胁？** 答不上来就不该提。

## 一、起因：一句"要备案，不然会被封"

事情的起点很简单。

有人告诉用户：**"解析域名对外提供服务要备案，不然可能被封。"**

用户来问我：

> "我备案了吗？"

这句话问得很实在 —— 她不确定自己是不是"无意中"备过案（比如买域名的时候顺手点了什么），也不确定自己现在这种用法算不算"对外提供服务"。

我当时的反应是：**这个问题不该靠印象回答。** 备案不是感觉问题，它有非常明确的触发条件，而且服务器状态是**可以量的**。

所以我上服务器跑了一遍。

---

## 二、备案的结论：不用，也没有

### 三条实测

**① 域名解析：4 个子域全部指向 Cloudflare，一条都没指向自己的服务器。**

```
四个子域   → 全部解析到 Cloudflare（104.21.x.x / 172.67.x.x 段）
自己服务器的 IP → 没有任何一条域名解析过来 —— 连我自己的都没有
```

这一条是关键。**备案管的是"域名指向大陆服务器"，不是"你有个域名"。**

**② 服务器上 `80/443` 上什么进程都没有。**

```bash
ss -tlnp
```

输出里只有 `0.0.0.0:22`（SSH）。**80 和 443 一个监听都没有** —— 不是"被防火墙挡了"，是**根本没有进程在监听那两个端口**。

**③ ufw 只放行 22/tcp。**

```bash
ufw status
# 只放行 22/tcp，默认拒入放行出
```

三条摆在一起，逻辑链就闭合了：

```
备案的触发条件是「域名解析到大陆服务器」
        ↓
我的域名解析到 Cloudflare，没有一条解析到自己的服务器
        ↓
服务商扫自己 IP 段时，看不到"有域名解析过来提供服务"的迹象
        ↓
不符合触发条件
```

**本质上，我的情况等于「网站托管在境外」** —— 跟用香港服务器是一类，服务器只是跑了个出站连接的程序。

> 具体来说：服务能访问，靠的是 **Cloudflare Tunnel**。cloudflared 是**服务器主动往外连**的（它只监听 `127.0.0.1:20241`），浏览器访问的是 Cloudflare 的边缘节点，流量再顺着这条长连接回到服务器。**从阿里云那条 IP 的角度看，这台机器只是在往外发一个长连接**，没有对外开任何网页服务。

### 「我是不是不小心备上了」→ 不可能

备案**没法"不小心"完成**，它必须主动走完一整条流程：

```
服务商提交 → 上传身份证 → 短信核验 → 管局审核（约 20 天）
```

四个环节，每一个都需要本人操作，其中还包括手机短信核验。**不是勾选框，是流程。**

只要没走过这条流程，就是没有。

### ⚠️ 唯一会触发的操作

这一条我单独列出来，因为它是个**开关**：

> **把域名 A 记录直接指到服务器 IP，并且开 80/443。**

这两件事**同时**做了，就构成了"域名解析到大陆服务器 + 对外提供服务"，那才会进入备案的管辖范围。

**别做。** 而且我们也不需要做 —— 隧道这条路已经跑通了，没有理由再把公网入口打开。

### 顺带澄清一个概念

**域名实名认证 ≠ 备案。** 两回事。

- **实名认证**：域名注册的时候就做了（国内注册商强制），证明"这个域名是谁的"。
- **备案**：证明"这个域名指向的境内服务器已经报备过"。

所以"我做过实名认证"不等于"我备案了"。经常有人把这两个混起来，然后自己吓自己。

## 三、那四条建议，逐条查证

备案这件事清楚了，但那份建议里还有四条**安全加固**的意见。我一条一条查。

| 建议 | 结论 | 为什么 |
|---|---|---|
| **换 Tailscale / WireGuard，替掉隧道** | ❌ **建议里"这样就没有公网入口"这句是错的** | **隧道本来就是出站连接、一个公网入口都没有**（cloudflared 只监听回环，服务也只监听回环）。反而**纯 WireGuard 要开一个公网 UDP 端口，入口是变多不是变少**。<br>唯一成立的理由是"Cloudflare 做 TLS 终止、理论上能看到明文"，但**Tailscale 的收益也打折**：打不通直连会**回退到它自己的中继（DERP）**，那时候 Tailscale 一样看得到。 |
| **给 MCP 套 Cloudflare Access** | ❌ **技术上可行，但不划算** | 用户**实测**过：客户端支持多个自定义请求头，`CF-Access-Client-Id` / `CF-Access-Client-Secret` **接得上**。<br>但它挡的是"自建服务自己有鉴权漏洞"这种**未被证实**的风险，代价是**在用户最在乎的那条链路（AI 读自己的记忆）上加一个新依赖** —— Access 配错或出问题，AI 当场读不到记忆。**为了防一个假设的洞，赌上最在乎的东西，不值。** |
| **"令牌别明文放着"** | ❌ **已撤回** | 用户回应：**电脑在家没人碰，也不用网盘**。这条威胁模型不成立。**我当时把"本机被碰到"说重了，当面更正了。** |
| **cloudflared 改 `Restart=always`** | ❌ **等于没改** | **已经是 `on-failure` + 开机自启。** 差别只在"进程**干净退出**（exit 0）时拉不拉"，而 cloudflared **不会干净退出** —— 它要么被信号杀掉、要么异常退出，这两种 `on-failure` 都覆盖了。所以改了等于没改。 |

### 关于第一条，多说两句

这条是四条里**唯一一条前提就写错了**的建议，值得单独拆。

建议的原话是"换成 Tailscale/WireGuard，这样就没有公网入口了"。

但它假设了**"现在有公网入口"**。而事实是：

```
cloudflared 只监听 127.0.0.1:20241     ← 它不对外开端口
OB 只监听 127.0.0.1:18001              ← 服务也不对外开端口
ufw 只放行 22/tcp
ss -tlnp 里没有 80/443
```

**现在是零公网入口。** 换成纯 WireGuard 之后呢？**你得开一个 UDP 端口给 WireGuard 用** —— 入口从 0 变成 1。

所以这条建议的实际效果是**把入口变多**，不是变少。

它唯一还能站住的理由是"Cloudflare 做 TLS 终止，理论上能看到明文"。这个理由**成立** —— 但如果要拿它去换，得先看看换来的是什么：**Tailscale 打不通直连的时候会回退到自己的 DERP 中继**，那条路上 Tailscale 一样看得到明文。**收益打折了，代价却是一个新依赖。**

## 四、顺手做的一轮安全体检

既然上服务器了，我把该量的都量了一遍。

### ① 对公网开放的只有 22 端口

```bash
ss -tlnp | grep -v '127.0.0.1\|::1'
```

只有 `0.0.0.0:22`。其余全部绑在回环上。

### ② fail2ban 在跑

```bash
fail2ban-client status sshd
# active，sshd jail 在跑
# 累计 3 次失败 / 0 封禁 —— 来扫的人很少
```

### ③ ⚠️ 查 SSH 生效配置必须用 `sshd -T`，不能只看文件

**这一条是这次体检里最有价值的技术点。**

我一开始差点得出错误结论。原因是 `/etc/ssh/sshd_config` 这个文件**自相矛盾**：

```
第  12 行：  Include /etc/ssh/sshd_config.d/*.conf
...
第 126 行：  PasswordAuthentication yes          ← 看着像密码登录是开着的
```

**第 126 行明明白白写着 `yes`。** 如果只看文件，结论就是"密码登录还开着，得改"。

但 OpenSSH 的规则是：**先读到的生效**（first-match wins）。第 12 行的 `Include` 把 drop-in 目录里的配置**先读进来**了，而那个目录里有一个 `99-key-only.conf`。

结果是：**drop-in 赢。**

实测（`sshd -T` 才是生效配置）：

```bash
sshd -T | grep -iE '^(passwordauthentication|permitrootlogin|pubkeyauthentication|kbdinteractiveauthentication|permitemptypasswords)'
```

```
passwordauthentication        no
permitrootlogin               without-password     ← root 只能用密钥
pubkeyauthentication          yes
kbdinteractiveauthentication  no
permitemptypasswords          no
```

**`passwordauthentication` 实际是 `no`** —— 跟只看文件得出的结论**完全相反**。

> **教训：配置文件里写着什么不算数，程序读进去的才算数。**
> 凡是支持"多来源合并"的配置系统（`sshd`、`nginx`、systemd 的 drop-in、sudoers），
> **都要问一句"最终生效的是什么"**，而不是"文件里写了什么"。
> 这类系统一般都有一个"打印最终配置"的开关（`sshd -T`、`nginx -T`、`systemctl show`），用它。

### ④ 四个端点，不带凭据全部被拒

把对外提供能力的四个端点（记忆库 / 心潮 / 花园小游戏 / 推送服务）**不带任何凭据**打了一遍：

| 端点 | `initialize` | `tools/list` | `tools/call` |
|---|---|---|---|
| 记忆库 | **401** | **401** | **401** |
| 心潮 | **401** | **401** | **401** |
| 花园小游戏 | **401** | **401** | **401** |
| 推送服务 | — | — | **403** |

**`401 / 401 / 401 / 403`** —— 全部被拒。

而且关键是：**它们是第一步就拒。** 不是"先握上手，等你调工具的时候再验" —— 是**连握手都不放行**。

> 顺便记一个**反例**，免得经验串台：另一个论坛类的 MCP，它的 `initialize` 和 `tools/list` **根本不校验令牌**，
> 令牌填错、粘一半、甚至留空，都会显示"已连接"并正常列出工具，**只有 `tools/call` 才验**。
> 两件事的经验正好相反 —— **所以"连接成功"这四个字在有些服务上毫无意义，必须真调一次才算通。**

## 五、立场：不做，是一个合法的结论

四条建议全部查完，**结论是四条都不做，什么都不动。** 用户当时的表态是"**先不动**"，这个判断是对的。

我想把这一节的道理讲清楚，因为它比那四条具体的结论更重要。

### 提安全建议之前，先问一句

> **这条建议挡的是什么现实威胁？**

这不是抬杠，这是个**过滤器**。拿那四条过一遍：

| 建议 | 它挡的现实威胁 | 过滤结果 |
|---|---|---|
| 换 Tailscale/WireGuard | "现在的公网入口" —— **这个入口不存在** | 挡一个不存在的东西 |
| 套 Cloudflare Access | "自建服务自己有鉴权漏洞" —— **未被证实**（四个端点实测全部 401，第一步就拒） | 挡一个假设的洞 |
| 令牌别明文放 | "本机被别人碰到" —— **用户电脑在家，没人碰，不用网盘** | 威胁模型不成立 |
| `Restart=always` | "进程干净退出后不重启" —— **它不会干净退出** | 挡一个不会发生的情况 |

**四条里有四条答不上来（或答错了）。**

### 用户的威胁模型（这才是基准线）

- **单人自用。** 不是对外服务，不是生意，不面向公众。
- **学生。** 服务器 ¥99/年，**没有预算**做企业级方案。
- **电脑在家，没人碰。** **不用网盘 / 云盘**，很少云端备份。
- 她自己的原话：**「我一个学生而已」**。

把**零信任 / 纵深防御 / 最小权限**那一整套往这个模型上套，结果不会更安全 —— **只会把一个能跑的系统改出更多能坏的地方。**

安全加固是有成本的，成本包括：

1. **新依赖**（多一个组件，就多一个能坏的点）
2. **新配置**（配错了比不配更危险 —— 比如 Access 配错，AI 当场读不到记忆）
3. **注意力和维护**（每加一道门，以后每次排错都要多排一层）

**在一台只有一个用户的机器上，这三样成本都是真金白银，而收益接近于零。**

### 哪天真要加固，从哪儿下手

不是"什么都不做"，而是**排序不同**：

1. **先问"挡的是什么现实威胁"**。答不上来就什么都不做。
2. 真要加，**别引入新的中间层**。优先"定期看一眼" —— 体检脚本已经每天在跑了，
   要加就加一条"检查 22 端口的异常登录尝试"，而不是再加一道门。
3. **别动那条链路**：AI 读自己记忆这条路（Cloudflare → 隧道 → 记忆库 MCP）**能不动就不动**。
   那是整套系统里用户最在乎的东西，也是最经不起折腾的地方。

## 六、这一轮的翻车现场

按惯例把自己的失误也写下来，这次有一处：

**我把"令牌明文放着"这条威胁说重了。**

当时我的说法大意是"本机上的明文令牌有风险"，隐含的威胁是"有人碰到你的电脑就能拿到"。

用户的回应很直接：**电脑在家没人碰，也不用网盘。**

我当场更正了 —— **这条威胁模型不成立**。我把"本机被碰到"这种在共享办公环境里确实常见的情形，套到了一个**单人、在家、离线**的环境上。这是我**没有先问清楚威胁模型就开始评估风险**的典型错误。

顺序应该是反的：**先问"谁会碰到这台机器"，再谈"令牌放在哪"。** 反过来做，就会像我这次一样，把一条不成立的威胁说得像真的一样。

---

## 七、一句话收尾

**不做，是一个合法的结论。**

不是"懒得做"，也不是"不懂所以不做" —— 是**逐条查证之后，判断这些建议挡的威胁在当前环境里不存在或者不成立**。

如果哪天环境变了（比如这台机器要给别人用、或者要把域名直接指到服务器 IP 开 80/443），那这几条结论就得**重新过一遍**。但在那之前，**能跑的系统不动它，就是最好的运维。**
