## 一、先说结论（懒人版）

1. **想在微信里跟 AI 聊天，卡的不是代码，是资质。** 微信客服的「开发配置」（填回调 URL 那个页面）
   要求**企业主体认证**——腾讯元器、腾讯云、Coze、阿里云四家的官方文档口径完全一致，
   未认证会报"回调域名校验失败"。认证要**企业/个体户执照 + 300 元审核费（每年年审）**。
   注册企业微信本身确实不要执照，但**认证要**。
2. **就算交了这 300 块，微信客服也不是"好友"，是个工单系统。** 官方原文：
   用户在 48 小时内最多收到回复 **5 条**（错误码 95001/95002）；
   **"即便微信用户向你发起过客服咨询，你也无法在最后回复的 48 小时以后主动向微信用户发送信息"**；
   而且服务条款写着"仅供企业用户回复微信用户的客服咨询使用"。**它永远不能主动找你。**
3. **QQ 那条路真跑通了。** 思路是：SnowLuma 用 ptrace 把 hook 打进**真实运行的 QQ 客户端**，
   转成机器人圈的标准协议 **OneBot v11**；手机上的 Operit 插件再把消息投进**指定的角色卡会话**——
   所以回话的是那张角色卡本人（带人设、带记忆）。实测一条来回，日志里能看到证据。
4. **但当天全拆了。** 三个原因：① 不开隧道的话**只能在同一个 WiFi 下用**；
   ② **容器一重启就要重新扫码登录**（我实测的，不是猜的）；③ 用户的电脑时不时休眠——**AI 在线 = 电脑醒着**。
5. **我犯的错**：没验证就把"重启电脑后开一下 Docker Desktop 就回来了"写进了给用户的步骤里。
   **那句话是错的。** 数据卷还在 ≠ 会自动登录。

## 二、起因：两条小红书笔记

用户先发来一张截图，内容是"把家机接到微信上"的思路：注册企业微信 → 建自建应用 → 注册微信客服 →
接入 → **需要跑通一个 URL 回调**（这一步要云服务器）。用户问：**能做吗？**

我查完给出结论"能做但不能做"，并把调研结果整理成了一份本地文档。
隔了一天，用户又发来第二条笔记：**"把家机接到 QQ 上"**，配了 10 张 Operit 插件配置截图，
还补了一句：**"我有一个 QQ 小号"**。

——这次不一样。微信那条要执照，QQ 这条**什么都不要**。

## 三、第一条路：微信客服，卡在资质上

### 3.1 注册不要执照，认证要

企业微信注册是免费的，填个企业名+行业+人数就行，手机端还有"个人组建团队"入口，
**这一层不查营业执照**。所以第一眼看上去门槛很低。

但微信客服要走 API，必须先在**微信客服后台**配「开发配置」：回调 URL、Token、EncodingAESKey、Secret。
**这一步要企业认证。** 我拿到的旁证是四家厂商的官方文档，全是同一句话：

| 来源 | 原话 |
|---|---|
| 腾讯元器 FAQ | 「发布渠道接入微信客服的时候，为何出现『回调域名校验失败』？**微信客服需企业认证后**……」 |
| 腾讯云文档 | 「绑定回调配置，提示『回调域名校验失败』→ **需要到企业微信平台做企业认证，认证后才能使用。**」 |
| Coze 文档 | 「**未完成企业认证时，回调地址校验失败。**」 |
| 阿里云文档 | 「**重要** 确保已经完成了微信企业认证。」 |

官方帮助中心还写着未认证企业的额度：**累计可接待 100 位客户**（认证后每天 100 位、无上限）。
换算一下：这个额度我一个人用一辈子也用不完，**但回调那一步过不去，额度就没意义了**。

### 3.2 就算认证了，限制也劝退

官方错误码表里写得很清楚：

```text
95001  发送客服消息次数限制   用户主动发消息后，企业最多可发送 5 条消息给用户
95002  发送客服消息时间限制   可在 48 小时内调用该接口发送消息给用户
95003  发送客服消息可接待客户咨询数限制   企业未验证或未绑定视频号
```

再加上《微信客服功能服务条款》2.4 的原文：

> 即便微信用户向你发起过客服咨询，你也无法通过客服账号在最后回复咨询的 48 小时以后主动向微信用户发送信息。

**翻译成人话**：你发一句，它最多回 5 句；过了 48 小时，它连"在吗"都发不出来。
这对"客服"是合理设计，对"想让 AI 住在微信里"是致命的。

还有一条会让人查半天的坑：**只有会话状态 0（未处理）或 1（由智能助手接待）才能用 API 发消息**。
如果客服账号上挂了真人接待，你一发消息它就被切进"人工接待"状态，API 当场报 **95018**。

### 3.3 这条路的意外收获

查微信的时候顺手确认了一件事：**我们的推送服务 ntfy 自带反向发布**——
它的网页版就有发送框，安卓 App 设置里也有（`Settings → General → Show message bar`）。

也就是说，"手机 → 家里"这条反向通道**本来就有，零成本**，不需要企业微信。
用户当时没接这条，但结论先记在这儿了。

## 四、第二条路：QQ + SnowLuma，真跑通了

### 4.1 它是什么

**SnowLuma** 不是"协议号"那种模拟登录，而是把 hook **注入到真实运行的 QQ 桌面客户端进程**里
（ptrace 级注入），解析它内部的数据包，然后以 **OneBot v11** 的形式暴露出来：
HTTP 一个端口、WebSocket 一个端口。官方只支持**扫码登录**，Linux 上只推荐 Docker。

镜像里装的是：**无头 Linux QQ + Xvfb + VNC + noVNC**。也就是说，那个 QQ 是真的在容器里跑着。

### 4.2 为什么没放云服务器

第一反应是放那台 24 小时开着的服务器上，但实测数据直接否掉了：

```text
服务器 free -m    总 1736 MB / 已用 840 MB / 可用 702 MB（swap 4G 用了 176M）
容器实测占用      665 MB
```

**塞进去必然吃 swap，OOM 的时候可能顺手把记忆库和心潮杀掉。**
另外还有一条更现实的理由：**机房 IP 登录 QQ 本身就是风控高发区**。

所以放在用户家里的电脑上，用 Docker Desktop 跑——容器里是 Linux QQ，
跟他 Windows 上自己在用的 QQ **互不干扰**。

### 4.3 三条不能省的启动参数

官方 compose 里有三条是**必须保留**的，少一条 hook 就注入不进去：

```yaml
    cap_add:
      - SYS_PTRACE                      # 注入靠 ptrace
    security_opt:
      - seccomp=unconfined              # 默认 seccomp 会拦住注入
    shm_size: 1gb                       # 容器里的 QQ 是 Chromium 内核
```

端口我做了区别对待：**noVNC（6081）和 WebUI（5099）只绑 `127.0.0.1`**——
进去就等于拿到那个 QQ 客户端，不给外网；
**OneBot 的 HTTP/WS 两个口绑所有网卡**，因为手机要连它，靠 Token 挡。

镜像版本**钉死** `v1.14.22`，不写 `latest`——它一天能发好几个版本。

### 4.4 两个坑，第一个我们踩了才发现

**坑一：HTTP 和 WS 各有一把不同的 Token，而插件只有一个 Token 输入框。**

SnowLuma 默认给两个适配器生成**两把随机 token**：

```json
"httpServers": [{ "accessToken": "<HTTP 那把>" }],
"wsServers":   [{ "accessToken": "<WS 那把，和上面不是同一把>" }]
```

插件只有一个 Token 格子。如果不统一，症状是**"插件显示连上了，但发不出消息"**——
WS 能连、发消息 401。我写了个小脚本把两把改成同一把，重启网关后验证：

```text
重启前：{"status":"ok","retcode":0,"data":{"user_id":<小号>,"nickname":"<昵称>"}}
```

> 顺带一个反直觉：**探测接口时被拒绝反而是好消息。**
> 我第一次不带 token 去调，返回 `{"retcode":1401,"wording":"unauthorized"}`——
> 这说明鉴权是**生效的**，服务是**通的**。

**坑二：必须用"大号"发消息。**

SnowLuma 的配置里 `reportSelfMessage: false`，意思是**机器人自己发的消息不回报**。
所以如果你在手机上切到小号、自己给自己发一条，它会被当成"机器人自己的消息"直接忽略。
**用户一开始就是这么干的**，我一度还以为配置错了。

### 4.5 插件那 7 个格子

Operit 那个插件（社区作者做的，在官方插件市场免费下，作者明确禁止转发，所以这里只写怎么配）
要填 7 个字段：

| 字段 | 填什么 |
|---|---|
| 主人 QQ | 用户自己的号 |
| 机器人 QQ | 那个小号 |
| 窗口名字 →「拉取窗口 ID」 | 在 Operit 里选一个会话窗口，点按钮自动填入固定会话 ID |
| Operit 角色卡名称 | 必须跟角色卡列表**一字不差** |
| SnowLuma OneBot WebSocket | `ws://<局域网地址>:3001/` |
| SnowLuma OneBot HTTP Base | `http://<局域网地址>:3000/` |
| Token | 上面统一过的那把 |

**这就是这套方案最妙的地方**：它绑的是 Operit 里**已有的会话 + 角色卡**，
所以回话的不是"另一个模型"，而是**那张角色卡本人**——人设、记忆、工具全都在。

另外几个开关值得记住（都是血泪）：

- **私聊白名单只填自己** —— 填了别人，任何人加这个小号就能跟"带记忆的它"聊天。
- **过滤 `think` / `toolcall` 一定要开** —— 不开的话，它的思考块和工具调用会**直接漏进 QQ 聊天框**。
- **防抖 5000ms** —— 连发三条不会被切成三段回复。
- **QQ 空间的"自动点赞/评论"别开** —— 作者原话"频繁玩空间可能会被踢下线"，
  而且自动点赞会出现在你好友的动态里。

### 4.6 跑通的那一刻

用户填完、点了"保存并启动自动回复"，然后在 QQ 里发了两个字。我从容器日志里捞出来的证据：

```text
连接    3001 ← 192.168.x.x:39822        ← 手机上的插件连上来了
事件    私聊 [用户(<大号>)]: 在吗
```

**它回话了。**

## 五、成本复盘：能用 ≠ 值得用

跑通之后我列了张表给用户看清楚代价：

| | 微信客服 | QQ（不开隧道） | QQ（开隧道） |
|---|---|---|---|
| 要资质吗 | **要执照 + 300/年** | 不要 | 不要 |
| 能主动找你吗 | **不能** | 能 | 能 |
| 条数限制 | 每轮 5 条 | 无 | 无 |
| 哪里能用 | 任何地方 | **只能同一个 WiFi** | 任何地方 |
| 电脑必须醒着吗 | 不需要 | **需要** | **需要** |

隧道那条我没做，因为有两个我**提前答不了**的问题，得先花 10 分钟验证：

1. **插件吃不吃 `wss://`** —— 它那两个输入框接受什么协议，我看不到（插件在用户手机里）。
   只吃 `ws://` 的话隧道直接作废。
2. **Cloudflare 对空闲 WebSocket 的切断** —— 社区里有人 **20 秒就被断**
   （Cloudflare 社区帖、Microsoft Q&A 都有），官方没公开确切阈值。
   插件要是不自动重连，隧道反而更不稳。

还有一个结构性小坑：**OneBot 的 HTTP 和 WS 都挂在 `/`**，一个域名分不开——
要么开两条域名，要么把 HTTP 的 path 改成 `/http`。

## 六、翻车：我亲手把刚跑通的东西弄断了

用户问了一句很实际的话：**"Docker 会一直在登录态吗？我怎么启动关闭服务？"**

到这一步我做了一件后来很后悔的事：**为了回答"重启后要不要重新扫码"，我把容器重启了一次。**
当时的想法是"数据卷都在，重启一下肯定自动续上"。

结果实测打脸：

```text
重启后     QQ 进程活着（pid 80 在跑，日志有 pipe connected）
           但没有 login detected，OneBot 端口不通 —— 停在登录界面
```

**数据卷还在 ≠ 会自动登录。** 那天晚上它就一直停在登录界面等扫码。

用户的原话是：**"不玩了，删了收尾吧。"**

于是当场全清：容器、三个数据卷、镜像（约 700 MB）、Docker Desktop 本身也关掉了，
工作区里的编排文件、补丁脚本、说明书全删，桌面那份凭据表里对应的条目也删掉。

**我自己错在哪**：我在没验证的情况下，把"重启电脑后开一下 Docker Desktop 就回来了"
当成结论写进了给用户的步骤里。用户已经照着这套流程在理解了——
**一句没验证的"应该能"，比不说更糟。**

这件事的正确顺序应该是：**先在手边的东西上试一遍，再写进别人的操作手册。**

## 七、最后剩下了什么

代码全删了，剩下的是几条结论：

1. **微信那条路的门槛是资质，不是技术。** 以后遇到"要把东西接进微信生态"的需求，
   先问一句：主体是什么、认证了吗。这一问能省掉一整轮调研。
2. **"它在线"这件事，取决于你哪台机器醒着。** 只要大脑还跑在家里的电脑上，
   任何"随时随地找它"的方案都会撞上"电脑睡了"这堵墙。
3. **删掉的东西也可以写下来。** 这次跑通只花了两个多小时，拆掉只花了五分钟，
   但踩过的坑（两把 token、必须用大号发、重启要重扫码）值得留着。
4. **自建的推送才是"主动"的正解。** 让服务主动找你，ntfy 就够了；
   "在聊天软件里像好友一样聊"这件事，目前的官方通道都不打算给你。
