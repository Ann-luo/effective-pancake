## 先说结论

这次本来只是想给博客做个"大扫除"——文章越来越多，目录有点乱，顺手理一理。

结果扫出两个真正的坑：

### 坑一：同一个链接，在三个地方表现完全不同

文章里的一条链接，会出现三种情况：

| 在哪里点 | 结果 |
|---|---|
| GitHub 仓库页面 | ✅ 能打开 |
| 本地编辑器预览 | ✅ 能打开 |
| 博客网站上 | ❌ 404，页面找不到 |

原因是：**GitHub 和 Jekyll 是两套完全不同的渲染规则**。

"能在 GitHub 上点开"这件事，**完全不能说明它在博客上也是好的**。这一点是整篇文章最值钱的结论。

### 坑二：`categories` 这个字段会改你的文章网址

`categories` 看起来只是"给文章分个类"，很无害。实际上它会**进到文章网址里**。

而且写法稍微不对，一个分类会被拆成好几个分类，网址跟着一起乱。

### 顺手做掉的

- 3 篇文章补上了 front matter（之前它们在博客上显示的标题是英文的，还是机器生成的）
- 19 篇文章的分类统一成 7 个固定值
- 导航和仓库结构图补齐
- `.gitignore` 从 Node.js 模板换成 Jekyll 版

## 一、背景：先把流程说清楚

要理解后面两个坑，得先知道"写一篇文章"到底发生了什么。

### 1. 写文章 = 写一个 Markdown 文件

我在 `_posts/` 目录下建一个文件，名字有固定格式：

```text
_posts/2026-09-26-some-title.md
       └── 日期 ──┘ └─ 名字 ─┘
```

文件开头有一小段被 `---` 包起来的东西，叫 **front matter**（前置信息），长这样：

```markdown
---
layout: post
title: "文章标题"
date: 2026-09-26 12:00:00 +0800
categories: ["日志"]
tags: [Jekyll, 博客, 踩坑]
---

> 导语

---

## 正文
```

大白话：**front matter 就是这篇文章的"身份证"**。标题叫什么、什么时候发的、属于哪个栏目，都写在这里。

### 2. Jekyll 把它变成网页

我把文件 push 到 GitHub，GitHub Actions 自动跑 Jekyll，把 Markdown 翻译成 HTML 网页，再发布出去。

```text
我写的 .md 文件
    ↓
Jekyll 翻译
    ↓
一个网页（.html）
    ↓
GitHub Pages 发布到网上
```

### 3. 链接有"三个世界"

这是这次踩坑的根源。同一份 Markdown，会被**三种不同的东西**解读：

```text
GitHub 网页    ← 它在解读你的 .md
Jekyll         ← 它也在解读你的 .md
浏览器         ← 它只认最终生成的 .html
```

三个解读器的规则**都不一样**，尤其是"相对路径"和"文件扩展名"的处理。

我一开始以为"GitHub 上能点开就是对的"，就是这个错误假设害的。

## 二、坑一：链接的三个世界

### 1. 现象

整理时我跑了一遍首页上所有链接，发现好几条是 404。

但奇怪的是，这些链接在 GitHub 仓库页面上**点了是好的**。

具体来说，坏掉的链接分三类，每一类的原理都不一样。

---

### 2. 第一类：`_posts/` 目录根本不会被发布

我在导航里写过这样的链接：

```markdown
- 4.9 [手机里塞个AI论坛](./_posts/2026-08-09-forum-ai-bbs.md)
```

在 GitHub 上点开，会跳到仓库里的那个文件，**完全正常**。

但在博客上点开，是 404。

**为什么？**

因为 Jekyll 有个规矩：

> **以下划线 `_` 开头的目录，不会被复制到网站里。**

`_posts` 正好是下划线开头。所以它只是"源文件仓库"，Jekyll 读完它、生成网页，然后**不把它发布出去**。

大白话：

```text
_posts/ 是"后厨"，
读者只能看到端上桌的菜（网页），
进不了后厨（_posts/）。
```

所以链接指向 `_posts/xxx.md`，在网站上永远是 404——**这个文件在网站上压根不存在**。

**那应该怎么链？**

Jekyll 提供了一个专门的标签 `post_url`：

```markdown
- 4.9 [手机里塞个AI论坛]({% raw %}{% post_url 2026-08-09-forum-ai-bbs %}{% endraw %})
```

它的好处是：**你不用管最终网址长什么样**，Jekyll 会自己算出来。

这一点很重要，因为网址格式以后可能会变（我这次就变了），用 `post_url` 的话，网址变了也不用回来改。

> ⚠️ `post_url` 里写的名字必须和 `_posts/` 下的文件名**完全一致**（去掉 `.md`）。
> 写错的话，Jekyll 会**直接构建失败**，整个博客停在旧版本不更新。这是它唯一的缺点。

---

### 3. 第二类：相对路径的"基准"不一样

还有一类坏链接长这样：

```markdown
下载项目文件：[p-ent-phone.html](../assets/p-ent-phone/p-ent-phone.html)
```

`../` 的意思是"往上一层目录"。这个写法在 GitHub 上和本地都是对的。

但在博客上是 404。**为什么？**

因为**"上一层"到底是哪一层，取决于当前页面在什么位置**。

```text
GitHub 上的位置：
effective-pancake/2026-07-30-phone-desktop-dev-record.md
                  ↑ 上一层就是仓库根目录，assets/ 就在那儿 ✅

博客上的位置：
/2026/07/30/phone-desktop-dev-record.html
       ↑ 上一层是 /2026/07/，不是根目录 ❌
```

博客上的文章网址是**带层级的**（年 / 月 / 日 / 文件名），所以 `../` 会把你带到 `/2026/07/assets/...`——那个地方什么都没有。

大白话：

```text
"楼上"这个词，在一楼说和在三楼说，
指的是不同的地方。
```

**怎么修？** 用绝对路径，从网站根目录写起：

```markdown
下载项目文件：[p-ent-phone.html](/effective-pancake/assets/p-ent-phone/p-ent-phone.html)
```

开头的 `/` 表示"从根目录开始算"，不管当前页面在哪一层，都指的是同一个地方。

> 小提醒：这里的 `/effective-pancake/` 是仓库的 `baseurl`，也就是你这个博客在网上的"目录名"。
> 写在文章里的绝对路径要带上它。

---

### 4. 第三类：同一个目录里，两个文件命运不同

这一类最反直觉。

我的博客里有个 `skills/` 目录，放了几个 Skill 文件，都是一个模子：`skills/名字/SKILL.md`。

我给它们做了链接，指向 `.md` 文件。结果：

```text
skills/codex-chat/SKILL.md      → 404 ❌
skills/publish-blog/SKILL.md    → 200 ✅
```

**同一个目录，一样的文件名，一个通一个不通。**

**为什么？**

因为 Jekyll 判断一个文件"要不要翻译成网页"，看的是**它开头有没有 front matter**。

```text
有 front matter 的 .md  →  Jekyll 翻译它  →  生成 SKILL.html
没有 front matter 的 .md  →  Jekyll 不管它  →  原样复制成 SKILL.md
```

而这三个文件的情况是：

| 文件 | 有没有 front matter | 网站上实际是 |
|---|---|---|
| `codex-chat/SKILL.md` | 有（要写 name、description） | `SKILL.html` |
| `qq-messenger/SKILL.md` | 有 | `SKILL.html` |
| `publish-blog/SKILL.md` | 没有 | `SKILL.md` |

所以我链接写成 `.md`，对 publish-blog 是对的，对另外两个就是 404。

大白话：

```text
同一个抽屉里的两个文件，
一个有"加工标记"，一个没有。
有标记的被厨房加工成了菜，
没标记的原样端上桌。
你按原料名字点菜，只能点到没加工的那个。
```

**怎么修？** 我在这种情况下干脆指向 GitHub：

```markdown
[Skill 资源包：codex-chat](https://github.com/Ann-luo/effective-pancake/blob/main/skills/codex-chat/SKILL.md)
```

理由：这些 Skill 本来就是**给人下载的**，GitHub 上点开还能正常渲染，比纠结 `.html` 还是 `.md` 省事。

---

### 5. 为什么本地和 GitHub 都发现不了

这三类坑有个共同特点：**你在本地和 GitHub 上怎么点都是好的。**

| 检查方式 | 能发现问题吗 |
|---|---|
| 本地编辑器预览 | ❌ 它按本地文件路径解析 |
| GitHub 仓库页面 | ❌ 它按仓库文件路径解析 |
| `git diff` 看改动 | ❌ 只是文本对比，不知道链接通不通 |
| 博客上线后点开 | ✅ 只有这里是真的 |

因为前三个都在"源文件的世界"里，只有博客在"渲染后的世界"里。

**这两个世界不一样，而且差异还挺大。**

## 三、坑二：`categories` 会改你的文章网址

### 1. 它不只是"分个类"

我一直以为 `categories` 就是给文章贴个分类标签，方便归类和展示。

直到看见自己的文章网址长这样：

```text
https://ann-luo.github.io/effective-pancake/claude code & ai 工具/2026/08/09/forum-ai-bbs.html
                                        └──── 这一段就是分类 ────┘
```

**分类名直接进了网址。**

原因是 Jekyll 的默认网址格式：

```text
/:categories/:year/:month/:day/:title
```

`:categories` 就是"把分类名填到这里"。

### 2. 后果一：网址变丑，而且是无效的

分类名里有空格和 `&`，进到网址里就变成这样：

```text
claude%20code%20&%20ai%20工具
```

- 空格变成了 `%20`
- `&` 原样留着——这在 HTML 里其实**应该写成 `&amp;`**，属于无效写法

### 3. 后果二：同一个栏目，网址分成好几份

这是我的真实情况。同样是"Claude Code & AI 工具"这个栏目下的文章，网址前缀却有三个：

```text
claude code & ai 工具/2026/08/09/...
claude code/ai工具/2026/07/28/...
四、claude code & ai 工具/2026/06/10/...
```

**为什么？** 因为分类名是**手填的**，19 篇文章跨了好几个月，每次写的时候想到什么写什么：

| 我写过的分类名 | 实际效果 |
|---|---|
| `["Claude Code & AI 工具"]` | 一个分类 |
| `[Claude Code, AI工具]` | 两个分类 |
| `["四、Claude Code & AI 工具"]` | 把"四、"也写进去了 |
| `[教程, VS Code]` | 另一套命名体系 |
| 什么都不写 | 没有分类，网址里直接少一段 |

### 4. 最重要的坑：不加方括号，一个分类会变成一堆

这是最隐蔽的一个。看这两行：

```yaml
categories: ["Claude Code & AI 工具"]   ← 正确：一个分类
categories: Claude Code & AI 工具        ← 错误：一堆分类
```

第二行为什么不对？

**YAML 本身没错**，它老老实实把这一行解析成**一个字符串**。

问题出在 **Jekyll 拿到这个字符串之后**。Jekyll 内部对"分类值"的处理是这样的：

```ruby
# 简化过的逻辑
当分类值是字符串时 → 对它调用 split（按空格拆开）
```

所以那一串会变成 6 个分类：

```text
"Claude Code & AI 工具"   ← 原来那一整串，也算一个分类
"Claude"
"Code"
"&"
"AI"
"工具"
```

一共 **6 个**（整串 1 个 + 按空格拆出来的 5 段）。

后果：网址里直接多出 6 段前缀，彻底乱掉。

> 顺便说个小细节：分类进网址的时候会被**转成小写**，
> 所以 `"Claude Code & AI 工具"` 在网址里显示成了 `claude code & ai 工具`。

**我自己在整理的时候就踩了这个坑。** 第一遍批量改分类，写成了不加方括号的形式，改完 19 篇全都是坏的，检查时才发现，第二遍才改回来。

所以现在我的自检脚本里专门有一条：**检查 `categories` 是不是方括号列表形式**。

---

### 5. 怎么修的

两件事一起做：

**第一，把分类名固定下来。**

定了 7 个，谁也不许乱写：

| 栏目 | front matter 里写 |
|---|---|
| 一、VS Code & GitHub Copilot | `["VS Code & GitHub Copilot"]` |
| 二、Windows 技巧 | `["Windows 技巧"]` |
| 三、GitHub & 博客搭建 | `["GitHub & 博客搭建"]` |
| 四、Claude Code & AI 工具 | `["Claude Code & AI 工具"]` |
| 五、杂项 | `["杂项"]` |
| 六、Codex & Computer Use | `["Codex & Computer Use"]` |
| 七、日志 | `["日志"]` |

注意：front matter 里**不带**"一、二、三"这种中文数字前缀，那个只出现在目录标题里。

**第二，把分类从网址里拿掉。**

在 `_config.yml` 里显式指定网址格式：

```yaml
permalink: /:year/:month/:day/:title:output_ext
```

`permalink` 就是"固定链接格式"。这样写之后，网址变成：

```text
整理前：/effective-pancake/claude code & ai 工具/2026/08/09/forum-ai-bbs.html
整理后：/effective-pancake/2026/08/09/forum-ai-bbs.html
```

干净了，而且**以后改分类名不会再动网址**。

> ⚠️ 代价：所有旧网址都会失效（404）。
> 如果博客已经有很多外部链接（别人收藏了、搜索引擎收录了），这一步要慎重，
> 可以先加一个"自动跳转"的插件。博客刚建不久、外部引用少的话，直接改代价最小。

## 四、更隐蔽的问题：本地根本验证不了

改完上面这些，新的问题来了：

**我怎么知道改对了？**

### 1. 本地没有 Ruby

Jekyll 是 Ruby 写的。要在本地预览博客，得装 Ruby，然后跑：

```bash
bundle exec jekyll serve
```

但我这台电脑上**没装 Ruby**。所以：

```text
改完之后，我只能在本地"看文本"，
没法真的生成一遍网站看看效果。
```

**唯一的验证方式，是 push 上去让 GitHub Actions 构建，然后看线上结果。**

这就很被动了——错了要等 1 分钟才知道，而且已经推出去了。

### 2. 那就写个自检脚本

既然没法"跑一遍看看"，就换个思路：**把能机器判断的规则，全部写成脚本，提交前跑一遍。**

我写的检查项：

```text
1. post_url 引用的文件名，在 _posts/ 里真的存在吗？
   （不存在 = 构建会失败）

2. categories 是不是方括号列表？值在不在那 7 个里面？

3. 正文里有没有"多余的一级标题"？
   （标题由 front matter 提供，正文再写一遍会显示两次）

4. 有没有相对路径链接？（博客上会 404）

5. 有没有手写的文章网址？（应该用 post_url）

6. 站内资源链接指向的文件，真的存在吗？
```

跑一遍几秒钟，比等 CI 快得多。

### 3. 结果这个脚本自己也有 bug

有意思的是，脚本写完第一次跑，报了一个错：

```text
index.md: categories 不是列表
```

我一看就愣了——`index.md` 是**博客首页**，它当然没有 `categories` 字段。

**是我脚本写错了**：我把首页和文章用同一个循环处理，但首页根本不是文章，没有那一套 front matter。

大白话：

```text
我写了个尺子去量东西，
结果尺子本身的刻度就是歪的。
```

这件事让我印象挺深：**验证工具本身也是代码，也会出错。**写完必须拿真数据跑一遍，不能想当然觉得"检查脚本肯定是对的"。

### 4. 补记：这篇文章自己把构建搞崩了

写完推上去，GitHub Actions **构建失败了**。

原因在这篇文章**自己的正文里**——我为了演示"正确写法"，在代码块里写了一个 Jekyll 标签。

**关键在于：Jekyll 的 Liquid 模板引擎在 Markdown 之前执行，而且它不管你在不在代码块里。**

代码围栏（那三个反引号）对 Liquid 来说只是**普通文字**，不是"这里面的东西别动"的意思。

所以我那段"示例"被**当成真的指令执行了**。更巧的是，我在"以后怎么快速定位"那节里还写了半句"改用某个标签"，标签没给参数——Jekyll 直接报错，构建就挂在那儿。

大白话：

```text
我写了一段"错误的示例"来教学，
结果系统认真照做了。
```

**修法**：用 Jekyll 自带的 `raw` 标签把示例包起来，告诉它"这一小段别执行，原样输出"。包起来之后，读者看到的才是标签原文，而不是被替换后的结果。

**更值得记的是：自检脚本没查出来。**

因为脚本为了避开"代码块里的假链接"，**主动把代码块剥掉了**——而这个真正会执行的东西，正好落在被剥掉的范围内。

教训一句话：

```text
检查工具的盲区，
往往就是它为了处理另一类问题而设的那条规则。
```

## 五、这次排查的几个教训

### 1. "在 GitHub 上能点开" ≠ "在博客上能点开"

这是最重要的一条。两个渲染器的规则完全不同，尤其在**相对路径**和**文件扩展名**上。

### 2. 相对路径是个陷阱

`../` 的含义取决于当前页面在哪一层。文章网址带层级，所以 `../` 特别容易指错。

**站内资源一律用绝对路径**，从 `/` 开始写，最省心。

### 3. 看起来最无害的字段，可能影响最大

`categories` 只是"分个类"，结果它进了网址。

写配置文件的时候，**不确定的字段最好去查一下它有没有副作用**。

### 4. 配置字段的格式差异，不会报错

```yaml
categories: ["A & B"]   # 一个分类
categories: A & B        # 一个字符串，被 Jekyll 拆成 6 个分类
```

差了两个方括号，语义完全不同。**这种坑不会报错**，只会静默地产生错误结果——
你以为设了一个分类，实际设了一堆。

### 5. 不能本地验证的东西，要把验证做成流程

本地跑不了构建，那就把能自动检查的都写成脚本，提交前必跑。

而且**脚本本身也要拿真数据验证**——我那个脚本第一次就是错的。

## 六、以后遇到类似问题怎么快速定位

### 链接点不开

按顺序检查：

1. 链接指向的是 `_posts/` 吗？→ 改用 `{% raw %}{% post_url %}{% endraw %}`
2. 链接里有 `../` 或 `./` 吗？→ 改成 `/` 开头的绝对路径
3. 链接指向 `.md` 文件吗？→ 看看那个文件有没有 front matter，有的话应该指 `.html`
4. 都不是？→ 打开浏览器的开发者工具，看它实际请求的网址是什么

### 网址突然变了

1. 检查 `_config.yml` 里的 `permalink` 有没有被改
2. 检查文章的 `categories` 有没有变（默认情况下它会影响网址）
3. 检查文章文件的**名字**有没有改过

   注意：网址里那一段来自**文件名**（去掉日期和 `.md` 之后的部分），
   而不是 front matter 里的 `title`。

   ```text
   文件：2026-08-09-forum-ai-bbs.md
   标题：title: "手机里塞个AI论坛——智能体发帖回帖全记录"
   网址：…/2026/08/09/forum-ai-bbs.html
                         └── 用的是文件名，不是标题
   ```

### 文章在博客上不显示

Jekyll 默认**跳过"未来时间"的文章**：

```text
如果 date 写的是未来 → 构建时直接跳过，不生成网页
```

而 GitHub Actions 用的是 **UTC 时间**（比北京时间早 8 小时）。

所以 date 别写晚上，统一写：

```yaml
date: 2026-09-26 12:00:00 +0800
```

---

## 最后总结

这次不是单一问题，是两类问题叠在一起：

```text
链接问题 = GitHub 和 Jekyll 是两套渲染规则
网址问题 = categories 会进网址，且字符串格式会被静默拆散
```

链接问题的修复路径是：

```text
发现 404
→ 排除 _posts/（不会被发布）
→ 排除相对路径（基准不同）
→ 排除 .md/.html（front matter 决定）
→ 全部改成 post_url 或绝对路径
```

网址问题的修复路径是：

```text
发现网址里带分类
→ 查 permalink 格式
→ 统一分类名（并写成方括号列表）
→ 显式指定 permalink，把分类从网址里拿掉
```

最后再记一句这次最实用的心得：

> **"在 GitHub 上能点开"，只能说明这个文件在仓库里存在。
> 它不能说明这个链接在网站上能用——那是另一套规则。**

如果这个博客是你自己在维护，建议把这句话贴在心上：

```text
改完之后，去线上点一遍。
本地预览和 GitHub 预览，都会骗你。
```
