## 0. 先说结论

**事情**：用户要「用 TypeScript 把梵高的《星夜》转成 3D 场景，有运镜、空间巨大、高度创新」，先要网页，后来因为浏览器卡顿改成要 60 秒 MP4。

**做成的**：一个能跑的 3D 网页。把原画拆成 **11,400 笔立体笔触**，每笔有自己的位置、颜色、走向、厚度，沿梵高的旋涡流场铺开成有纵深的星云；7 段镜头走完正好 **60 秒**，最后一镜机位回到起点，所以循环是无缝的。

**没做成的**：MP4 导出。不是画质问题、不是参数问题——是**这台机器上无头 Chrome「把一帧画面从显卡读回内存」固定要 3 秒**，我实测 **320×180 和 1920×1080 都是 3 秒**。60 秒片子等于一个半小时起步。

**用户最后拍板**：项目到此为止，清理。

**最该记住的一条**：

> ⚠️ **我用 `performance.now()` 测出「渲染只要 0.1 毫秒」，就以为渲染很快——那是错的。**
> WebGL 调用是异步的，0.1 毫秒只是「命令提交给驱动的耗时」，GPU 干完没有根本不知道。
> 我拿这个假数据支撑了至少三轮错误判断。**要测 GPU 真实耗时，必须 `gl.finish()` 或读回像素把管线逼停。**

## 2. 核心做法：怎么把一幅油画变成「可以飞进去的空间」

这是整个项目里唯一值得单独讲的技术点。

**不是**把画贴在一块板上做 3D 位移——那叫假 3D。做法是**逐格采样，把每个格子变成一根有厚度的独立笔触**：

1. **算笔触走向**：对亮度图求 Sobel 梯度，再算**结构张量**（Jxx / Jyy / Jxy 三个分量各做一次高斯模糊），从主特征向量解出「这里的笔触朝哪边」。各向异性高的地方（明确有笔画方向）就顺着它，低的地方（死平区域）就随机。

2. **亮度 → 深度**：亮的（星星、月亮、云峰）沿 Z 轴往观者方向顶出来，暗的（丝柏、山、村庄）沉下去。这样一幅平面画就变成了**有几米厚的浮雕**。

3. **旋涡流场**：在画面上放几个解析的涡旋（中央大旋涡、右上月亮、左中那颗亮星、左上小旋、右下云浪），每个产生切向 + 径向外推的速度，再叠一层值噪声破掉「解析感」。笔触沿这个场位移 → **整幅画被旋涡吹开成一片星云**。

4. **归位即成画**：流场位移和深度都乘一个全局系数。系数回到 0 时，所有笔触**正好落回原画位置**，整幅《星夜》重新显形。所以运镜能「从画里飞出来，再飞回去」——这是整个片子记忆点所在。

5. **一笔 = 8 个顶点**：一根有厚度的丝带（正面 + 背面 + 侧边）。逐实例 16 个 float（笔心、颜色、方向、长宽、流场、起伏、卷曲、亮度、随机相位），逐顶点 8 个 float。一次 `drawElementsInstanced` 画完全部。

**一处刻意的优化**：星核的辉光**在上传时烘进每笔的颜色**（`bakeStarGlow`），而不是在片元着色器里对每个像素算 8 次距离。这个改动是真的有用，实测帧时间从 13.5 秒降到 7 秒——虽然最后还是没能救回来。

代码分 8 个 TypeScript 文件：`math`（向量矩阵 + 值噪声）、`gl`（WebGL2 薄封装）、`shaders`（GLSL 字符串）、`painting`（上面那套解析）、`renderer`（场景装配 + 后处理链）、`tour`（镜头脚本）、`main`（入口 + 交互）、`params`。

## 3. 开发环境：两个绕过去的坑

**坑一：浏览器不认 `.ts` 的 MIME，ES 模块直接罢工。**

我一开始想让浏览器原生剥类型跑 `.ts`（Chrome 有这个能力），结果报 `Unexpected identifier 'RenderOptions'`——它剥不了我这写法。

**绕法**：写了个开发服务器 `tools/serve.mts`，**浏览器请求 `.ts` 时，服务端用 TypeScript 官方编译器现场剥类型再发出去**，结果缓存。改完源码刷新即生效，没有任何构建等待。这比配 Vite/webpack 轻得多，脚本本身 100 行。

**坑二：pnpm 在这台机器的沙箱里建不了符号链接。**

```
[ERR_PNPM_EPERM] [symlinkAllModules] EPERM: operation not permitted, symlink ...
```

第一次 pnpm 装到一半崩了，还**把我原来装好的 `node_modules` 冲掉了一半**。换 npm 装，npm 又往 `C:\Users\<用户>\AppData\Local\npm-cache` 写日志，被沙箱拒。

**绕法**：`npm install --cache .\.npm-cache`，把缓存指到工作区里。另外——邻居项目《宇宙短片》里已经有 `puppeteer-core` 和 `ffmpeg-static`，**直接 robocopy 过来复用**，省了 79 MB 下载。

## 4. 撞墙：那堵 3 秒/帧的墙

这是这篇存在的主要理由。用户先是说「卡」，我一路以为是渲染太慢，**结果是采集环节**。

### 4.1 用户视角的现象

用户第一句反馈是：**「它导致我浏览器卡死了？做成 MP4 会不会好很多」**。

**这是我的锅**：我默认给了 300 列笔触 × 全分辨率。300 列 = 9 万笔 × 8 三角形 = **72 万个三角形**，还带 alpha 混合（透明笔触层层叠加）。集成显卡画这个，overdraw 直接爆炸。

**我改了两件事**：
- 按屏幕面积自动选档（大窗口自动降到 100 列 + 0.7 倍渲染分辨率）
- 给镜头加了条硬约束：**别把相机塞进笔触体积里**。原本开场是「钻在颜料内部」，相机被上千个笔触糊住，屏幕上每个像素叠几十个半透明笔触。把它挪到体积外侧的 -z 方向后，帧时间从 15 秒降到 3 秒。

但用户第二次反馈还是：**「还是卡，改作MP4吧」**。于是方向改成离线导出。

### 4.2 我测出来的数据（这才是重点）

为了找瓶颈，我写了六个测量脚本，一路测下来：

| 测量项 | 结果 | 备注 |
|---|---|---|
| `gl.finish()` 后的纯渲染 | **0.1–0.3 ms/帧** | ❌ **假的**，见 4.4 |
| 页面自报帧率（HUD） | 30 fps | 也只是命令提交速率 |
| 分步：渲染 | 0.5 ms | |
| 分步：**`readPixels`（默认帧缓冲）** | **9,509 ms** | 💥 |
| 分步：拼二进制字符串 | 25 ms | |
| 分步：base64 | 6.7 ms | |
| 离屏 RGBA8 FBO 读回 | **3,064 ms** | 💥 |
| scene 半浮点 FBO 读回 | **2.3 ms** | 😳 同一个像素量 |
| 离屏 FBO **半尺寸**读回 | **0.63 ms** | |
| `Page.captureScreenshot` | **超时**（一帧 50 秒） | 💥 |
| `Page.startScreencast` | **0.3 fps** | 💥 |
| `canvas.toDataURL` | 8,811 ms | |
| `canvas.toBlob` | 6,334 ms | |

然后是最致命的那张表——**读回耗时和分辨率的关系**：

| 分辨率 | 像素数 | 第 1 帧 | 第 2 帧 |
|---|---|---|---|
| 1920×1080 | 207 万 | 13,074 ms | 3,280 ms |
| 1280×720 | 92 万 | 9,329 ms | 3,066 ms |
| 960×540 | 52 万 | 9,296 ms | 3,021 ms |
| 640×360 | 23 万 | 9,291 ms | 3,222 ms |
| 480×270 | 13 万 | 9,957 ms | 3,367 ms |
| **320×180** | **6 万** | **10,288 ms** | **3,090 ms** |

**结论：跟分辨率完全无关。** 像素数差了 34 倍，耗时一模一样。这是一条固定的同步卡点，不是带宽问题。

### 4.3 我试过、全都失败的路

1. **截图路线**（`Page.captureScreenshot`）→ 超时。一帧 50 秒，144 帧要 2 小时。
2. **离屏读回**（`gl.readPixels` 读自己的 FBO）→ 3 秒。
3. **换像素格式**：发现「scene 半浮点 FBO 只要 2.3 ms」，我以为是格式问题，**把导出的合成目标也改成半浮点**——还是 3 秒。那条 2.3 ms 是**测量假象**（可能是缓存/预热效应，换到真实逐帧循环里就没了）。
4. **`Page.startScreencast`**（让浏览器主动推帧，不走「我求一帧」的路）→ 0.3 fps。而且抓回来的样本帧里，**8 秒只推了 3 帧、推的还是「正在上传到显卡…」的加载画面**——合成器堵到连页面画完都没推出来。
5. **降分辨率**→ 见上表，无效。
6. **最后想换渲染引擎**（Node 端用 `@napi-rs/canvas` 的 Skia 光栅化，完全不经过浏览器），包都装上了。**用户这时候喊停**，清理收工。

### 4.4 我最大的判断失误

我用 `performance.now()` 包住 `render()`，测出 **0.1 毫秒/帧**，还连着测了「不画笔触 0.1 ms」「四分之一笔触 0.1 ms」——三组数据一模一样，这本身就该是个红灯，**说明这个测量根本没在量渲染**。

原因：**WebGL 是异步的**。`drawElementsInstanced` 只是把命令塞进驱动队列就返回，GPU 什么时候画完它不管。

**正确做法**：`gl.finish()`，或者读回一个像素把管线逼停。我后来用 `gl.finish()` 重测，数据才开始说人话。

**这个假数据害我至少三轮**：我拿它得出「渲染没问题，是采集慢」的结论，然后花了大量时间去优化采集路径——而真实情况是**两边都慢**，只是慢的方式不同。

## 5. 那 50 分钟到底在干嘛

用户中途问过两次「你在干嘛」「五十分钟了」，我得如实写。

那段时间我在**反复试采集路径**：截图 → 离屏读回 → 换像素格式 → 换分辨率 → screencast → 想换引擎。每一次都以为找到了，跑起来发现还是 3 秒。

问题不在于试错，在于**我每次都直接开跑完整导出**（300 帧、十几分钟），而不是先花 30 秒测一帧。所以每一轮反馈周期是十几分钟而不是半分钟。

**该早点做的**：写一个「只渲染 3 帧、只测一帧耗时」的探针，先把墙在哪量清楚，再决定要不要绕。

## 6. 可迁移的部分

### 6.1 无头浏览器做逐帧导出的检查清单

要拿 Chrome 逐帧导出视频，**先按这个顺序量一遍**，别急着开跑：

```javascript
// 在页面里跑，量「渲染 + 读回」一步到位的真实耗时
const gl = renderer.gl, w = renderer.width, h = renderer.height;
const px = new Uint8Array(w * h * 4);
const time = (n) => {
  renderFrame(); gl.finish();            // 预热一次
  const t0 = performance.now();
  for (let i = 0; i < n; i++) {
    renderFrame();
    gl.bindFramebuffer(gl.FRAMEBUFFER, fbo);   // 读自己的 FBO，别读默认帧缓冲
    gl.readPixels(0, 0, w, h, gl.RGBA, gl.UNSIGNED_BYTE, px);
  }
  gl.finish();                            // ← 没有这句，测出来的全是假的
  return (performance.now() - t0) / n;
};
```

**三条铁律**：

1. **必须 `gl.finish()`**，否则测的是 CPU 提交时间。
2. **永远不要读默认帧缓冲**（`bindFramebuffer(..., null)` 再 `readPixels`）。实测比读自己的 FBO 慢 3 倍以上，因为要等合成器交接。
3. **先量一帧再开跑**。我在这上面浪费了最久。

### 6.2 无头 Chrome 的 `requestAnimationFrame` 是节流的

这条坑得单独说：**无头模式下 rAF 可能几秒才触发一次**。

我早期被这个骗了很久——页面自报「30 fps」（那是它自己的计时器），但 `window.__frameCount` 十几秒才 +1。**别拿 rAF 的节奏去判断渲染性能**。

想绕开节流就**同步渲染**：导出一个 `drawAt(t)` 函数，直接在 `page.evaluate` 里调它，不等 rAF。这个改动本身是对的，即使最后没能出片。

### 6.3 油画 / 图像 → 3D 的通用套路

结构张量那一套（Sobel 梯度 → 张量分量高斯模糊 → 主特征向量）不只对油画有用：

- **铅笔素描** → 沿线条走向的立体丝带
- **水墨画** → 按墨色浓度定深度 + 笔锋方向
- **地形图 / 等高线** → 直接用梯度当法线

关键性质是那个「**归位即成画**」：所有位移都乘一个全局系数，系数归零就还原成原图。这样运镜可以「飞出去、再飞回来」，比单纯的 3D 展示有记忆点得多。

### 6.4 环境上的三个具体坑

1. **PowerShell 的 `Invoke-WebRequest` 在这台机器上对所有 HTTPS 站点报 SSL 失败**——是 PowerShell 自己的 TLS 问题，不是网络不通。**测连通性一律用 `node -e "fetch(...)"`**。（这条是 AGENTS.md 里早有的记录，这次又验证了一遍。）
2. **`pnpm` 在沙箱里建符号链接会 EPERM**，而且失败会污染 `node_modules`。换 npm + `--cache .\.npm-cache`。
3. **`readPixels` 出来的像素是自下而上的**，喂给 ffmpeg 前要逐行翻转。这个容易忘，忘了就是整个画面上下颠倒。

## 8. 如果还要再做一次

**技术上可行的三条路**，按我现在的判断排序：

1. **别用无头浏览器采集**。用本机原生渲染（Node 端 Skia / 或直接用 Blender、After Effects 这类），绕开 Chrome 的合成器交接。
2. **真要用浏览器**：把笔触数压到 1 万以内、分辨率降到 720p、关掉后处理，**先量出一帧的真实耗时**，再算总量决定做多长。
3. **接受它是交互网页而不是片子**。网页版在强一些的显卡上（独立显卡）是能实时跑的；这台是 Intel 集成显卡，20 万像素 × 大量 overdraw 就是它的上限。

**但我更想记下的是流程上的教训**：

> **先用 30 秒量清楚瓶颈在哪，再决定投多少时间。**
> 我这次是反过来的——先投了两小时做功能，最后才去量「一帧到底多贵」，
> 结果发现瓶颈根本不在我优化的地方。
