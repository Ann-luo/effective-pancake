## 一、先说结论（懒人版）

1. **同一个症状，三次不同的真相**：「工具全没了」是**客户端**卡在半个会话里；「星图空着」是**客户端**那条腿断了；
   「看板上一栏空着」是**上游代码里根本没人写那个字段**。
2. **"服务端坏了"这个猜测，三次都错了。**
3. **一条救命的判据**：服务器日志里出现**孤零零一个 `202 Accepted`**（前面没有成对的 `200 OK`）=
   客户端连上了但**没做握手** → **是客户端的问题，别重启容器**。
4. **我的第三次误判最该骂**：我**先**跟用户说了"加了回传之后那栏就会长东西"，
   **后来**才去 grep 整个代码库 —— 那个字段全库只出现在「数它有几个」和「读它」两处，
   **没有任何地方写它**。**我错在没查参数表就下了结论。**
5. 一条通用教训：**"看着是同一个问题"往往最骗人** ——
   先问一句"我看到的这个界面/这个报错，真的反映了我以为的那一层吗"。

## 二、第一次：用户说「记忆库的工具突然全没了」

### 用户看到的

用户反馈：客户端里报 `Tool not found` / `Package not found`，记忆库那套工具**全掉了**。
从用户这边看，就是"记忆库挂了"。

### 我的第一反应（错的）

**"服务端是不是挂了？"** —— 这是最自然的猜测，也是**最省事的解法**（重启容器）。

我没有直接重启。先去服务器上量了一遍：

```text
容器状态      Up 26h              ← 26 小时没重启过，说明它一直好好活着
RestartCount  0                   ← 一次都没崩过
OOMKilled     false               ← 不是被内存杀掉
MCP 现调       tools/list → 18 个工具      ✅
               breath     → 能拿回记忆正文   ✅
```

**服务端一点事都没有。** 它自己不觉得自己出过任何问题。

### 真正的判据：日志里那个孤零零的 `202`

那问题在哪？去看服务端日志的**时间线**：

```bash
docker logs <容器名> --since 20m -t 2>&1 | grep '"POST /mcp'
```

关键判据是这个：

> **如果出现孤零零一个 `202 Accepted`（前面没有成对的 `200 OK`）**
> → 说明客户端**连上了，但没做 `initialize` 握手** → **是客户端卡住了。**

一个健康的握手长这样（成对的）：

```text
200 OK   ← initialize
202 Accepted   ← 握手完成
200 OK   ← tools/list
```

而我们当时看到的，是**只有中间那一个 `202`，前面没有 `200`** ——
意思是它把请求发到了，服务端也接了，但**握手那一步从来没完成**。

同时还伴随着两个伴生现象，都对得上：

| 伴随现象 | 含义 |
|---|---|
| `400 Bad Request` | 客户端拿着一个**服务端不认的会话**在请求 |
| 隧道层 `context canceled` | 隧道把请求掐断了 → 握手被打断在半路 |

**`202` 有了、`400` 有了、`context canceled` 有了 —— 三个都对上，那就不是玄学，是客户端卡在半个会话里。**

### 解法：在客户端断开重连，服务端不用动

**用户的动作很简单：在客户端把这个 MCP 断开、重连**（不行就删了重加）。

结果：

```text
重连后 12 秒内恢复正常
之后连着 4 次真实调用全 200
重连成功的标志：日志里出现一对新的
  200 OK（initialize） → 202 Accepted（握手完成） → 200 OK（tools/list）
```

**服务器一行没动。**

> ⚠️ 这一条我后来写进了排错第一站，因为它太容易搞反了：
> **看到工具全没了，第一反应不是重启容器，是先看一眼那个 `202` 是不是孤零零的。**
> 重启容器不但没用，还会把好好的服务打断一次、并且让它掉出共享网络（那是另一个坑）。

## 三、第二次：星图空着，我一度想去改服务端源码

记忆星图是网页上一张可视化：每颗星是一条记忆。它**一直空着**。

我当时的想法是：**"这是网页端的功能，多半是服务端少了一条接口，我去给服务端加一条路由。"**
（上游确实有一篇文档在讲怎么给记忆库加这条路由 —— 所以这个猜测看起来还挺有依据。）

真去查了才发现方向反了：

```text
星图的首选数据源：请求记忆库的 /api/bucket-map
                   → 实测 404，我们跑的这个版本里根本没有这条路由

于是退回第二条路：调 MCP 的 pulse 工具，解析返回文本

但 pulse 也是 MCP 调用 —— 撞的是同一个 session id 的错
                   → 所以星图一直是空的
```

**根因和「读记忆坏了」是同一个**：客户端那条腿断了，星图只是它的另一个受害者。

我本来要写的那个服务端补丁，**不需要写**。详见 [4.21 那篇](https://ann-luo.github.io/effective-pancake/2026/10/11/%E4%B8%80%E8%A1%8Cthrow%E8%AE%A9%E5%BF%83%E6%BD%AE%E7%99%BD%E8%A3%85%E4%BA%86%E4%B8%80%E5%A4%A9.html)。

**这次误判的性质**：我把"界面上的东西坏了"直接等同于"提供界面的那一层坏了"。
实际上界面底下有两条路，坏的是**下面那条调用链**，不是最上面那个提供接口的东西。

## 四、第三次：那栏一直是空的 —— 这条最该写透

### 用户看到的

看板上有一栏「念头」，**一直是空的**。

### 我错在哪：我先把结论说出去了

**我当时跟用户说的是**："加了回传之后，那栏就会长东西。"
（意思是：数据没写进去是因为缺一个回传入口，加上就好了。）

**说完之后**我才去做那件早就该做的事 —— **递归 grep 整个代码库，看那个字段到底是谁在写。**

```text
搜 flashThoughts：

  出现 1：数它有几个   ← 读
  出现 2：读它         ← 读

  总计 2 处，没有任何地方「写」它
```

**那个字段全库只有两个出口，没有入口。**

所以那栏空着**不是因为我没加回传**，也不是配置问题 ——
**上游代码里，那一栏就是一条断头路**：有人把显示和统计都写好了，但**从来没有人往里面放数据**。

### 我错得具体在哪

不是"猜错了"，而是**流程反了**：

| 我做的 | 应该做的 |
|---|---|
| 先给用户一个听起来合理的解释（"加回传就会长东西"） | **先查参数表**：这个字段是谁写的、写到哪、什么时候写 |
| 凭"这类功能一般是缺回传"的直觉 | 凭 grep 结果 |
| 让用户按我的猜测去预期结果 | 让证据决定我说什么 |

> 这就是最典型的一种翻车：**结论说得比查证早一步。**
> 而且它比"查不出来"更糟 —— 因为用户会按我那句话去等一个**永远不会发生的结果**。

### 顺便确认了一件没用的事：没得升

查完之后我想："那去上游升个版本，说不定已经修了。"
去看了一眼：**上游 main 分支的版本号，和我们正在跑的一模一样。**

**没得升。** 这条路当场就断了 —— 不然我会去折腾一轮升级，然后什么也没变。

## 五、三次之后，剩下的一条方法论

三次误判，骨架是同一个：

| # | 我看到的 | 我以为的那一层 | 真实的那一层 |
|---|---|---|---|
| 1 | "工具全没了" | 服务端挂了 | **客户端**卡在半个会话里 |
| 2 | 星图空着 | 服务端少一条接口 | **客户端**那条腿断了 |
| 3 | 一栏空着 | 缺一个回传入口 | **上游代码里没人写那个字段** |

**"看着是同一个问题"往往最骗人。**

具体到能用的动作，就一句：

> **先问："我看到的这个界面 / 这个报错，真的反映了我以为的那一层吗？"**

拆成三个可以照着做的动作：

1. **先量服务端，再动手。** 容器 `Up 26h` / `RestartCount=0` / `OOMKilled=false` / 现调现通 ——
   四行数字就能把"服务端坏了"这个猜测排除掉，比重启一次容器还快。
2. **看日志的"形状"，不只看有没有报错。** 今天最有用的一条判据不是某个错误信息，
   而是**"那个 `202` 是不是孤零零的"** —— 这是**成对关系**上的异常，不是单条日志上的异常。
3. **界面上缺东西时，先 grep 谁负责写它。** 不要先假设"缺的是入口"。
   **读和写都要数**：今天那个字段读的地方有 2 处、写的地方有 0 处 —— 数出来只要一行命令。

## 六、最后

今天这一天，真正让我难受的不是那三次猜错 —— **猜错很正常，谁都会。**

难受的是第三次：**我把结论说在了查证前面。**
前两次我只是自己想了错的方向，然后去查、被证据纠正；
第三次我是**先让用户产生了预期**，才去查。

如果那天我查完再说，那句话就根本不会说出口。
