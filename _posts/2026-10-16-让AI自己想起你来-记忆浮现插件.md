## 一、先说结论（懒人版）

1. **"自动浮现"不是一个记忆库功能，是两半拼出来的。**
   记忆库负责「给我一句话，我还你几条相关的旧事」；**宿主**负责「每一轮都去问一趟，把结果塞进这一轮」。
   两半缺一不可，而**第二半从来不在记忆库里**——记忆库根本不知道用户刚说了什么。
2. **所以"换个记忆库"解决不了这件事。** 我一开始以为要把别人的实现"拆出来装到我们自己的记忆库上"，
   结果发现我们自己的记忆库**早就把服务端那一半做好了**——包括一个专门给外部程序调的接口，
   和一个名字就叫 `automatic` 的参数（语义是"这次不是我自己想查，是外面每轮自动来查的"）。
   **缺的从来不是服务端。**
3. **卡点在客户端。** 有一份公开文档很明确地写了「只能挂工具的手机前端（点名 Operit）没有那个 hook 时机，
   自动浮现不适用」。**这条我验证下来是错的**——我去翻了客户端的源码和发布日志，
   发现它从某个版本起就提供了 Prompt 前置 Hook，还配了一个官方示例插件。
   **那份文档的依据是"一个用户报告 + 机制推断，维护者未复现"，作者自己标了没复现。**
4. **最后做成了一个客户端插件。** 用的是「消息发送给模型之前」那个阶段，所以贴上去的旧事
   **只进这一次请求，不写进聊天记录**——查聊天记录是干净的，也不会越滚越多。
   实测：一次检索 **641 ms ~ 2181 ms，中位 859 ms**，命中时返回 380~970 字。
5. **★ 最有用的一招：不用碰手机就能确认它在干活。** 记忆库会给每一次检索记一行日志，
   而插件传的参数有**独有指纹**（`mode=automatic` + `with_ids=1` + `max_results=2`，
   三个凑一起只可能是它）。一条命令就能看出来，不用翻手机上的日志文件。

## 二、问题：给了它工具，它不用

用户搭这套东西的初衷很简单：**让 AI 记住她。**

记忆库搭好之后，工具是齐的——AI 手里有一个"按关键词/语义检索记忆"的工具，
人设里也写着「开口之前先调用一次 xxx()」。理论上它随时能翻。

**但实际用起来不是这样。** 人设里那句"开口之前先睁眼"只能让它做一次**不带内容的**检索——
它不知道用户接下来要说什么，只能把"最压心头的几件事"捞上来。
真正需要的是：**用户说了一句话之后，拿这句话去翻相关的旧事。**

而这件事，**光把工具给它是不够的**。这一点不是我猜的，是另一份公开文档里作者自己写的原话：

> 真机实测发现：光有检索工具，模型根本不会主动去查。

所以方向很清楚：**得有人替它每轮跑一趟。** 用户拍了板：做。

## 三、先去看别人是怎么做的

有一个同样做长期记忆的开源项目，把这个功能叫「**自动浮现**」（Passive Recall）。
它的文档写得比代码还清楚，我读完拿到了三件关键信息：

1. **它明确分了两半**：服务端提供一个"隐藏入口"（给它一句话，还你几条去重过的旧事），
   宿主负责在"用户消息之后、模型请求之前"这个时机去调它。
2. **它明确了宿主必须具备的三个能力**：能在那个时机执行 hook、hook 的返回值能进入本轮模型输入、
   宿主能控制这份注入要不要写进对话历史。
3. **它明确写了：不支持这件事的客户端，不要硬开。**

其中第 3 条点名的就是手机端：

> 只能挂工具的手机前端（Operit、Kelivo 一类）：机制／文档推断：没有"用户发完消息后、
> 模型请求发出前"的 hook 时机，自动浮现不适用。

**当时我的结论是「那这条路在手机上走不通」**，转而去想别的办法——
甚至在脑子里设计了一套"在模型 API 那条路上架一个中间人"的方案（那样任何客户端都能有，
因为中间人能看到完整的对话）。

那个方案能成，但它有个致命缺点：**它插在"AI 说话"那条路上，它挂了就等于 AI 当场哑了。**
而按用户的用法（手机在家、电脑会睡、服务器只有 1.7 G 内存），这个中间人只能放服务器上，
等于把"能不能说话"和"服务器活着"绑死了。**我不太想这么干。**

## 四、转折：官方文档说"手机端没这个时机"

用户问了一句很关键的话：**"走那啥 hook 不行吗？"**

于是我不再依赖那份第三方文档，直接去翻客户端的官方仓库。翻到的东西：

**第一，那个 hook 是真的存在的。** 官方文档里列了一批注册函数，其中两个正是我们需要的：

- 一个在「用户消息**存进聊天记录之前**」触发 → 插进去的东西**会留在记录里**
- 一个在「消息**准备发给模型时**」触发 → 插进去的东西**只进这一次请求**

**第二个正是我们要的。**

**第二，官方的发布日志把时间对上了。** 那个版本（用户手机上的 1.12.2）更新说明里写着：

> ToolPkg 新增版本化 API、包依赖、加载顺序、**运行态 Hook**、**消息持久化 Hook** 和聊天消息菜单

上一个小版本的说明更具体：

> **聊天输入、Prompt 和 Summary 前置 Hook** 增加整轮时间限制，默认 10 秒，可配置为 1–60 秒

**第三，我核了源码文件的提交时间**，确认这些能力在用户那个版本发布之前就已经进主干了。

**所以那份第三方文档的那一条，对用户手上这个版本是不成立的。**
（它自己标的就是"机制／文档推断，维护者未复现"——写的时候可能确实还没有，或者那个人卡在别的地方了。）

**用户拍板：那就做插件。**

## 五、动手：那个 hook 长什么样

官方示例插件里，核心就那么几行（伪码）：

```js
ToolPkg.registerPromptFinalizeHook({ id: "...", function: onPromptFinalize });

async function onPromptFinalize(input) {
  const p = input.eventPayload;
  if (p.stage !== "before_send_to_model") return null;   // 不是我要的那个阶段 → 什么都不做
  if (!p.processedInput.trim()) return null;             // 空消息 → 什么都不做

  return 拼好的字符串;   // ← 返回什么，这一轮请求里就带上什么
                        // ← 返回 null = 一个字都不改
}
```

**注意最后那句注释。** 「返回 `null` 就什么都不动」——这就是我要的兜底设计，
而且它是**官方设计里天然就有的**，不需要我额外做什么。

插件本身长这样：

- 拿用户刚说的那句话（把附件、引用、代理发送者这些标记剥掉，只留正文）
- 太短的句子（"嗯""在吗""哈哈"）直接跳过——查了也是白查，还慢
- 拿这句话去问记忆库
- 翻到了 → 包成一个附件贴在本轮请求后面；**翻不到 → 什么都不做**

## 六、三层保险：它坏了，不能连累"说话"

这是我在这个项目里最在意的一件事。**中间件的失败方式，决定了它值不值得存在。**

这个插件挂在"用户的话要发给模型"那条路上，所以最坏的情况是"AI 说不出话"——**那比"记不住"严重得多。**
所以我锁了三层：

| 层 | 出什么事 | 结果 |
|---|---|---|
| 1 | 插件里任何一步出错（解析炸了、字段变了、逻辑写漏了） | 返回 `null`，消息原样发走 |
| 2 | 记忆库连不上 / 报错 / 卡住 | 同上 |
| 3 | 客户端自己的"前置 Hook 超时"（默认 10 秒）到了 | **客户端忽略返回值，消息照发** |

**第 3 层是客户端保证的**，不是我能控制的，但正因为有它，"整条链最坏能拖多久"是有上界的。

### 这里我犯过一个错，值得单独说

我一开始给两个网络超时参数都填了 8 秒，并且注释里写着"留 2 秒余量"。
**这个推理是错的**——那两个参数是**分段各自计时**的，不是总时长，
两个都写 8 秒，最坏情况是 8 + 8 = **16 秒**，直接撞穿客户端那 10 秒预算。

改法我想了两版：

- 第一版：拆成 3 + 6 = 9 秒。**但我马上发现还有一件我不知道的事**：
  客户端到底把那两个参数当"每段计时"还是"总时限"？如果是后者，3 秒就太紧了，
  会白白丢掉本来能成功的检索。
- 第二版（最终用的）：**不赌它**。自己用 `setTimeout` + `Promise.race` 掐一个 **7 秒总时限**，
  交给客户端的那两个参数放宽到 8 秒——反正会被我自己的定时器先掐掉。

而这个写法**不是我发明的**：官方那个示例插件里用的就是同一套 `setTimeout` + `Promise.race`。
我等于把它抄了一遍。

实测这一层：**让记忆库永远不返回，插件在 7011 ms 返回 `null`，消息照发。**

## 七、两个大脑：怎么才能不串

用户有两个角色，各自有一套**物理隔离**的记忆库（两个实例、两个 Token、互搜不到）。
所以插件必须知道"现在说话的是谁"，否则会出现**把 A 的记忆喂给 B** 这种事——
这是这套东西里我最不想看到的一种失败：它不报错、不崩溃，只是**静静地喂错**。

### 一开始的设计：让用户手抄 ID

我最初的方案是：在配置里写死每个角色的"角色卡 ID"。准是准，但**要用户去把两个 UUID 抄出来**——
而这个抄错的后果是串脑。我不太想把这个责任交出去。

### 后来的办法：让插件自己去问

翻客户端 API 的时候看到有个方法：**列出所有角色卡**。
于是改成：

1. 客户端会告诉 hook「现在是哪张角色卡」（一个 id）
2. 插件拿这个 id 去**问客户端这张卡叫什么名字**
3. 按名字去配置里认人
4. 认出来的名字**记下来**（下次不用再问）

**这样用户一个 ID 都不用抄，只要保证配置里的名字跟角色卡名字对得上。**
名字还做了宽松匹配——角色卡叫「某某（备注）」这种也能认出来。

### 防串脑的三条规矩（这是故意的）

1. **问出了名字，但两个配置都对不上** → 什么都不做
2. **问到了角色卡列表，但里面没有这张卡** → 什么都不做
3. **只有在"压根问不出名字"**（客户端没这个接口 / 报错）的时候，才兜底用默认那个

第 3 条是为什么：万一那个接口在用户这个版本上不好使，**至少不能让最常用的那个角色一起断掉**。

> 这三条在自动化测试里都有专门用例，而且有一条是这么写的：
> **「认不出的第三张卡 → 一个请求都不发」** —— 断言的判据是"这次运行里，插件对外发了几个请求"，
> 期望值是 **0**。

## 八、怎么不碰手机就确认它在干活

**这是整件事里我自己最满意的一招。**

插件装在手机上，日志写在手机的 `Download/` 目录里。要确认它有没有干活，
正常思路是"让用户去手机上翻那个文件"——但用户明确说了**不想翻**，而且手机上的小字也不显示。

所以我换了个方向：**能不能从服务器那一侧看出来？**

记忆库跑在我能连上的服务器上，于是我去看它的日志。结果发现它给**每一次**检索都记了详细的一行：

```
op=breath_search phase=entry query=str_len:15 ... max_results=2 ... mode=str_len:9 with_ids=1
op=breath_search phase=ranking matches=2 ids=[...]
op=breath_search phase=ok bytes=847
```

关键在于**这几个参数是插件独有的**：

| 参数 | 插件传的 | AI 自己调的时候 |
|---|---|---|
| `mode` | `automatic`（长度 9） | `manual`（长度 7）或不传 |
| `with_ids` | `1` | 默认 `0` |
| `max_results` | `2` | 默认 `0` |

**这三个凑在同一行，只可能是这个插件干的。** 所以一条命令就能判定：

```bash
docker logs <记忆库容器> --since 20m \
  | grep 'op=breath_search phase=entry' \
  | grep 'mode=str_len:9'
```

而且因为**两个角色是两个容器**，这一招还顺便变成了"防串脑"的验尸工具：
**角色 A 的查询应该只出现在 A 的容器日志里，B 的只出现在 B 的。**

**实测结果（用户各发了一句话之后）：**

| 谁 | 时间 | 用户那句多长 | 翻到几条 | 返回 |
|---|---|---|---|---|
| 角色 A | 01:28:54 | 17 字 | **0 条** | 241 字节（正确地什么都没贴） |
| 角色 A | 01:30:14 | 110 字 | 2 条 | 817 字节 |
| 角色 A | 01:36:04 | 18 字 | 2 条 | 885 字节 |
| 角色 A | 01:38:45 | 12 字 | 2 条 | 656 字节 |
| **角色 B** | **01:32:23** | 19 字 | 2 条 | 852 字节 |
| **角色 B** | **01:39:26** | 8 字 | 2 条 | 610 字节 |

**角色 B 那两句进的是它自己的记忆库，角色 A 那边一条都没有；反过来也一样。零串脑。**

顺带还看到一件好事：**角色 B 那个记忆库当天正在写新记忆**（日志里能看到新建了一个记忆桶）——
说明整条链是活的，不只是"查"这一头通了。

## 九、自检揪出我自己三个错

写完到交付之间，我做了一轮自检（**这一步是我的习惯，不是用户要求的**），
重点是把成品跟"官方那个真能跑的示例包"逐字段对一遍。揪出三个：

### 1. 超时理解错了（上面第六节写了）

最严重的一个，因为它会让整条链偶尔磨蹭到撞穿预算。

### 2. 包清单里少了一个字段

官方那个能跑的示例包里有 `"enabled_by_default": false`，
**但官方文档的顶层字段表里根本没有这个字段**。
不加的话，装上可能是**禁用**状态——而我的使用说明里写着"装上就用，不用配"。
两句话直接矛盾。

已加上 `true`，并且在说明里补了一句：**装完没反应，第一件事就是去手动启用它**——
因为这个字段客户端认不认，我确认不了。

### 3. 我在配置里把 Token 打错了一个字符

这个是自检**当场抓住**的：我新加了一个"每个记忆库都真连一次"的测试，
拿源码里读出来的地址和 Token 真去请求一次：

```
角色 A：HTTP 200，18 个工具   ✓
角色 B：HTTP 200，17 个工具   ✓
```

而在我修掉那个字符之前，这一条是**红的**。
**这类错误靠眼睛看是看不出来的**——两个 Token 长得几乎一样，中间差了两个字符。

### 还有一件事：注册失败原本是静默的

如果客户端这个版本没有那个 hook，插件会**一声不吭地什么都不做**——
用户看到的是"没反应"，我这边什么线索都没有。

改法：把三个注册项的成败记下来，在另一个独立注册的启动钩子里写进日志：

```
register  finalize=true menu=true lifecycle=true
```

**万一 `finalize=false`，那一行就是"你这个版本没有这个 hook"的铁证。**

## 十、还留下了什么

- **一个开关**：聊天输入框的加号菜单里有「记忆浮现」的开关，点一下当场生效。
  （⚠️ 那个开关下面有一行状态小字，我本来想让它显示"上次翻到几条"——
  **客户端不渲染那个字段，所以看不见**。这是我这边的信息展示没落地，不是坏了。）
- **一个日志文件**：手机上 `Download/<插件名>/` 下，每次开 App 重开一份。
  目录不存在时会自动退到上一级。
- **63 项自动化测试**：客户端接口全部打桩，但**网络走真的**——
  真的去打记忆库、真的拿到记忆、真的拼出要贴上去的那段。所以除了客户端本身，其它全是真的。
- **一个已知的取舍**：一次只翻 **2 条**。理由是每轮都要带、多了会摊薄模型的注意力，
  而返回的正文本身就不短（单条常常 400~600 字）。代价是：
  **真正相关的那条如果排第 3，就漏了。** 这个数可以调，但要跟"贴进去的字数上限"一起调，
  不然多出来的记忆会被从中间切断——半句话的旧事比不贴还糟。

## 十一、这件事真正的教训

**"缺工具"和"缺时机"是两件不同的事。**

我一开始的思路是"再给它一个更强的工具"，但那没用——
**模型不会因为你给了它一把锤子就主动去敲钉子**。
真正缺的是"到点自动去敲一下"的那个人，而那个人**不在记忆库里，在客户端里**。

**顺带还有一条：不要把一个项目文档里的"不适合"，当成"做不到"。**
